# Phase 2.6 Design — Sandboxed run pods

**Date:** 2026-10-01
**Phase:** 2.6
**Surface:** Infra
**Stage:** phase (one phase, implementation-ready)

Brainstormed with the owner on 2026-10-01. The four scope rulings and the choice of architecture are
recorded under [Owner rulings](#owner-rulings-2026-10-01).

## Goal

An agent-written file can never execute on the API host. Each run's worktree, its `workspace__*` tools,
its Roslyn server, and new build and test tools live in a per-run Docker sandbox that holds no secrets
and cannot reach the network except NuGet. The sandbox hands its work back as a git bundle, and the
trusted API side publishes from that bundle. Once confinement holds, the write extension allow-list is
relaxed.

## Background

- **The threat is proven.** The MSBuild spike (`docs/plans/2026-09-25-phase-2.5-msbuild-execution-spike.md`)
  showed that a `Directory.Build.props` or `.csproj` hooked to `BeforeTargets="CoreCompile"`,
  `ResolveAssemblyReferences`, `ResolvePackageAssets`, or `InitialTargets` runs code. It does so on the
  RoslynCodeLens server's first load, and again on every `rebuild_solution`.
- **The control so far is an allow-list.** Phase 2.5 limited writes to `.cs` and `.md` (ruling R29).
- **Everything still runs inside the API process.** The run worktree under `<DataRoot>/runs/<runId>`
  (Thalos `GitWorktreeWorkspaceProvider`) is there, along with:
  - `workspace__*`, a concrete local-filesystem `WorkspaceTools`;
  - the run-scoped RoslynCodeLens server, a stdio child process started by `RunMcpServerRegistry`, which
    hard-codes `StdioClientTransport`;
  - publish, which runs local `git` and LibGit2Sharp on `ws.Root`.
- **Five consumers treat `RunWorkspace.Root` as a host path:**
  - `WorkspaceTools`
  - `ManufactureRunStarter` (it reads `AGENT.md`)
  - `StandingInstructionsWriter`
  - `OpenPullRequestAction` and `ThalosPullRequestPublisher`
  - `GitCliRunWorkspaceGit`
- **Nothing ever runs `dotnet restore`.** B17's run server therefore reported 35 bogus xunit errors.
  Restoring on the host would itself be a code-execution path.
- **There is no deployment target yet.** The repository has no Kubernetes, Helm or ArgoCD files, and no
  Docker or Kubernetes client library. The API image is `aspnet:10.0-alpine` with no git, no SDK and no
  `dnx`.

## Owner rulings (2026-10-01)

1. **Backends: Docker now, with a seam for Kubernetes later.** This phase builds an `ISandboxRuntime`
   abstraction and a Docker backend, used under Aspire, and proves the live run against it.
   The Kubernetes backend is a later phase, along with RBAC, NetworkPolicy, ArgoCD for the static
   deployment and pod-local `emptyDir` volumes. It waits until Daedalus actually deploys to a cluster.
2. **Egress goes through a NuGet-only proxy.** The sandbox sits on an internal Docker network with no
   route out. An allow-listing forward proxy that sits on both networks permits only the NuGet hosts.
3. **Build and test tools are added.** `sandbox__build` and `sandbox__test` run fixed commands, with no
   arbitrary shell. Test results reach the review lenses as host-recorded evidence.
4. **The allow-list relaxes to any extension, with CI paths protected.** For sandboxed grants the
   extension allow-list is removed. A reviewed list of protected paths is enforced at write time and,
   decisively, again at publish.
5. **Architecture A: the sandbox owns the worktree.** The sandbox host serves its tools as a remote MCP
   server, and code moves in and out as git bundles. The API keeps the mirror and the GitHub token.
   - Rejected: B, a shared volume. Host git and file tools would operate on a tree that sandboxed code
     can mutate.
   - Rejected: C, a file-system RPC alongside MCP. It adds a second protocol and duplicates confinement
     checks.

## Approach

### Components

The generic parts go in Thalos, per the 2026-09-21 direction that Thalos.NET is the reusable framework.
Expect one Thalos minor release, which will be breaking where interfaces gain members (R28 precedent).

**Thalos:**

1. **`ISandboxRuntime`**, in a new `Thalos.NET.Sandbox`. It exposes `CreateAsync(SandboxSpec)`,
   `GetAsync(id)`, `DeleteAsync(id)` and `ListAsync()`, all returning `Result`-shaped values.
   - `SandboxSpec` carries the image, the run id, the CPU, memory and pids limits, the network name and
     a per-sandbox bearer token. It carries **no other environment**, so "no secrets" holds by
     construction rather than by filtering.
   - `SandboxHandle` exposes the id, the MCP endpoint and the container state.
2. **`Thalos.NET.Sandbox.Docker`**, a Docker Engine API backend. The client library is chosen in the
   plan; the Docker.DotNet fork that Testcontainers already uses is the default candidate. Each
   container gets:
   - an `--internal` network, with no published ports;
   - a non-root user;
   - `cap-drop ALL` and `no-new-privileges`;
   - a read-only root filesystem, plus one writable work volume and a tmpfs `/tmp`;
   - pids, CPU and memory limits;
   - no Docker socket;
   - labels `thalos.sandbox=true` and `thalos.run_id=<id>`.
3. **The sandbox host**, `Thalos.NET.Sandbox.Host`. It is a small ASP.NET app and the image's entry
   point.
   - **Tools:** it serves Streamable HTTP MCP behind the bearer token, with these tools:
     - `workspace__*` — the existing `WorkspaceTools` and path hardening, now against a local root;
     - `sandbox__build` and `sandbox__test`;
     - `roslyn__*` — proxied to a RoslynCodeLens stdio child that the host supervises.
   - **Control endpoints:** `import` (receive a bundle, clone, restore, load), `export` (bundle the run
     branch) and `ready`.
4. **`SandboxRunWorkspaceProvider : IRunWorkspaceProvider`**, which replaces `GitWorktreeWorkspaceProvider`
   for runs. `RunWorkspace` stops promising a host `Root` for sandboxed runs. Consumers that need files
   either go through the sandbox, or work on the trusted side from the mirror and bundle.
5. **A transport seam in `RunMcpServerRegistry`.** A run-scoped server can be a remote HTTP endpoint,
   resolved from the run's sandbox handle, not only a stdio child. Run tool schemas come from the run's
   own server, which removes the dependency on the host-wide server and its hard-coded
   `C:/Projects/Prive/daedalus/Daedalus.sln`.

**Daedalus:**

6. **The sandbox image**, `src/Daedalus.Sandbox/Dockerfile`. It contains the .NET 10 SDK, git (2.32 or
   later), RoslynCodeLens 2.18.1 pre-installed so no `dnx` download happens at run time, and the sandbox
   host.
7. **A NuGet egress proxy container.** It allow-lists `api.nuget.org`, `*.nuget.org` and the NuGet CDN
   host. It joins both the internal sandbox network and the default network. The sandbox gets
   `HTTPS_PROXY`.
8. **Aspire AppHost wiring:** the proxy, the internal network, and the image built from the Dockerfile.
   The API gets the Docker endpoint, the image and the network name through config. The API joins the
   internal network, or reaches it in the way the plan's spike decides for a host-project API under
   Aspire.
9. **Trusted-side publish.** `OpenPullRequestAction` works from the stored bundle and a clean host
   worktree. `StandingInstructionsWriter` writes `AGENT.md` there, never into the sandbox. Then commit,
   push and open the PR, as today.

### Run lifecycle

| Moment | What happens |
|---|---|
| **Start** (`ManufactureRunStarter`) | 1. The provider takes the mirror lock and runs `git fetch` into the bare mirror. No code runs. 2. It creates a bundle with `git bundle create` of `origin/<default>`. 3. It creates the sandbox and POSTs the bundle to `import`. 4. Inside the sandbox, the host clones from the bundle and runs `checkout -b manufacture/<runId>`, with `core.symlinks=false` and hooks disabled. It runs `dotnet restore` through the proxy, then RoslynCodeLens loads the solution. 5. `AGENT.md` is read on the trusted side with `git show` against the mirror, never from the sandbox. 6. A sidecar record is written under `DataRoot`, holding the run id, container id, endpoint, token and state. |
| **Dispatch gate** | `RunToolServersReadyGate` waits on `ready`, which means import is done, restore was attempted and Roslyn is loaded. A failed restore is not fatal: a `SandboxRestoreFailed` event is recorded and `ready` reports it, since the agent may be the one to fix it. |
| **Node turns** | `workspace__*`, `sandbox__*` and `roslyn__*` route to the run's sandbox endpoint by the `thalos.run_id` claim, as run-scoped routing does today. Write grants, per-grant claims, tool policies and the audit all stay on the API side. The sandbox only executes calls that have already been authorized. |
| **After a write** | The host marks the solution dirty. If a `*.csproj`, `*.props`, `*.targets`, `global.json`, `NuGet.config` or `Directory.Packages.props` file changed, it re-runs restore before `rebuild_solution`. |
| **Build and test** | The commands are fixed: `dotnet build <sln>` and `dotnet test <sln> [--filter <validated>]`. Each has a timeout and capped output (the tail plus a summary), and returns its exit code. On timeout the process tree is killed inside the sandbox. Test results are recorded as host evidence for the review lenses. |
| **Park at the gate** | Nothing runs in the sandbox after retrospect. The sandbox exports a bundle of `manufacture/<runId>`. The API checks it with `git bundle verify` against the mirror, stores it at `<DataRoot>/bundles/<runId>.bundle`, then **deletes the sandbox**. A parked run uses no container. |
| **Resume → publish** | The API makes a clean host worktree from the mirror plus the bundle, fetched into the mirror. It runs the protected-path diff (see below), applies `AGENT.md`, then runs the existing commit, push and PR path. The host only ever receives git objects. It never checks out a tree that a sandboxed process touched. |
| **Retry** (Part C) | Retry works from the stored bundle, so it no longer depends on when the sweeper runs. This closes the "retry after sweep" gap. |
| **Sweep** | `RunWorkspaceSweeper` deletes sandboxes and bundles under today's retention rules. It also reaps labelled containers that have no record once `OrphanGrace` passes. |
| **API restart** | Containers outlive the API. On boot, sidecar records are reconciled against `ISandboxRuntime.ListAsync`: matching containers are reattached, a `Provisional` record's sandbox is deleted, and `Exporting` is retried. |

### Security model

- **The sandbox can't reach secrets or the network.**
  - Its environment is only the run id and its own bearer token. It never sees `GITHUB_TOKEN`,
    `ANTHROPIC_API_KEY`, database or Keycloak credentials.
  - Its only route out is the NuGet proxy. It has no Docker socket.
  - Its ports are unpublished and each sandbox has its own token, so sandboxes cannot reach each other.
- **The API never runs what the sandbox wrote.** It never evaluates MSBuild, never runs restore, and
  never checks out a tree that sandboxed code could mutate. It receives only a verified git bundle and
  bounded MCP results. After each bundle fetch it re-checks `MirrorConfigSurface`.
- **Protected paths are shipped, reviewed config.** The defaults are:
  - git and run state: `.git/`, `AGENT.md`, `.gitattributes`, `.gitmodules`;
  - CI definitions: `.github/`, `.gitlab-ci.yml`, `azure-pipelines.yml`, `.azure-pipelines/`,
    `.circleci/`, `Jenkinsfile`.

  The CI paths are there because the branch is pushed to the real repository. Its CI would run an
  agent-written workflow with the repository's secrets. `.gitattributes` and `.gitmodules` are there
  because the host runs `git` on the published tree.
- **Protected paths are enforced twice.** The sandbox refuses them at write time, which is a convenience.
  The API diffs the bundle against the base at publish, which is **the control**, because sandboxed code
  can write any file directly. A protected path changing fails publish. An admin retry re-runs the same
  check.
- **The allow-list relaxes only for sandboxed grants.** A grant with no extension list is refused at
  boot unless the sandbox backend is enabled. You cannot relax the allow-list without the sandbox.
- **Residual risk, accepted and documented:**
  - A run can spend NuGet bandwidth.
  - It can leak data at low bandwidth by encoding it in the package ids it looks up on nuget.org.
  - The pushed branch runs in the target repository's own CI. That is the repository's trust model.

## Files / Modules Touched

**Thalos.NET:**
- `src/Thalos.NET.Sandbox/` (new): `ISandboxRuntime`, `SandboxSpec`, `SandboxHandle`,
  `SandboxRunWorkspaceProvider`, the sidecar records and reconcile, the bundle export/verify/store, and
  the protected-path diff.
- `src/Thalos.NET.Sandbox.Docker/` (new): the Docker backend.
- `src/Thalos.NET.Sandbox.Host/` (new): the ASP.NET MCP host, `SandboxTools` (build and test), the
  Roslyn stdio proxy, and the import/export/ready endpoints.
- `src/Thalos.NET.Mcp/RunMcpServerRegistry.cs`, `RunScopedMcpToolSource.cs`: the transport seam, and
  per-run tool schemas.
- `src/Thalos.NET/Workspaces/WorkspaceTools.cs`: reused inside the host, plus an optional extension list
  and configurable protected paths.
- `src/Thalos.NET.Abstractions/Workspaces/RunWorkspace.cs`, `IRunWorkspaceProvider.cs`: `Root` is no
  longer guaranteed to be a host path.
- `src/Thalos.NET.Workflow/RunWorkspaceSweeper.cs`: deletes sandboxes and bundles, and reaps orphaned
  containers.
- `src/Thalos.NET.Git/Workspaces/`: a clean worktree built from mirror plus bundle, for publish.

**Daedalus:**
- `src/Daedalus.Sandbox/Dockerfile` (new), and a proxy config under `deploy/sandbox-proxy/` (new).
- `src/Daedalus.AppHost/Program.cs`: the proxy, the network, the sandbox image and the API config.
- `src/Daedalus.Agents/DaedalusAgentsServiceCollectionExtensions.cs` and `DaedalusAgentsOptions.cs`: the
  sandbox options, provider wiring, grant validation (no extension list only when sandboxed) and the
  protected-path config.
- `src/Daedalus.Agents/Workflow/ManufactureRunStarter.cs`: reads `AGENT.md` from the mirror, and returns
  503 when the sandbox is unavailable.
- `src/Daedalus.Agents/Workflow/OpenPullRequestAction.cs`, `StandingInstructionsWriter.cs`, and
  `src/Daedalus.Agents/Git/ThalosPullRequestPublisher.cs`: publish from the bundle-backed clean worktree.
  The publisher reads the remote from `ws.Remote`, not from the mirror's shared `origin`.
- `src/Daedalus.Api/appsettings.json`, `.mcp.json`: the sandboxed write grant, the `sandbox__*`
  envelopes and policies, and the run-scoped Roslyn entry pointing at the sandbox.
- `processes/manufacture.yaml` and the `skills/manufacture-*` files: `implement` may build and test, and
  the lenses may cite test evidence. The process version is bumped.

## Tests

Every security assertion names the change that turns it red, and that change is made once during review.
This follows CLAUDE.md, "tests that pass for the wrong reason".

- **Unit (Thalos):**
  - The `SandboxSpec` builder: no inherited environment, and every hardening flag present.
  - The protected-path diff, including renames into and out of protected paths, and `.gitattributes`.
  - The bundle-verify gate.
  - `sandbox__test` filter validation.
  - Output capping and timeouts.
  - The registry's transport seam.
  - Sweeper rules for sandboxes and bundles.
- **Integration (Thalos, Testcontainers, the real Docker engine and image):**
  - **The spike's vector 1, as a test.** A `.csproj` with a `BeforeTargets="CoreCompile"` marker `Exec`
    is written through `workspace__write_file`, followed by a reload. The marker must exist inside the
    container and not on the host. Red: an in-process fake backend.
  - **Egress.** An arbitrary HTTPS host fails, and a restore from nuget.org succeeds. Red: drop
    `--internal`.
  - **Environment.** The sandbox's environment has no `GITHUB_TOKEN` while the test process has one.
    Red: pass the host environment through.
  - **Export and publish.** Export, `bundle verify`, and a publish refusal on a `.github/` change. Red:
    skip the publish-side diff.
- **Integration (Daedalus):**
  - Claim routing reaches the right sandbox.
  - A parked run has no container.
  - Retry works after the sandbox is gone.
  - Reconcile works after a restart.
  - A grant with no extension list is refused when the sandbox is off.
  - The replacement for B16's config test: `.csproj` is allowed only under a sandboxed grant, and a
    `.github/` change is refused at publish.
- **Live proof (owner checkpoint, B17-style)** runs `manufacture` on `daedalus-sandbox` under the
  AppHost. Each step below must be recorded in the run's event log:
  1. `implement` edits a `.csproj` to add a real package.
  2. `sandbox__test` comes back green.
  3. The lenses cite the test evidence.
  4. The gate parks the run, and its sandbox is deleted.
  5. A resume opens a PR containing the `.csproj` change.
  6. The run's Roslyn output has zero restore-related diagnostics.
- **Suites:** Unit, Unit.Application, Unit.Domain, Unit.Infrastructure and Integration all pass, and all
  Thalos projects pass.

## Open Questions

None block planning. Two are left for the plan's first spike task:

- **How the API reaches the sandbox network under Aspire**, when the API is a host project rather than a
  container. One option publishes the sandbox port to loopback only, behind the bearer token. The other
  runs the API as a container in the AppHost. The spike decides, and records what weakens if loopback is
  chosen.
- **The Docker client library:** the Testcontainers Docker.DotNet fork, or calls to the Engine API's
  REST endpoints over the named pipe or socket.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Sandbox start latency (clone, restore, Roslyn load) slows every run | Minutes added per run | Measure in the live proof. The image pre-installs RoslynCodeLens. A per-repository warm NuGet cache volume, mounted read-only, is a later optimization and not built now. |
| The SDK image makes the sandbox image large (over 1 GB) | Slow first pull | Build once under Aspire, and pin the tag. |
| Docker Desktop on Windows behaves differently from Linux Docker (internal networks, the named pipe) | Tests pass in CI and fail locally, or the other way round | Integration tests run against whatever engine is present. The live proof runs on the owner's Windows box. |
| Breaking Thalos interface changes ripple through Daedalus | A larger bump task | List them all in one Thalos release, following the R28 precedent. |
| An agent fills the sandbox disk or loops a build | A run is lost | Volume size and pids, CPU and memory limits, plus per-command timeouts. A dead sandbox fails the node with `SandboxLost`. |
| The proxy allow-list is too narrow and misses a NuGet CDN host | Restore fails | The integration test restores a real package through the proxy. Proxy logs record any denied host. |
