# Phase 2.9 Design: Observability

**Date:** 2026-10-10
**Phase:** `2.9`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

## Goal

Make a manufacture run debuggable from the Aspire dashboard, or from any OTLP collector. Each step of a run is a
trace you can find by run id and follow back to the request that started it. The run's durations, outcomes and token
spend appear as metrics.

## Decisions (owner, 2026-10-10)

| # | Decision |
|---|---|
| D1 | **One trace per step, tied by run id.** Each node dispatch, host action and gate action is its own trace, tagged with the run id and linked to the run's start span. A run waits at the gate and can outlive a restart, so no span stays open for its whole life. |
| D2 | **Export over OTLP when it is configured.** Traces, metrics and logs are exported over OTLP whenever `OTEL_EXPORTER_OTLP_ENDPOINT` is set, and are not exported otherwise. Under the AppHost, Aspire sets it, so the dashboard on :17300 receives everything. There is no Daedalus-specific export configuration, and the dead `"OpenTelemetry"` appsettings sections are deleted. |
| D3 | **Turn on existing sources.** Subscribe to `thalos` (agent turns, tokens, tool calls and stores), `ZeroAlloc.Mediator`, ASP.NET Core and HttpClient. No Npgsql spans, because the outbox poller would drown the traces. Drop the dead `OpenTelemetry.Instrumentation.SqlClient` package, which is unused because the database is Postgres. |
| D4 | **A hybrid approach.** ZeroAlloc.Telemetry `[Instrument]` proxies go on the interface seams that exist. Hand-written spans go only where no seam exists. |
| D5 | **Thalos first.** Workflow-level instrumentation ships in a Thalos.NET 0.15.0 release, under its own `thalos.workflow` source and meter. Daedalus subscribes to it and adds only what is specific to Daedalus. |

**The current state, which confirms the roadmap's premise:**
- `src` contains no `ActivitySource` or `Meter`.
- `ServiceDefaults` calls `WithTracing()` and `WithMetrics()` with empty bodies: no sources and no exporters. Only logs reach OTLP.
- Thalos 0.14.2 already emits a `thalos.turn` span, turn, failure, duration and token metrics, and instrumented session, memory and skill stores. Its workflow engine emits nothing.

## Approach

### Part A: Thalos.NET 0.15.0, workflow telemetry

This is a minor release, with no breaking API change. One schema migration adds a nullable column.

1. **A source and meter named `thalos.workflow`.** They sit in the workflow assembly, alongside the existing `thalos` ones in `ThalosTelemetry`.
2. **The per-step root span.** `WorkflowNodeDispatcher` is a sealed class, so its span is hand-written. `DispatchAsync` starts `thalos.workflow.dispatch`, a span of kind `Consumer`, with these tags:
   - `thalos.run.id`
   - `thalos.node`
   - `thalos.seq`
   - `thalos.run.process`, set once the run is loaded

   It ends with `thalos.outcome` set to `completed`, `failed`, `awaiting` or `skipped`, with the span status set to Error on failure. Everything the step does nests under this span: the `thalos.turn` agent span, the review lenses' turns, the host actions, and the HTTP calls to Anthropic, GitHub and the sandbox.
3. **The link to the run's start.** `WorkflowStartRequest` gains no new field, because the store reads `Activity.Current` itself. `IWorkflowStore.StartAsync` persists the current W3C `traceparent` in a new nullable column, `trace_parent`, on the run. The migration follows `1009_add_workflow_run_event_actor.sql`. `DispatchAsync` adds an `ActivityLink` to the run's stored context when one is present. A run started before 0.15.0 has none, and is dispatched without a link.
4. **Generated proxies.** ZeroAlloc.Telemetry generates proxies with `PublicProxy = true`, the pattern Thalos already uses for its stores. Thalos wraps the implementations itself where hosts register them.
   - `IWorkflowHostAction.RunAsync(WorkflowRun run, ProcessNode node, ct)` gets the span `thalos.workflow.host_action.{type}`, tagged `thalos.run.id` (`run.Id`) and `thalos.node` (`run.CurrentNode`).
   - `IWorkflowStore` gets spans on `StartAsync`, `ResumeAsync`, `CancelAsync`, `FailAsync`, `RetryFailedNodeAsync` and `FailStrandedAsync`, each tagged with the run id. `ResumeAsync` also carries the signal. These spans make the gate approval and the admin actions visible.
5. **Metrics on the `thalos.workflow` meter:**

   | Metric | Type | Tags |
   |---|---|---|
   | `thalos.workflow.runs.started` | counter | `thalos.run.process` |
   | `thalos.workflow.runs.finished` | counter | `thalos.run.process`, `thalos.run.state` (Succeeded, Failed, Cancelled) |
   | `thalos.workflow.dispatch.duration` | histogram, ms | `thalos.node`, `thalos.outcome` |
   | `thalos.workflow.host_action.duration` | histogram, ms | `thalos.host_action` |
   | `thalos.workflow.run_tool.duration` | histogram, ms | `thalos.tool.source`, `thalos.tool` |

   The run-tool histogram is recorded from `IRunToolCallObserver`'s `RunToolCall.Elapsed`. That observer is called only after the call has finished, so a span there would be invented. The duration is the honest signal, and sandbox `build` and `test` show up as tools.
6. **Result-returning methods.** ZeroAlloc.Telemetry sets Error status only on an exception, and Thalos methods return `Result`. A failed `Result` must still mark the span as an error. The first plan task checks whether `[TraceTagFromResult]` can map `IsFailure` to the span's status.
   - If it can, the attribute is used.
   - If it cannot, a small ZeroAlloc.Telemetry feature ships first, in its own release. The feature is an opt-in status from a boolean result member. Thalos then pins that release.
   - A hand-written wrapper around a generated proxy is not acceptable. That would be the workaround CLAUDE.md forbids.

### Part B: Daedalus

1. **Wiring, in `src/Daedalus.ServiceDefaults/AspireExtensions.cs`.**
   - `WithTracing` adds:
     - the sources `thalos`, `thalos.workflow`, `ZeroAlloc.Mediator` and `daedalus.*`;
     - ASP.NET Core instrumentation, with health and alive endpoints filtered out;
     - HttpClient instrumentation.
   - `WithMetrics` adds:
     - the meters `thalos`, `thalos.workflow` and `daedalus.*`;
     - ASP.NET Core, HttpClient and runtime metrics.
   - OTLP export for traces, metrics and logs is registered only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, with one `UseOtlpExporter()` replacing the log-only `AddOtlpExporter`.
   - Delete the dead `"OpenTelemetry"` sections from the Api and Cli `appsettings*.json` files.
   - Remove the `OpenTelemetry.Instrumentation.SqlClient` reference and its version pin.
   - Remove OpenTelemetry package references from projects that do not use them. ServiceDefaults owns the instrumentation packages.
   - Web's browser-side logging setup is unchanged.
2. **Daedalus's own seams**, with `[Instrument("daedalus.manufacture")]`:
   - `IManufactureRunStarter`: span `daedalus.manufacture.start`, tagged with the repository name. The run id is tagged from the result. This span is the "run start" the dispatches link to.
   - `IWorkflowRunCanceller`: span `daedalus.manufacture.cancel`, tagged with the run id.
   - Daedalus code registers the proxies, next to where it registers the implementations today.
3. **The task id on the start span.** `TaskManufactureService` is a class in Api with no interface. Rather than invent one, it tags `daedalus.task.id` on `Activity.Current`, which is the ASP.NET Core request span, once the task is read.
4. **A token meter.** `daedalus.manufacture.tokens` is a counter tagged with `thalos.node`, `gen_ai.request.model` and `daedalus.token.kind` (input, output, cache_read or cache_write). It is emitted in `NodeUsageRecorder` when it records a completed node's usage, so a dashboard can chart token spend by node and model without querying the database. The backfill does not emit it: those tokens were spent in the past.
5. **Bump** Thalos packages to 0.15.0 in `Directory.Packages.props`.

### Rule for both parts: no content in telemetry

Tags carry only ids, names, counts, durations, outcomes and error codes. They never carry:
- prompt or agent text;
- task titles or descriptions;
- PR titles or bodies;
- finding text;
- file content;
- credentials or token values.

HttpClient spans keep the URL but mask query values, as in `?key=Redacted`, and record no request headers. That is the instrumentation default, and it is kept.

## Tests

Every assertion names a code change that turns it red, and the red is verified. Tests that pass for the wrong reason are this codebase's recurring defect.

**Thalos, unit.** These are the first `ActivityListener` and `MeterListener` tests in Thalos, so build one shared listener fixture.
- A dispatch emits `thalos.workflow.dispatch` with the run id, node, seq and process, and `thalos.outcome`. A failed node sets Error status.
- A dispatch of a run that has a stored traceparent carries an `ActivityLink` to that context. A run without one carries no link and does not throw.
- A host action call emits the host-action span with its run and node tags. A failed `Result` marks the span as an error.
- The store's resume, cancel and fail calls emit their spans, with run id and signal tags.
- Each metric records the expected value and tags, measured with a `MeterListener`.
- With no listener attached, dispatch behaves identically. The existing workflow tests guard this.

**Thalos, ORM integration:**
- Start under an active `Activity`, and `FindAsync` returns the same traceparent.
- Start without one, and the column is null.

**Daedalus:**
- **Wiring.**
  - With `OTEL_EXPORTER_OTLP_ENDPOINT` set, OTLP exporters are registered for traces, metrics and logs.
  - Without it, none are registered.
  - The tracer provider includes the `thalos.workflow` and `daedalus.manufacture` sources.
- **Start span.** The starter proxy emits `daedalus.manufacture.start`, tagged with the run id on success.
- **Token counter.** It emits per kind with node and model tags on live completion, and nothing during the backfill.
- **Privacy, end to end.** A scripted manufacture run runs under an `ActivityListener`. The test asserts that no tag value on any span contains the task description, the agent's summary text or the PR body.
- **Regression.** The full suites, Playwright included, stay green.

**Live proof, owner-gated.** Run one manufacture run under the AppHost, then check in the Aspire dashboard:
- filtering traces by `thalos.run.id` shows one trace per step, each with `thalos.turn`, host-action and HTTP children, and a link to `daedalus.manufacture.start`;
- the gate approval appears as a `thalos.workflow` resume span;
- the dispatch duration and token metrics are charted.

The dashboard's MCP endpoint is used to read the traces back if it allows that. Otherwise the owner confirms in the UI.

## Open Questions

None blocking. Resolved during planning:
- Whether ZeroAlloc.Telemetry can set span status from a failed `Result`. If it cannot, a ZeroAlloc.Telemetry release comes first, per Part A step 6.
- Whether Daedalus already receives ZeroAlloc.Telemetry transitively through Thalos, or needs its own `PackageReference` for the generator.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| ZeroAlloc.Telemetry cannot express "Error on a failed Result" | Failed steps look green in traces | Add the feature in ZeroAlloc.Telemetry and release it first. No hand-written wrapper |
| Three repositories, three releases (ZeroAlloc.Telemetry possibly, Thalos 0.15.0, Daedalus) | Slower, with ordering mistakes possible | Plan Part 0, A and B in dependency order, as 2.6 did. Each upstream release is verified on nuget.org before Daedalus pins it |
| The new nullable `trace_parent` column on a populated database | A migration failure at boot | It is a nullable column with no backfill. An old run simply has no link |
| Trace volume from HttpClient and Mediator spans | A noisy dashboard | Health and alive endpoints are filtered out. The standard `OTEL_TRACES_SAMPLER` environment variables tune it later without code |
| A tag leaks content, such as a task title in a span name | Sensitive text in a third-party collector | Span names are constants. The end-to-end privacy test guards tag values |
| `IWorkflowStore` proxy overhead on hot paths, such as the outbox poller's `FindStrandedAsync` | Extra spans on every poll | `FindAsync`, `FindStrandedAsync` and other read paths carry no `[Trace]`. Only state-changing calls are traced |
