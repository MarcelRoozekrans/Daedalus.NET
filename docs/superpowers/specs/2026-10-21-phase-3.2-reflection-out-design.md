# Phase 3.2 Design — Our own reflection out

**Date:** 2026-10-21
**Phase:** `3.2`
**Surface:** `Refactor`
**Stage:** phase (one phase, implementation-ready)

Milestone design: `docs/superpowers/specs/2026-10-17-milestone-3-design.md`, "Phase 3.2". Inputs from phase 3.1: the
AOT survey (`docs/plans/2026-10-17-native-aot-survey.md`), the native smoke run
(`docs/plans/2026-10-17-phase-3.1-native-smoke.md`) and the ratchet (`eng/aot/`). Brainstormed with the owner on
2026-10-21.

## Goal

Every reflection site in Daedalus' and Thalos' own code is replaced by a compile-time path, with behaviour unchanged:
the suites and a live manufacture run stay green on JIT, the native CLI reaches "Application started", and the
native API gets past every blocker that 3.2 owns.

## Finish line (owner, 2026-10-21)

- **Behaviour is identical on JIT.** All seven suites pass, the browser e2e suite included, and one **live manufacture
  run** against Anthropic completes, with the owner topping up credits for it. "Identical" means:
  - stored JSON is byte-for-byte what it was: workflow rows, agent sessions, node-selection and review records;
  - the wire JSON of the API and of the tools is byte-for-byte what it was;
  - every tool keeps its name, description, argument schema and result schema;
  - configuration binds to the same values.
- **One native runtime target.** The native CLI reaches "Application started". The native API runs until it stops at
  a blocker 3.2 does not own: the MVC application parts (3.4) or EF Core (3.5). The run is recorded as in 3.1's smoke
  doc.
- **Warnings are the measure.** Every target's count moves through the ratchet, and each change is committed with its
  cause.

## Owner decisions (2026-10-21)

- **Tool registry: explicit registration plus a guard test, not a source generator.** Every tool class registers
  through Thalos 0.18.0's `AddLocalTools<TTools>(name, jsonOptions, t => t.Method, ...)` with its methods written
  out. A JIT test reflects over each tool class and fails when a public tool method is missing from the list, or
  when a tool's name, description or schemas differ from the old reflective path. Reflection is fine in tests.
- **Thalos ships once.** All Thalos fixes go in one Thalos PR and one release, **0.19.0**, which Daedalus then bumps
  to.
- **ZeroAlloc-Net:**
  - the two EF-bound items, `ValueObjects.EfCore`'s `AddTypedIdConventions` and `Outbox.EfCore`, leave 3.2, because
    3.5 removes EF Core and them with it;
  - `ZeroAlloc.Outbox`'s `WithSystemTextJsonSerializer` needs an overload that takes a JSON context. It goes to the
    owner's ZeroAlloc session as a handover, as with ZeroAlloc.Linq. Daedalus adopts it once released; if it has not
    landed by the end of 3.2, it is listed as a carried blocker.
- **`ZeroAlloc.Inject` and `ZeroAlloc.Resilience` leave 3.2** for a phase of their own after it. Neither is needed
  for AOT: Microsoft DI is AOT-safe once its generic parameters are annotated, and the resilience handler raised no
  warning in the survey. This keeps 3.2 to one finish line, and keeps DI-swap failures from mixing with
  reflection-removal failures.
- **AI.Sentinel gets a small PR in its own repo:** a `[DynamicallyAccessedMembers]` annotation on
  `DetectorRegistration` and a typed `DisableDetector<T>`. Daedalus drops its `GetExportedTypes` and
  `MakeGenericMethod` once that is released. If the release has not shipped by the end of 3.2, it is carried as a
  named blocker, like the Outbox overload **(my call)**.
- **Daedalus' second tool registry stays, without its scan.** `DaedalusLearningsTools` and
  `DaedalusFailurePatternsTools` are `[McpServerToolType]` classes that Daedalus' own `McpToolBuilder` builds for
  `BrainstormService` and PRD generation, outside Thalos. `McpToolBuilder` keeps serving them, with an explicit,
  delegate-based list and a JSON context in place of the assembly scan. Their names stay unprefixed, and the same
  equivalence guard test covers them.
- **Thalos turns `IsAotCompatible` on everywhere, and 0.19.0 waits for zero.** Thalos builds with
  `TreatWarningsAsErrors` (`Directory.Build.props:7`), so every analyzer warning in a packable project is a build
  error. When a cause outside Thalos blocks a project, such as an unsupported YamlDotNet construct or an annotated
  third-party API, the work stops and the owner gets the exact warning and a fix at its source: an upstream PR, a
  replacement, or a format change. No project ships with the analyzer off.
- **A native probe host proves 3.2's own paths.** The native API stops at MVC or EF Core before it reaches the
  workflow JSON, the tools or the YAML. So a small native test host in Thalos, like 3.1's sandbox smoke host, proves
  them natively:
  - it loads every process YAML;
  - it writes and reads workflow rows through the JSON contexts against Postgres;
  - it lists every tool with its schemas;
  - it binds the configuration;
  - it asserts the same results as JIT.

## Approach

**1. Remove the suppressions first, so the count tells the truth.** Phase 3.1's rule is no suppressions, but five
`UnconditionalSuppressMessage` attributes at three sites predate it. Such an attribute hides warnings from ILC as
well, so today's baselines undercount:
- the assembly-level `IL2026` suppression in `src/Daedalus.Api/Program.cs:29-31`, which hides every IL2026 in the
  Api assembly;
- `ApplicationServiceExtensions.RegisterHandlersAot`'s three suppressions, `src/Daedalus.Application/Extensions/
  ApplicationServiceExtensions.cs:68-76`, over an `Assembly.GetTypes()` handler scan;
- `ApplicationDbContext`'s, `src/Daedalus.Infrastructure/Persistence/ApplicationDbContext.cs:15-17`.

The `#pragma warning disable IL20xx` lines silence the Roslyn analyzer only, and go too. They are in
`McpToolBuilder.cs:180-182`, `DaedalusLearningsTools.cs:1`, `DaedalusFailurePatternsTools.cs:1`,
`BrainstormService.cs:1` and `InfrastructureServiceExtensions.cs:53`, `:85` and `:191`, the last three around
configuration binding. The
first commit removes them all and re-baselines upward with that cause; every later commit only lowers counts.
`ApplicationDbContext`'s suppression covers EF Core, so its warnings stay until 3.5 removes EF; the attribute still
goes, because a suppression is not allowed to stand in for the real fix.

**2. Thalos, in one PR released as 0.19.0.** The work branches from Thalos `main`, which is at v0.18.0 or later.
The survey measured an older commit, `2ca2396`, and listed 90 analyzer warnings in Thalos' own source. 0.18.0
already fixed some of them, such as the Sandbox.Host tool path, so the plan re-counts first. The two smoke-run
blockers come on top. Each fix:
- **JSON:** source-generated `JsonSerializerContext`s for `Workflow.Orm`'s `OrmWorkflowStore` (36 warnings, 18
  sites), `WorkflowVariableBlock`, `AnthropicCacheMarkers`, `McpConfigFile.Parse`, the smoke run's first blocker,
  `AuthorizingAIFunction` and `Testing`'s `ScriptedChatClient`. Every serialised shape keeps its property names,
  casing, null handling, enum format and number format, so stored and wire JSON stay identical.
- **DI generics:** `[DynamicallyAccessedMembers(PublicConstructors)]` on every builder generic: `AddPolicy`,
  `UseChatClientProvider`, `AddToolSource`, `UseSessionStore`, `UseConversationMap` (the smoke run's second blocker),
  the Skills, Memory and Channels builders, and the rest the analyzer names.
- **Configuration:** the binder source generator (`EnableConfigurationBindingGenerator`) for every `Bind` and `Get<T>`
  call, in Anthropic, Channels, Telegram and Skills.
- **YAML:** `ProcessLoader` moves to YamlDotNet's static generator, a `StaticDeserializerBuilder` with a
  `[YamlStaticContext]`. Process YAML files load into the same model.
- **Tool sources:** Thalos' remaining reflective tool discovery, the reflective `LocalToolSource` path and
  `AddRemoteRunTools`, moves to `AddLocalTools<TTools>`. The reflective `AddLocalTools(typeof ...)` overload stays
  for third-party JIT hosts.
- **Build:** `IsAotCompatible=true` on every packable Thalos project except `Testing`, so the analyzer guards Thalos
  from now on.

The Thalos PR goes to the owner to merge, then the release-please PR for 0.19.0.

**3. Daedalus, on Thalos 0.19.0.**
- **JSON:** contexts for the stores and records in `Daedalus.Agents`, `Daedalus.Infrastructure` and
  `Daedalus.Application` (`ReviewEvidence`, `NodeSelectionRecord`, `PostgresAgentSessionStore`, `FindingRecords`,
  `SandboxCallRecorder`, `BrainstormService` and the rest that `grep JsonSerializer` finds), plus the API's own JSON
  (`GlobalExceptionHandler`, `AgentSessionsController`) and `Daedalus.Web`'s `AgentApiClient`. Phase 3.7 needs that
  last one. Anonymous types that are serialised become records with the same property names.
- **Tools:**
  - the `[ThalosToolType]` classes registered at `DaedalusAgentsServiceCollectionExtensions.cs:424-437` move to
    `AddLocalTools<TTools>` with explicit method lists;
  - `McpToolBuilder.BuildLocalTools` stops scanning the assembly and builds its two `[McpServerToolType]` classes
    from an explicit delegate list.

  The guard test compares every tool on both paths with the old reflective output.
- **Mediator handlers:** `RegisterHandlersAot`'s `GetTypes()` scan is replaced by an explicit or generated
  registration. If ZeroAlloc.Mediator's generator can emit the handler registration, use it; if not, list the
  handlers and add a guard test like the tools'. The plan decides which, after reading the generator.
- **DI helpers:** `ForwardHostedServiceToConcreteSingleton<T>` and Daedalus' other generic helpers get DAM
  annotations.
- **Configuration:** the binder generator, on `Daedalus.Api`, `Daedalus.Agents`, `Daedalus.Cli` and
  `Daedalus.Infrastructure`.
- **ServiceDefaults:** the `Aspire.Hosting` and `Aspire.Hosting.PostgreSQL` references go, 128 Api warnings.
  `AspireExtensions.cs` uses more than constants: line 57 defines `AddServiceDefaults(this
  IDistributedApplicationBuilder)`, an AppHost-side extension. That and every other AppHost-side member move into
  the AppHost project, or a new AppHost-only library. The resource-name constants that the API needs stay in
  ServiceDefaults.
- **AI.Sentinel:** once the AI.Sentinel release ships, `DisableDetector` drops its `GetExportedTypes` and
  `MakeGenericMethod`.

**4. Prove it.** The native probe host passes in Thalos. A native CLI run against the measurement stack reaches
"Application started". A native API run goes
as far as it gets, recorded with the failure that stops it. Then the full suites, the browser suite and the live
manufacture run. Count changes go through the ratchet, target by target.

## Tests

- **JSON byte-identity, the check this phase lives or dies by.** For every serialised type, a test serialises a
  representative value with the new context and compares the bytes with a **golden string**. The golden string is
  captured from the reflection path **before** the swap and committed with the test, so a later change to the
  context's options turns it red. A round-trip test is not enough, because it passes even when both directions
  change. Stored-data reads get a golden-row test: an existing row's JSON deserialises to the same value. These go
  in Thalos for its stores, and in Daedalus for its own.
- **Tool equivalence:**
  - The guard test compares every tool's name, description, `JsonSchema` and `ReturnJsonSchema` with the reflective
    path, which stays in test code as the oracle.
  - A second test fails on any tool method left out of the explicit list.
- **Configuration:** for each options type the generator now binds, a test binds a representative configuration and
  compares the result with the reflective binder.
- **YAML:** every process file in `processes/`, plus the Thalos fixtures, loads to a model equal to the reflective
  loader's.
- **Mediator:** the handler set the new registration resolves equals the set the old scan found.
- **Regression:** all seven Daedalus suites, the browser suite through `btest.sh`, the full Thalos suite, and the live
  manufacture run.
- **Native:** the Thalos native probe host, as a test that publishes it with `PublishAot` and asserts zero
  warnings and JIT-equal results. Also the native CLI run and the native API run, recorded, and the ratchet's
  count per target, each change with its cause.
- Every new assertion carries a `Red:` line, applied once and seen failing (CLAUDE.md, "Tests that pass for the wrong
  reason").

## Open Questions

None blocking. Two are left to the plan:
- whether ZeroAlloc.Mediator's generator can emit handler registration, which decides generated versus explicit;
- the exact options of each JSON context, read off the current reflective `JsonSerializerOptions` at each site.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A JSON context differs subtly from the reflective options: camelCase, null handling, enum strings, number handling, or polymorphism without `[JsonDerivedType]` | Stored rows stop reading, or the wire format changes for clients and the model | Golden-byte tests captured before each swap; a golden-row read test for stored data; polymorphic types get their derived-type attributes and a test per derived type |
| Removing the suppressions raises the Api count sharply, the assembly-level IL2026 especially | Looks like a regression | It is the truth. Commit it alone, first, with its cause; every later commit lowers counts |
| The Thalos 0.19.0 release depends on two owner merges, the PR and the release PR | Daedalus work waits | The Daedalus items that need no new Thalos API go first: the ServiceDefaults split, Daedalus' JSON contexts, tool registration on 0.18.0's API, and the suppression removal. The bump comes last |
| Explicit tool lists drift from the tool classes | A tool silently goes missing for the model | The guard test fails on any public tool method that is not listed |
| The YamlDotNet static generator does not support a construct the process format uses | `ProcessLoader` cannot move | Find it with the static-context build first. If something is unsupported, report it before deciding; changing the format is out of scope |
| The live manufacture run fails for model reasons, not code reasons | Unclear proof | Compare with phase 2.15's runs; a failure is diagnosed to its cause before anyone calls it a model issue |
| The `ZeroAlloc.Outbox` serializer overload does not land in time | One reflection site remains | It is carried as a named blocker in the rulings and STATE |
