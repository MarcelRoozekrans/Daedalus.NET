## Goal

Every reflection site in Daedalus' and Thalos' own code is replaced by a compile-time path, with behaviour unchanged:
the suites and a live manufacture run stay green on JIT, the native CLI reaches "Application started", and the
native API gets past every blocker that 3.2 owns.

## Finish line (owner, 2026-10-21)

- **Behaviour is identical on JIT.** All seven suites pass, the browser e2e suite included, and one **live manufacture
  run** against Anthropic completes, with the owner topping up credits for it. "Identical" means:
  - the serializer writes byte-for-byte the JSON it wrote before, for workflow rows, agent sessions, node-selection
    and review records, and existing stored rows read back to the same values. The columns are `jsonb`, which
    Postgres normalises, so bytes are compared at the serializer, not in the row. The outbox payload is raw bytes and
    is compared byte for byte on both sides;
  - the wire JSON of the API and of the tools is byte-for-byte what it was;
  - every tool keeps its name, description, argument schema and result schema;
  - configuration binds to the same values.
- **One native runtime target.** The native CLI reaches "Application started". The native API runs until it stops at
  a blocker 3.2 does not own: the MVC application parts (3.4) or EF Core (3.5). The run is recorded as in 3.1's smoke
  doc.
  - **Amended, 2026-10-23 (owner): the CLI's "Application started" moves to 3.3.** The native CLI passes every
    blocker 3.2 owns, and its first stop is C3: Thalos' Anthropic provider builds the SDK's `CacheControlEphemeral`
    at boot, and Anthropic SDK 13's reflection JSON throws. Thalos 0.18.0 did the same; 3.1's run stopped earlier,
    at C2. 3.3 removes the SDK, so 3.2's CLI target is "no stop in code 3.2 owns", and "reaches Application started"
    becomes 3.3's. Record: `docs/plans/2026-10-21-phase-3.2-native-smoke.md`.
- **Warnings are the measure.** Every target's count moves through the ratchet, and each change is committed with its
  cause.

## Owner decisions (2026-10-21)

- **Tool registry: explicit registration plus a guard test, not a source generator.** Every tool class registers
  through Thalos 0.18.0's `AddLocalTools<TTools>(name, jsonOptions, t => t.Method, ...)` with its methods written
  out. A JIT test reflects over each tool class and fails when a public tool method is missing from the list, or
  when a tool's name, description, schemas or result bytes differ from the old reflective path. Reflection is fine
  in tests. The options passed are the ones that mirror the reflective path, which Thalos 0.19.0 makes public
  (controller's call), so Daedalus' Thalos tool registration lands on 0.19.0.
- **Thalos ships once.** All Thalos fixes go in one Thalos PR and one release, **0.19.0**, which Daedalus then bumps
  to.
- **ZeroAlloc-Net:**
  - the two EF-bound items, `ValueObjects.EfCore`'s `AddTypedIdConventions` and `Outbox.EfCore`, leave 3.2, because
    3.5 removes EF Core and them with it;
  - `ZeroAlloc.Outbox`'s `WithSystemTextJsonSerializer` needs an overload that takes a JSON context. It goes to the
    owner's ZeroAlloc session as a handover, as with ZeroAlloc.Linq. Daedalus adopts it once released; if it has not
    landed by the end of 3.2, it is listed as a carried blocker.
- **`ZeroAlloc.Inject` and `ZeroAlloc.Resilience` leave 3.2** for a phase of their own after it. Neither is needed
  for AOT: Microsoft DI is AOT-safe once its generic parameters are annotated, and the resilience handler raised no
  warning in the survey. This keeps 3.2 to one finish line, and keeps DI-swap failures from mixing with
  reflection-removal failures.
- **AI.Sentinel ships the fix on its 2.x line as 2.4.0** (owner, corrected after the impact analysis). It branches
  from v2.3.2 and adds:
  - a name- or id-based detector disable API, because Daedalus disables detectors by name from configuration and a
    typed `DisableDetector<T>` would not remove the reflection;
  - the IL2069 fix at the `DetectorRegistration` constructor parameter, since the property already carries the
    annotation.

  Thalos 0.19.0 takes 2.4.0, and Daedalus drops its `GetExportedTypes` and `MakeGenericMethod` on that. AI.Sentinel
  3.x (Renovate PR Thalos#364) stays a separate change. If the release has not shipped by the end of 3.2, it is
  carried as a named blocker, like the Outbox overload **(my call)**.
  - **Amended, 2026-10-21 (owner): AI.Sentinel ships on 3.x, not on a 2.x line.** A second release line costs a
    branch, a release workflow and pinned versions to maintain, and Thalos has to reach 3.x anyway. AI.Sentinel#426
    into `release/2.x` was closed unmerged and the branch deleted. The disable-by-name API and the IL2069 fix were
    ported to `main` and released as 3.1.0; Thalos 0.19.0 pins 3.2.1. Daedalus re-establishes its 2.x behaviour on
    3.x itself, as `RedactByDefault=false` among others, and the owner accepted 3.x's wider SEC-02 credential
    patterns on 2026-10-23. So 2.4.0 was never released, and the 2.x release mechanics in "Open Questions" and
    "Risks" are moot. Record: plan amendment `1a346699` and `docs/plans/2026-10-21-phase-3.2-rulings.md`, "Owner
    decisions" and rulings 31 and 32.
- **Thalos workflow variables accept JSON-shaped values only** (owner): string, number, bool, null,
  `JsonElement`/`JsonNode`, and lists or dictionaries of those. They are converted to `JsonElement` at the boundary.
  Any other type fails with a clear error that names the variable and its type. Thalos 0.19.0 documents it as a
  breaking change, and the bytes for the allowed types stay identical.
- **Daedalus' second tool registry stays, without its scan.** `DaedalusLearningsTools` and
  `DaedalusFailurePatternsTools` are `[McpServerToolType]` classes that Daedalus' own `McpToolBuilder` builds for
  `BrainstormService` and PRD generation, outside Thalos. `McpToolBuilder` keeps serving them, with an explicit,
  delegate-based list and a JSON context in place of the assembly scan. Their names stay unprefixed, and the same
  equivalence guard test covers them.
- **Thalos turns `IsAotCompatible` on everywhere, and 0.19.0 waits for zero.** Thalos builds with
  `TreatWarningsAsErrors` (`Directory.Build.props:7`), so every analyzer warning in a packable project is a build
  error. When a cause outside Thalos blocks a project, such as an unsupported YamlDotNet construct or an annotated
  third-party API, the work stops and the owner gets the exact warning and a fix at its source: an upstream PR, a
  replacement, or a format change. No packable project but Testing ships with the analyzer off.
- **A native probe host proves 3.2's own paths.** The native API stops at MVC or EF Core before it reaches the
  workflow JSON, the tools or the YAML. So a small native test host in Thalos, like 3.1's sandbox smoke host, proves
  them natively:
  - it loads every process YAML;
  - it writes and reads workflow rows through the JSON contexts against Postgres;
  - it lists every tool with its schemas;
  - it binds the configuration of the packages it references;
  - it asserts the same results as JIT.

  It leaves out Thalos.NET.Anthropic, which belongs to 3.3, and Thalos.NET.Testing, which pulls in assertion
  libraries, and it asserts zero warnings from the assemblies it roots (controller's call). Anthropic's configuration
  binding is tested on JIT.

## Approach

**1. Remove the suppressions, so the count tells the truth.** Phase 3.1's rule is no suppressions, but five
`UnconditionalSuppressMessage` attributes at three sites predate it. Such an attribute hides warnings from ILC as
well, so today's baselines undercount:
- the assembly-level `IL2026` suppression in `src/Daedalus.Api/Program.cs:29-31`, which hides every IL2026 in the
  Api assembly;
- `ApplicationServiceExtensions.RegisterHandlersAot`'s three suppressions, `src/Daedalus.Application/Extensions/
  ApplicationServiceExtensions.cs:68-76`, over an `Assembly.GetTypes()` handler scan;
- `ApplicationDbContext`'s, `src/Daedalus.Infrastructure/Persistence/ApplicationDbContext.cs:15-17`.

The `#pragma warning disable IL20xx` lines silence the Roslyn analyzer only, and go too. They are in
`McpToolBuilder.cs:180-182`, `DaedalusLearningsTools.cs:1`, `DaedalusFailurePatternsTools.cs:1`,
`BrainstormService.cs:1` and `InfrastructureServiceExtensions.cs:53`, `:85` and `:191`, the last three around
configuration binding. `IL2026` also sits inside multi-code `#pragma` lists in `RepositoryPlatformDetector.cs:8,177`
and `GitRepositoryManager.cs:11,549`; neither file calls an annotated member, so both look stale.

Each suppression comes out in the same commit as its fix (controller's call). Daedalus builds with
`TreatWarningsAsErrors` and the trim analyzer on, except in Api, Agents, Cli, Migrations and Web, so removing a real
suppression alone fails the build. Of those five, only Api holds one: its assembly-level IL2026 comes out on its own,
re-baselined upward with that cause. `ApplicationDbContext`'s attribute is removed and the build decides: if IL2026
does fire there, the honest form until 3.5 removes EF Core is `[RequiresUnreferencedCode]` on the constructor, because
a suppression is not allowed to stand in for the real fix.

  **Amended, 2026-10-21 (owner):** the pin moves to 3.x, 3.2.1; see the AI.Sentinel entry under "Owner decisions".

## Tests

- **JSON byte-identity, the check this phase lives or dies by.** For every serialised type, a test serialises a
  representative value with the new context and compares the bytes with a **golden string**. The golden string is
  captured from the reflection path **before** the swap and committed with the test, so a later change to the
  context's options turns it red. A round-trip test is not enough, because it passes even when both directions
  change. Bytes are compared at the serializer output, not on stored rows, because the columns are `jsonb`
  (controller's call). Stored-data reads get a golden-row test: an existing row's JSON deserialises to the same
  value. The outbox payload that Thalos writes and Daedalus reads is tested byte for byte on both sides. Lenient
  readers get golden tests over their lenient inputs. These go in Thalos for its stores, and in Daedalus for its own.
- **Workflow variables:** prompt-block bytes per allowed type, before and after; a test that run variables keep
  today's CLR types after start, node result and resume; and a refusal test per disallowed type.
- **Tool equivalence:**
  - The guard test compares every tool's name, description, `JsonSchema`, `ReturnJsonSchema` and invocation result
    bytes with the reflective path, which stays in test code as the oracle.
  - A second test fails on any tool method left out of the explicit list.
- **Configuration:** for each options type the generator now binds, a test binds a representative configuration and
  compares the result with the reflective binder.
- **YAML:** every process file in `processes/`, plus the Thalos fixtures, loads to a model equal to the reflective
  loader's.
- **Mediator:** the handler set the new registration resolves equals the set the old scan found.
- **Regression:** all seven Daedalus suites, the browser suite through `btest.sh`, the full Thalos suite, and the live
  manufacture run.
- **Native:** the Thalos native probe host, as a test that publishes it with `PublishAot` and asserts zero
  warnings from the assemblies it roots, and JIT-equal results. Also the native CLI run and the native API run,
  recorded, and the ratchet's count per target, each change with its cause.
