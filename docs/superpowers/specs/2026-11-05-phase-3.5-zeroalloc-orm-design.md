# Phase 3.5 Design — EF Core to ZeroAlloc.ORM

**Date:** 2026-11-05
**Phase:** 3.5
**Surface:** Data
**Stage:** phase (one phase, implementation-ready)

> Brainstormed with the owner on 2026-11-05. Milestone design: `docs/superpowers/specs/2026-10-17-milestone-3-design.md`,
> phase 3.5. The file-level record of every EF Core use is the phase 3.1 gap audit,
> `docs/plans/2026-10-17-zeroalloc-orm-gap-audit.md`; this design does not repeat it and the plan cites it by section.
> Outbox handover to the ZeroAlloc session: `docs/plans/2026-11-05-zeroalloc-outbox-orm-handover.md`.

## Goal

Daedalus' data layer runs on ZeroAlloc.ORM, with its queries written as LINQ through `ZeroAlloc.ORM.Linq`, over the
existing schema and data. EF Core leaves the dependency tree, and the native CLI reaches "Application started" and
tries one native turn.

## Why

EF Core builds and compiles expression trees at run time and has no Native AOT roadmap. Every phase before this one
removed a blocker that 3.6, the native publish, needs; this one removes the last and largest. The 3.1 native runs
stop at EF Core model building in both the CLI and Migrations.

## Where the ZeroAlloc side stands (checked 2026-11-05)

The milestone said 3.5 waits on ZeroAlloc.Linq and the six audit gaps being released. As of today:

| Audit gap | State | What 3.5 does |
|---|---|---|
| 4.1 adopt an EF database | released, ORM 2.4.0: a `MigrationRunner` baseline plus an EF history check | use it (below) |
| 4.2 arrays | released, ORM 2.4.0, float/double arrays 2.7.0 | use it |
| 4.3 jsonb parameters | released, ORM 2.4.0 (`[Json]`), LINQ jsonb binding 2.11.0 | use it |
| 4.4 `uint` / `xid` | closed for LINQ in 2.9.0: `Sql.Xmin(row)`, a `uint` column mapped to `xmin`, `Xid` binding, `[LinqCommand(ThrowOnNoRows = true)]`. Raw `[Query]` still has no unsigned types | every `xmin` read and guard goes through LINQ; no raw `[Query]` reads a `uint` |
| 4.5 `Outbox.Orm` dashboard store and fixed table | **not released**; `ZeroAlloc.Outbox.Orm` 4.4.6 still lacks both | **owner, 2026-11-05: fixed upstream.** Handover written; the outbox move waits on that release |
| 4.6 14-digit migration version skipped | not released: versions still parse as `int` | not hit: Daedalus' own migrations are numbered `1`, `2`, … (below). Recorded, not waited on |

`ZeroAlloc.Linq` shipped as **`ZeroAlloc.ORM.Linq`** in the ORM release train (2.5.0 onwards; 2.13.0 current), with
`[LinqQuery]`/`[LinqCommand]` partial methods over never-executed companion methods, map classes, GroupBy and
aggregates, joins, tuple companions for parent-and-children loads, `ForUpdate`/`SkipLocked`, `ExecuteUpdate` and
`ExecuteDelete`, and `xmin` guards. Daedalus pins ZeroAlloc.ORM 2.10.0 today.

## Owner decisions (2026-11-05)

1. **Start now, settle the open gaps in the design.** Design and plan proceed; only the outbox move waits on a
   release.
2. **Gap 4.5 is fixed upstream.** `ZeroAlloc.Outbox.Orm` gains a configurable table name per named pipeline and
   `RequeueAsync` (at least) on its store. The channel/RepoDigest pipeline keeps its own table, `"OutboxMessages"`, so
   its pending rows and leases stay where they are, and the workflow engine keeps `outboxmessages`.
3. **#290 is fixed, not ported.** The five live aggregates with a dead `bytea` `RowVersion` (`AgentSession`,
   `BrainstormSession`, `RepositoryConfiguration`, `Project`, `CodeAnalysisRequest`) get a real `xmin` guard, as
   `Task` has. A migration after the baseline drops the six dead `bytea` columns (those five plus
   `ExecutionSession`). They are always `NULL`, so no data is lost.
4. **Domain entities are rebuilt through explicit `Rehydrate` factories in `Daedalus.Domain`.** Infrastructure row
   records call them. Domain gains no ORM reference.
5. **The guard protects against lost updates only, not against all concurrency.** A save is `xmin`-guarded when it
   writes values computed from the row it loaded. A save that writes independent columns updates only those columns,
   with no `xmin` check. Atomic in-database updates (counter increments, compare-and-swap transitions) stay as they
   are. Adding children inserts the child rows without touching the parent. So benign concurrency keeps today's
   results, and the parity bar holds.
6. **Rolling back to an EF build is not supported.** Rollback means restoring a database backup taken before the
   upgrade. Migration 2 ships with the baseline in this phase. `__EFMigrationsHistory` is kept only for the adoption
   check. The dev-database proof shows the upgrade, not a downgrade.

Carried from the milestone design, unchanged: schema and data kept; no dual-ORM end state on `main` (both ORMs may
coexist only on this phase's branch); the integration suite is the parity bar, fixtures may change, assertions may
not, and each changed test is listed in the rulings; an existing database upgrades in place, proven on a copy of the
dev database.

## Approaches considered

**Rehydration** (owner picked A):
- **A. `Rehydrate` factories in Domain.** Explicit, compiler-checked, Domain stays persistence-free; the EF-only
  private constructors and their `S1144`/`CA1819` suppressions go. Costs about 20 factory methods.
- B. `[UnsafeAccessor]` in Infrastructure. Domain untouched and AOT-safe, but member names are strings, so a Domain
  rename breaks at run time.
- C. Row records only on read paths. Least mapping, but two shapes per aggregate drift and repository contracts
  change.

**Outbox move** (owner picked A):
- **A. Upstream: table name per pipeline plus `RequeueAsync`.** Pipelines stay separate, in-flight rows stay put.
  Waits on an Outbox release.
- B. One shared `outboxmessages` table, rows copied in a migration, one dispatcher for both pipelines, Daedalus-side
  requeue. No wait, but couples the pipelines.
- C. A Daedalus-local outbox store over `"OutboxMessages"` on raw ORM. No wait, but Daedalus owns an outbox.

**#290** (owner picked A): real `xmin` guard and drop the columns; B, guard and keep the dead columns; C, a
straight port that keeps the inert guard, leaving #290 open.

## Approach

### 1. Packages and the connection

- ZeroAlloc.ORM 2.10.0 → 2.13.0 and `ZeroAlloc.ORM.Linq` 2.13.0 added. `ZeroAlloc.Outbox.Orm` moves to the release
  that closes gap 4.5 when it ships.
- `AspireExtensions.AddApplicationDatabase` (`src/Daedalus.ServiceDefaults/AspireExtensions.cs:131-147`) registers an
  `NpgsqlDataSource` and the ORM's async connection in place of `AddDbContextPool`. During the phase both are
  registered; at the end only the data source remains.
- Units of work: where EF shared one `DbContext` (and its connection and transaction) across stores in a scope, the
  ORM path shares one scoped connection and an explicit transaction. Today's sites that rely on that sharing —
  `ScheduledRunStore` and `ScheduledRunExecutionStore` enqueueing into the outbox in the same transaction as their own
  writes — keep that atomicity; the plan names each.

### 2. Schema: baseline migration plus the #290 migration

- **Migration 1, the baseline**, is the schema as of EF's head, `20261014090300_AddNodeSelectionUniqueIndex`,
  generated once from EF (`migrations script` of the full chain, idempotent parts removed) and committed as a
  ZeroAlloc embedded SQL migration in a new Daedalus migration source. It keeps
  `CREATE EXTENSION IF NOT EXISTS vector` (audit 3.4) and creates the channel pipeline's `"OutboxMessages"` table
  exactly as EF did.
- **Adoption:** the runner's baseline option with the EF history check (ORM 2.4.0). On a database whose
  `__EFMigrationsHistory` head is exactly that id, version 1 is recorded without running. On a fresh database the
  table does not exist and version 1 runs. Any other EF head fails loudly.
- **Migration 2** drops the six dead `bytea` `RowVersion` columns (decision 3).
- **Version numbers** are small integers in the Daedalus source, so gap 4.6 does not apply. The source is scoped, as
  the outbox and workflow sources already are in `__zaorm_migrations`.
- **`Daedalus.Migrations/Program.cs`** replaces `dbContext.Database.MigrateAsync()` with the Daedalus source run
  through `MigrationRunner`, ahead of `WorkflowEngineMigrator`, in one process as today. `__EFMigrationsHistory` is
  left in place and never written again.
- `ExecutionSession` loses its mapping and its `DbSet`; nothing reads or writes it (audit 3.4). Its table stays.

### 3. Domain: `Rehydrate` factories

- Each of the 20 entity types gets `Rehydrate(...)`, which takes the stored state and does not re-run `Create`'s
  validation (stored rows are trusted; a row that `Create` would now reject must still load). Child collections are
  passed in, so aggregates with children (`BrainstormSession` and its messages, `Project` and its tasks, and the
  others the audit lists) are rebuilt whole.
- Value objects with private constructors are rebuilt through their existing `Create` factories in the row record,
  as audit 5.1 describes for `CodeAnalysisRequest`'s owned types.
- Enums stored as strings (`ScheduleOrigin`, `RunStep`) are parsed in the row record, so Domain does not reference
  `[StoreAsString]` (audit 5.1).
- `Rehydrate` is either `public` or `internal` with `InternalsVisibleTo` for Infrastructure and Agents. The plan picks
  one and applies it everywhere **(builder's call)**.
- `RowVersion` properties: `Task.RowVersion` stays a `uint` mapped to `xmin`. The five #290 aggregates replace their
  `byte[]? RowVersion` with a `uint` read from `xmin`, so the guard has a value to compare. `ExecutionSession`'s goes.

### 4. Infrastructure: maps, row records, stores

- One map class per table in Infrastructure (table, column overrides, jsonb and array columns, `xmin`), per the
  ORM.Linq design. Row records per table; each store reads rows and calls `Rehydrate`.
- **Store by store**, in the audit's section 2 order, adjusted so a store moves together with the stores it shares a
  transaction with. `ScheduledRunStore`, `ScheduledRunExecutionStore` and `ScheduleReconciler` share the `DbContext`
  transaction with `EfCoreOutboxStore`, so they move with the outbox, at the end (section 5). Each store's port is one plan task with its tests green before the next, while EF still serves
  the stores not yet moved.
- Queries stay LINQ through `[LinqQuery]`. The roughly five statements the audit marks as raw SQL (`FOR UPDATE` paths
  LINQ cannot express, the upserts) become `[Query]`/`[Command]`; anything LINQ now covers (`ForUpdate`,
  `ExecuteUpdate`) uses LINQ instead.
- **Explicit writes** replace the about 30 change-tracked saves: an `INSERT` or a targeted `UPDATE` per changed
  aggregate, child rows written explicitly. Where EF diffed a child collection, the plan states the write rule per
  aggregate (insert new children only, or replace).
- **Concurrency:** following decision 5, each load-mutate-save of `Task`, `ScheduledRun`, `ScheduledRunExecution` and
  the five #290 aggregates that writes values derived from the loaded row updates with `WHERE xmin = @expected`
  through `[LinqCommand(ThrowOnNoRows = true)]`. The plan classifies every save site as guarded or independent, and
  records each classification in the rulings. `Task`, `ScheduledRun` and `ScheduledRunExecution` keep the guard EF
  gives them today. Each caller maps
  `ZeroAllocOrmConcurrencyException` to the result it returns today for `DbUpdateConcurrencyException`. For the five
  #290 aggregates that result now also fires on a genuine lost race, not only on a deleted row; the callers'
  documented results do not change. `CodeAnalysisRepository` and `RepositoryConfigurationRepository`, which today let
  a concurrency exception fall into a generic `catch (Exception)` (audit 3.4), get an explicit conflict result; the
  plan names the result per method from what each caller already handles.
- `AgentSession`'s deleted-row-reported-as-busy defect (audit 3.4) is fixed where the guard lands: zero rows on a
  missing row is not-found, zero rows on a changed row is busy.

### 5. The outbox move (waits on the Outbox release)

- The channel/RepoDigest pipeline moves from `ZeroAlloc.Outbox.EfCore` to `ZeroAlloc.Outbox.Orm` as a named pipeline
  on the existing `"OutboxMessages"` table, with its own worker, alongside the workflow engine's `outboxmessages`.
  Whether `WorkflowOutboxDispatchService` can then become the stock worker is the upstream design's answer; 3.5 does
  not change it unless the release makes that free.
- `ScheduleDeliveryActions` requeues through the ORM store's `RequeueAsync`; `ScheduleDiagnostics` reads through it.
- Pending rows and leases are not migrated: the table is the same table. The plan pins that with a test that leaves a
  pending and a leased row in place across the switch and sees both delivered.
- If the release is late, every other task proceeds; the outbox tasks and EF's removal come last in the plan.

### 6. Tests

- **Integration fixtures** move off `EnsureCreatedAsync` to running the Daedalus migration source (baseline and
  migration 2), the outbox source and the workflow source, so tests run against the schema production has.
- The EF migration tests under `tests/Daedalus.Tests.Integration/Migrations/` that test individual EF migrations are
  retired with those migrations; `WorkflowOrmMigrationTests` keeps its point (both outbox tables coexist) on the new
  runner. Each retired or changed test is listed in the rulings.
- `Daedalus.Tests.Unit.Infrastructure`'s EF InMemory tests move to the integration project or to tests of the row
  mapping; InMemory leaves.
- **New tests:** a `Rehydrate` round trip per aggregate (store, load, compare); a lost-race test per guarded save site,
  and a test that a benign concurrent write (such as a turn's counter increment) does not fail an independent save;
  the baseline adoption on a database built by EF's 26 migrations (version 1 recorded, not run; migration 2 runs;
  data intact); the outbox carry-over above.
- **EF's chain as a frozen fixture (my call):** before EF is deleted, the full EF migration chain is scripted once to
  a committed SQL file, including its `__EFMigrationsHistory` inserts. The adoption test and the schema-equality test
  (Risks) build their "EF database" from that file. They stay as regression tests after EF is gone, and no test
  project keeps an EF reference.
- **Dev database proof:** a copy of the AppHost's dev Postgres volume (on the agents VM) restored into a throwaway
  container, upgraded by the new `Daedalus.Migrations`, then row counts per table compared before and after, and the
  API suite smoke-run against it. The plan picks which of the two `postgres-data` volumes is current.

### 7. EF Core removed, and the native CLI

- At the end: `ApplicationDbContext`, its factory, the 20 configurations, the 26 migrations, designers and snapshot
  deleted; `Microsoft.EntityFrameworkCore*`, `Npgsql.EntityFrameworkCore.PostgreSQL` and `ZeroAlloc.Outbox.EfCore`
  out of `Directory.Packages.props` and every project; `ZeroAlloc.ValueObjects.EfCore` leaves with them (audit 1). A
  guard test or CI check asserts none of them is in any dependency graph, test projects included.
- The native CLI is checked through the `native-publish` workflow on a labelled PR, never a local AOT publish: it
  reaches "Application started" and tries one native turn. A turn that fails for a reason 3.6 owns is recorded, not
  fixed here.
- `eng/aot/baseline.json` is set by hand to the counts CI's `aot-analysis` reports on a head that sat still. The EF
  warning family should leave Api, Cli and Migrations.

## Goals, non-goals, anti-goals

**Goals:** the above; every integration assertion unchanged; EF gone; #290 fixed; an existing database upgrades with
its data.

**Non-goals:** contract changes; query rewrites for performance beyond what the translation gives; dropping the
`ExecutionSession` table; moving the workflow engine's dispatcher; `ZeroAlloc.Inject` (3.8); the native API publish
(3.6).

**Anti-goals** (a failure even if the suite is green):
- a database that loses or rewrites rows on upgrade;
- a port that keeps an inert concurrency guard;
- EF Core and ZeroAlloc.ORM both serving `main`;
- a store's transactional outbox write losing its atomicity;
- a Domain reference to any ORM package.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The Outbox release is late | the outbox move and EF removal stall | everything else first; outbox tasks last; the handover is specific |
| The baseline drifts from EF's real schema | fresh and adopted databases differ | a test that builds one database with EF's 26 migrations and one with the baseline, and compares `information_schema` and `pg_indexes` |
| An ORM.Linq translation gap on a real query | a store cannot port as LINQ | raw `[Query]` for that statement, recorded in the rulings, and an ORM issue filed |
| Explicit writes miss a field EF tracked | silent data loss on update | round-trip tests per aggregate, plus the unchanged integration assertions |
| Lost-race results change behaviour for callers | API answers differ | each guarded method keeps its existing result type; contract tests stay green |
| A shared EF transaction is split | outbox writes no longer atomic | the plan lists each transaction-sharing site; a test per site rolls back and sees no outbox row |
| Phase size | long branch, review fatigue | subagent-driven tasks of one store each, a task review per task, a whole-branch review at the end, as in 3.4 |
