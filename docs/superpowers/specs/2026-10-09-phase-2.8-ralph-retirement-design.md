# Phase 2.8 Design — Ralph retirement

**Date:** 2026-10-09
**Phase:** `2.8`
**Surface:** Refactor
**Stage:** phase (one phase, implementation-ready)

Brainstormed with the owner on 2026-10-09. The owner made the decisions D1–D6 below. `refactor-analysis` produces the
authoritative impact list before the plan is written. The file list here is a starting hint only.

## Goal

The Ralph loop is gone. A task on the board becomes work only when a person starts a manufacture run for it, and the
task's status is that run's status. Cost analytics covers manufacture runs and chat turns as well as Ralph's history,
so no page or tool silently goes stale.

## Decisions

| # | Decision |
|---|---|
| D1 | **Bridge the board to manufacture.** Delete Ralph, its pipeline and its host. Keep the task board: a task starts a manufacture run, and its status follows that run. |
| D2 | **A human starts each run.** There is no automatic pickup, so no tokens are spent without a person choosing to. If automatic dispatch is ever wanted, it is a later issue. |
| D3 | **Costs from runs, patterns frozen.** Cost analytics adds manufacture-run usage and chat-turn usage, closing #281. Failure patterns keep reading historical `TaskExecutions` and say so. Rebuilding them from review rejections is filed as an issue. |
| D4 | **Task status is derived on read.** A task stores only its `WorkflowRunId`. Its status is computed from the run when read, so it can never drift. |
| D5 | **No table is dropped.** `TaskExecutions` and `ExecutionSessions` become read-only history. The migration only adds a column and backfills usage records. |
| D6 | **No live code says "Ralph".** `IRalphAgentFactory` is renamed to `IAgentFactory`. The unrelated `RalphLoopOrchestrator` in CodeAnalysis (#279) is out of scope; its naming confusion is noted on #279. |

## Approach

### 1. What is deleted

- **The host.** `src/Daedalus.Console` is removed from `Daedalus.sln`, together with its appsettings. Also removed:
  the AppHost `console` resource, the `docker-compose.full.yml` service, the `daedalus-console` image in both CI docker
  matrices and in `publish-release`, and the "Console Worker" option in both issue templates.
- **Ralph's pipeline.** Everything only the Console used:
  - `RalphLoopWorker`, `IRalphLoopService` and `RalphLoopPipelineService`, `AddRalphLoopMiddleware` and its 8
    middlewares;
  - `ITaskAssignmentService`, `IPhaseOrchestrator`, `IWorkspaceOrchestrator`, `IGitWorkflowService`,
    `ILoopbackEvaluator`, `IPromptBuilder` and `DefaultPromptBuilder`;
  - `IRalphPromptTemplateBuilder`, including its duplicate AGENT.md loop, which phase 2.4's `retrospect` replaced;
  - `IPromptContextStore` and `DatabasePromptContextStore`, `IWorkspaceContextProvider` and
    `FileSystemWorkspaceContextProvider`;
  - `TaskRepository.ClaimNextAsync` and `RecordExecutionAsync`;
  - `RalphLoopConfiguration` and the `RalphLoop` configuration section;
  - the never-dispatched `ExecuteTaskCommand` and its handler;
  - `LearningsService`, if `refactor-analysis` confirms Ralph is its only user.

  Each one's tests go with it.
- **Ralph-only UI and API.** `RalphConfigController` and `RalphConfig.razor`, which edited only the API process's
  copy and never affected the Console. `ExecutionSessionsController` and `Sessions.razor`, which showed worker
  heartbeats. The tasks `abandon` and `resume` endpoints, which manipulated worker claims. Their Playwright tests and
  page objects go too.
- **Closed by the deletion:** #283 (the Console never called `AddDaedalusAgents`) and #294 (the Ralph-side provider
  never probed `AGENTS.md`).

### 2. The bridge from the board to manufacture

- **Domain.** `Task` gains a nullable `WorkflowRunId` and `AttachRun(Guid runId)`. Starting again replaces the id.
  Earlier runs stay in the workflow run history.
- **Starting.** `POST /api/tasks/{id}/manufacture` uses the same authorization as `POST /api/workflow-runs`. It
  refuses before anything is spent:
  - **404** when the task does not exist.
  - **422** when the project's `RepositoryUrl` matches no allow-listed `Thalos:Workflow:Repositories` entry. The match
    is on owner and name, through `RepoRef.FromGitHubUrl` on both sides, and the message names the URL.
  - **422** when a dependency's derived status is not `Completed`, naming it.
  - **409** when the task's current run is not terminal.

  Otherwise it calls `IManufactureRunStarter.StartAsync`. The work intent is the task's title, a blank line, then its
  description. The repository is the matched allow-listed name, and the starter is the caller. It then attaches the run
  id and answers 201 with the run id. A starter failure maps as `WorkflowRunsController.Start` maps it.
- **Derived status.** Task responses carry `workflowRunId` and a derived `status`:

  | Run status | Task status |
  |---|---|
  | Running | `InProgress` |
  | Awaiting | `AwaitingApproval` |
  | Succeeded | `Completed` |
  | Failed | `Failed` |
  | Cancelled | `Cancelled` |

  A task without a run keeps its stored value: an old Ralph task keeps `Completed`, `Failed` or `Abandoned`, and a new
  task is `Pending`. `TaskStatus` gains `AwaitingApproval` and `Cancelled`, which are computed and never stored; the
  enum's documentation says so. Listing does one run lookup per task with a run.
- **Ralph-only fields.** `MaxIterations`, `CompletionPromise`, `IterationCount` and `CurrentSessionId` stay as
  columns. They leave the create and edit paths, and are shown read-only for old tasks only.
- **Web.** The Tasks page shows a "Manufacture" button on startable tasks, the derived status, and a link to the run
  view. The Brainstorm and PRD "generate tasks" flows are unchanged; their tasks are now startable.

### 3. Costs, failure patterns, history

- **Node-usage records.** When a node completes with usage, the host appends a `node-usage` `WorkflowRunRecord` with
  the node, the model and the input, output, cache-read and cache-write tokens. The append happens in the
  `CompleteNodeAsync` interception `ReviewHandoffWorkflowStore` already performs for every node. The migration
  backfills `node-usage` records once, from the usage on existing Thalos completion events. It is idempotent, skipping
  any (run, seq) already recorded.
- **Cost analytics (#281).** `CostAnalyticsService` reads three sources: `TaskExecutions` (Ralph history), `node-usage`
  records (manufacture) and `AgentMessages` token columns (chat). The Costs page and API show one total, split by
  source, model and day. Pricing is computed as today.
- **Failure patterns.** `FailurePatternDatabase` keeps reading historical `TaskExecutions`. The
  `daedalus__search_failure_patterns` description states that its data predates Ralph's retirement on its date, so an
  empty answer is not read as "no known pattern". An issue is filed to rebuild patterns from review rejections, using a
  rejection's findings and the next implement round's fix.
- **History.** The Executions page and `TaskExecutionsController` stay as read-only Ralph history, labelled as such.

## Tests

Each assertion names the code change that turns it red, and that change is made once to see it fail.

- **Unit, the start endpoint.** The 404, both 422s and the 409 send no run and attach nothing. The 201 path calls the
  starter with the composed intent and the matched repository, and attaches the run.
- **Unit, the derived-status mapping.** All five run statuses, a task without a run (stored value), and an old Ralph
  task.
- **Unit, `node-usage`.** One record per completed agent node with usage. None for a gate or a host action without
  usage.
- **Unit, cost analytics.** Totals split by source, model and day across the three sources. An empty source
  contributes zero and is not an error.
- **Integration.**
  - The migration: adds the column, backfills `node-usage` from run events, and backfills nothing twice.
  - Task to `POST /api/tasks/{id}/manufacture` to a run, whose status appears on `GET /api/tasks/{id}`.
  - The rewritten architecture and configuration tests stay green.
- **Playwright.** The Tasks page's Manufacture button and status. Deleted pages are removed from the navigation and
  screenshot tests.
- **Live proof, owner-approved.** Create a task on the board for `daedalus-sandbox` and press Manufacture. Watch the
  task go `InProgress`, then `AwaitingApproval`. Approve at the gate, and confirm the task shows `Completed` with a
  sandbox PR, and that Costs shows the run's usage under the manufacture source.

## Open Questions

None for the design. `refactor-analysis` settles the deletion order and confirms which shared pieces are Ralph-only,

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| A piece believed Ralph-only is used elsewhere | Deleting it breaks the API, Web or Cli | `refactor-analysis` maps transitive users before the plan, and the full suite plus Playwright run per task |
| One run lookup per task makes listing slow | The board renders slowly with many tasks | Acceptable at today's size. A batch lookup is the fix if it ever matters |
| The backfill misreads Thalos event usage | Costs are missing or doubled for older runs | The backfill is idempotent on (run, seq) and has its own integration test against real events |
| An old task still shows Ralph-only fields | It confuses a reader | Those fields are shown read-only for old tasks only and are absent from create and edit |
| Docs keep a sentence about the Console or Ralph | It misleads a reader | Grep for `Ralph`, `Console` and `RalphLoop` across `docs/`, `README.md`, `CLAUDE.md` and the templates as a plan step, with the final review's Mechanism pass |
