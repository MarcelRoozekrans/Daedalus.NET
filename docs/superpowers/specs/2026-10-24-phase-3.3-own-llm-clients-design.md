# Phase 3.3 Design — Own Anthropic and Ollama clients

**Date:** 2026-10-24
**Phase:** `3.3`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

Milestone design: `docs/superpowers/specs/2026-10-17-milestone-3-design.md`, "Phase 3.3", including its owner notes
of 2026-10-17 (where the clients live) and 2026-10-23 (the native CLI's "Application started"). Input from phase 3.2:
the native smoke run, `docs/plans/2026-10-21-phase-3.2-native-smoke.md`, stop C3. Brainstormed with the owner on
2026-10-24.

## Goal

The Anthropic SDK and OllamaSharp leave the dependency tree. Our own AOT-clean clients replace them:
`ZeroAlloc.Rest.Anthropic` and `ZeroAlloc.Rest.Ollama`, in ZeroAlloc-Net. Thalos.NET keeps only the
Microsoft.Extensions.AI adapters and the prompt-cache translator. The native CLI then reaches "Application started".

**Why:** the Anthropic SDK accounts for most of the AOT warnings: Api 20244 and Cli 4357 in `eng/aot/baseline.json`,
of which the SDK's reflection JSON is the bulk. It also stops the native CLI at boot. Its `CacheControlEphemeral`
constructor calls `JsonSerializer.SerializeToElement` with reflection options when Thalos' provider is built. It is
not part of Microsoft.Extensions.AI, which is warning-free.

## Finish line

- **Gone from the tree.** `Anthropic` and `OllamaSharp` appear in no `Directory.Packages.props` of Thalos or Daedalus,
  and in no resolved dependency graph: `dotnet list package --include-transitive` is clean on every Daedalus project,
  the AppHost included (owner, 2026-10-24).
- **Behaviour is unchanged on JIT.**
  - All seven Daedalus suites pass, and so does Thalos' suite.
  - One **live manufacture run** against Anthropic completes through review and the gate. The token usage it
    records, with the cache-read and cache-write split, reaches `/costs` as before.
- **The native CLI reaches "Application started"** (owner, 2026-10-23). Then it tries one native turn through the new
  client (owner, 2026-10-24).
  - If the turn answers, that is the native proof of the client.
  - If something later stops it, the stop is recorded with its owning phase and not fixed in 3.3. Examples: the
    ZeroAlloc.Outbox serializer, or C2, `PostgresConversationMap`.
  - The run is recorded in a native smoke doc as in 3.1 and 3.2. The binary comes from the `native-publish` workflow
    on a labelled PR, never from a local publish (owner, 2026-10-22).
- **Warnings are the measure.** The Api and Cli counts drop through the ratchet when the SDK leaves. Each baseline
  move is committed with its cause, from CI's `aot-analysis` counts.
- **Upstream issue.** The C3 failure is checked against the latest Anthropic SDK, 13.3.0 on 2026-10-24, at the time
  of filing. If it still reproduces, an issue is filed with Anthropic, linking the 3.2 smoke doc (milestone owner
  note, 2026-10-17). A fix there does not change this phase: the owner chose our own client.

## Owner decisions (2026-10-24)

- **Streaming lives in ZeroAlloc.Rest.** The generator learns `IAsyncEnumerable<T>` over `text/event-stream`, so a
  client method can return a stream of typed server-sent events. It ships in a ZeroAlloc.Rest release.
  ZeroAlloc.Rest.Anthropic is its first consumer.
- **This phase builds the ZeroAlloc packages.** It opens PRs in `ZeroAlloc-Net/ZeroAlloc.Rest`; the owner merges
  and releases them. Thalos and Daedalus then consume the release, as 3.2 did with Thalos and AI.Sentinel.
- **Both clients live inside the ZeroAlloc.Rest repo** as `src/ZeroAlloc.Rest.Anthropic` and
  `src/ZeroAlloc.Rest.Ollama`, released at the repo's one version.
- **API scope is what Thalos and Daedalus use**, nothing more:
  - messages create and stream;
  - text content;
  - tool definitions, tool use and tool results;
  - `cache_control` on system, messages and tools, with a TTL;
  - usage, including `cache_read_input_tokens` and `cache_creation_input_tokens`;
  - stop reasons;
  - error mapping and retries.

  Extended thinking, `tool_choice`, images and documents, token counting, the model list and batches wait until
  something needs them.
- **Recorded transcripts.** A few real Anthropic calls are recorded once and checked in. They are then replayed in CI.
  The recordings cover plain text, streaming, a tool call and a cache write followed by a read, on the cheapest model.
  API keys and other secrets never land in the files.
- **AgentFactory goes through Thalos.** Daedalus' `AgentFactory`, which serves PRD generation and the brainstorm,
  asks Thalos' `IChatClientProvider` for its client instead of building an `AnthropicClient`. There is one Anthropic
  path, with the same options, prompt caching and usage. `Daedalus.Infrastructure` loses its `Anthropic` reference.
- **Native proof:** "Application started" is required, then one native turn is attempted (see Finish line).

After the builder check, the owner also decided:

- **OllamaSharp leaves the AppHost too.** `CommunityToolkit.Aspire.Hosting.Ollama` depends on OllamaSharp, so the
  AppHost's `AddOllama("ollama").AddModel("nomic-embed-text")` is replaced by a plain Ollama container resource plus a
  model-pull step. That step must leave the same model available to the Api and the Cli.
- **Stream retries live in ZeroAlloc.Resilience.** Its generator learns to wrap an `IAsyncEnumerable<T>` method,
  retrying until the first item is yielded and never after. That is one more PR and release, in
  `ZeroAlloc-Net/ZeroAlloc.Resilience`, before ZeroAlloc.Rest.Anthropic ships.
- **Caller-set cache markers are dropped.** The translator places every breakpoint itself, from `PromptCacheHints`,
  which is all any real caller uses. The SDK-only seams it honoured are not rebuilt: `WithCacheControl`, raw SDK
  blocks sent verbatim, `ToolUnion` and a raw `MessageCreateParams` factory. Their tests go, and Thalos 0.20.0's
  BREAKING CHANGE footer names the change.

Standing rules that bind this phase:
- no local Native AOT publish on the agents VM (owner, 2026-10-22);
- no suppressions, and no workarounds presented as fixes;
- minors are fixed in the fix loop.

## Approach

### 1. ZeroAlloc.Rest: server-sent events

A client interface method may return `IAsyncEnumerable<T>`. Every such method needs a way to name the events it
yields. Anthropic's stream is named `event:` lines plus a JSON `data:` payload, with no `[DONE]` sentinel; it ends
when the connection closes, and a `message_stop` event comes before that. Both shapes must work:

- each event's `data:` deserialized as one `T` through the configured `IRestSerializer`, with the event name
  available to the consumer;
- or an event-name-to-type map onto a `T` base type.

The design leaves the exact attribute shape to the builder, under these constraints:
- it is source-generated and AOT-clean, and the response is read with `ResponseHeadersRead`;
- the parser is incremental and allocation-conscious, in the repo's style;
- it handles multi-line `data:`, comments, `retry:`, and a missing trailing blank line at end of stream;
- cancellation stops the read and disposes the response;
- a non-2xx status before the stream starts goes through the existing error path (`HttpRequestException` or
  `[ErrorMapper]`).

The generator's tests, the docs page and an AOT smoke sample cover it.

### 1b. ZeroAlloc.Resilience: retrying a stream before it starts

The Resilience generator only treats `Task` and `ValueTask` as async today. It learns `IAsyncEnumerable<T>`:

- a retry policy on such a method re-invokes it while the failure comes before the first item is yielded;
- once an item has been yielded, a failure propagates unretried;
- timeout and circuit-breaker semantics are defined for the same shape, or refused with a diagnostic if they do not
  apply. *Builder's call which.*

`ZeroAlloc.Rest.Resilience` then lets a ZeroAlloc.Rest SSE method carry `[Retry]`.

### 2. ZeroAlloc.Rest.Anthropic

The package is a typed client over `POST /v1/messages`, non-streaming and streaming, with its own models and one
source-generated `JsonSerializerContext`. It has no Microsoft.Extensions.AI dependency (owner, 2026-10-17).

- **Request:** model, max tokens, system as a string or as text blocks, and messages with text, tool-use and
  tool-result blocks. Optional fields: tools with input schema, temperature, top-p, stop sequences, metadata, and
  `cache_control` (`ephemeral`, TTL `5m` or `1h`) on system blocks, message blocks and tools.
- **Wire format:** unknown fields are never sent. Null optional fields are omitted. A tool's input schema passes
  through as raw JSON (`JsonElement`).
- **Response and stream events:**
  - The response is content blocks (text, tool use), the stop reason and usage.
  - Usage carries input, output, cache-read and cache-creation tokens, plus the TTL split if the API returns one.
  - Stream events are `message_start`, `content_block_start`, `content_block_delta` (text and input-JSON deltas),
    `content_block_stop`, `message_delta` (stop reason, usage), `message_stop`, `ping` and `error`.
  - An unknown event type or content block type is tolerated and skipped, not thrown, so a new API feature does not
    break old clients.
- **Transport:** `x-api-key`, `anthropic-version` and the base address come from options, through the existing
  `ZeroAlloc.Rest.DependencyInjection` registration. Retries go through `ZeroAlloc.Rest.Resilience`, with streaming
  retries resting on Approach 1b:
  - retry on 429, 529 and 5xx, honouring `retry-after`;
  - never retry after a stream has started yielding;
  - errors map to a typed `AnthropicApiError`, with type, message, status and request id.
- **Tests:** model round-trips against recorded transcripts and Anthropic's documented examples, plus the stream
  parser on recorded streams. An AOT smoke sample makes one call shape with zero warnings in the repo's AOT check.

### 3. ZeroAlloc.Rest.Ollama

The package is a typed client over `POST /api/embed`: model plus one or more inputs, returning embeddings. Like the
Anthropic package, it has no Microsoft.Extensions.AI dependency. Nothing else of Ollama's API is in scope.

### 4. Thalos.NET: adapters over our clients

- **`Thalos.NET.Anthropic`:** replaces the SDK with ZeroAlloc.Rest.Anthropic.
  - It gains its own `IChatClient` adapter, which replaces the SDK's `AsIChatClient`. The adapter maps both ways
    between M.E.AI and the client:
    - `ChatMessage`, `TextContent`, `FunctionCallContent` and `FunctionResultContent`;
    - `ChatOptions`: model, max tokens, temperature, tools via `AIFunction` schemas, stop sequences;
    - non-streaming responses and streaming updates, function-call arguments included;
    - usage: `InputTokenCount` is uncached + cache-write + cache-read, `CachedInputTokenCount` is cache-read, and
      `AdditionalCounts["CacheCreationInputTokens"]` is cache-write, exactly as the SDK adapter reports them today;
    - `ChatClientMetadata` and `RawRepresentation`.
  - `AnthropicPromptCacheTranslator` keeps its behaviour: at most four breakpoints in its priority order, the TTL,
    no mutation of the caller's input, and the cache-write copy to `TurnUsage`. Its markers now attach to our own
    request types instead of the SDK's `WithCacheControl` seams and raw representations. Caller-set markers are no
    longer honoured (owner, 2026-10-24), so the cap counts only the translator's own breakpoints.
  - Options, `UseAnthropic(...)`, `UsePromptCaching()`, `IChatClientProvider` and the `ANTHROPIC_API_KEY` fallback
    stay as they are.
- **Ollama embeddings:** the `IEmbeddingGenerator<string, Embedding<float>>` adapter over ZeroAlloc.Rest.Ollama
  becomes a new Thalos package, `Thalos.NET.Ollama`, with a `UseOllamaEmbeddings(...)` registration. *My call:* this
  follows the owner's 2026-10-17 pattern, client in ZeroAlloc and adapter in Thalos.
- **Release:** Thalos ships a minor release, 0.20.0. Its BREAKING CHANGE footer covers the public types that named
  SDK types.

### 5. Daedalus

- **Packages:** `Directory.Packages.props` drops `Anthropic` and `OllamaSharp` and bumps Thalos to 0.20.0.
- **`AgentFactory`:** takes `IChatClientProvider` and builds its client from it, keeping `UseFunctionInvocation()`
  and the MCP tools. `BrainstormService` and `GeneratePrdCommandHandler` behave the same: they read text and usage.
  - *My call:* it moves from `Daedalus.Infrastructure` to `Daedalus.Agents`.
    `CleanArchitectureTests.Infrastructure_ShouldNotDependOn_Thalos` forbids Infrastructure naming Thalos types.
    `Daedalus.Agents` is the one project that bridges the two, so the rule stands. `IAgentFactory` stays where its
    callers can see it, and its registration moves with the class.
  - *My call:* it keeps today's behaviour, translator included, with no prompt-cache hints and no Sentinel layer. Its
    model and max tokens still come from `ExternalServices:Llm:Claude` and are set per call through `ChatOptions`.
    `CostAnalyticsService` and `ClaudeModelPricedValidator` keep reading `Model`. That section's `ApiKey` goes: the
    key comes from Thalos' `Thalos:Anthropic:ApiKey` or `ANTHROPIC_API_KEY`, the same key every agent turn uses. The
    configuration docs say so.
- **Embeddings:** `Daedalus.Api` and `Daedalus.Cli` `Program.cs` register embeddings through `UseOllamaEmbeddings`,
  with the same endpoint and `nomic-embed-text`.
- **AppHost:** `CommunityToolkit.Aspire.Hosting.Ollama` goes. Ollama becomes a plain container resource, `ollama/ollama`
  with its data volume, plus a step that pulls `nomic-embed-text` before the Api and the Cli need it. The connection
  string the Api and the Cli receive keeps its shape. #412, the AppHost passing the model's connection string, is
  fixed on the way if this rewrite touches it. *My call.*
- **Tests:** the Daedalus tests that name SDK or OllamaSharp types are rewritten to the new types, with their
  assertions kept. Today these are `ClaudeConfigurationBindingTests`, `ApiHostClaudeModelTests`,
  `DaedalusAgentsRegistrationTests`, `CostAnalyticsCachePricingTests` and `ApiThalosConfigurationTests`.
- **Ratchet:** the baseline moves from CI's counts.

### Order

1. ZeroAlloc.Resilience's `IAsyncEnumerable<T>` support, then the owner's release. In parallel, ZeroAlloc.Rest SSE,
   then the two clients, which need that release before they merge. One PR or a short stack, then the owner's release.
2. Thalos.NET.Anthropic and Thalos.NET.Ollama on that release. A PR, then the owner's 0.20.0 release.
3. Daedalus on Thalos 0.20.0.
4. Native publish and smoke run, the live run, the upstream issue, then the docs.

While a step waits on a release, the next repo's work may be prepared against a local package feed. It is never
merged before the release it needs.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The SDK adapter's usage or tool mapping has behaviour our adapter misses | cost analytics or turn budgets drift | usage and tool round-trips pinned on recorded transcripts; the live run checks `/costs` |
| Stream parsing breaks on a wire detail the docs don't show | streamed turns fail live | recorded real streams in the tests; unknown events skipped |
| The ZeroAlloc.Rest generator change touches every client it generates | regressions in other consumers | SSE is opt-in by return type; existing snapshots unchanged |
| Four release hops make the phase slow | wall clock | Resilience and Rest work in parallel; prepare the next repo against a local feed while waiting |
| The plain Ollama container's model pull races the Api or Cli start | embeddings fail at start-up | the Api and the Cli wait on the pull step's completion, as Aspire's `WaitFor` does for the migrations |
| The native turn hits a stop another phase owns | proof incomplete | allowed by the finish line: recorded with its owner, not fixed here |
| The AppHost GitHub token still cannot push to Daedalus.NET | the live run fails at publish again | the run targets `daedalus-sandbox`, as 2.15 did, or the owner widens the token first |
