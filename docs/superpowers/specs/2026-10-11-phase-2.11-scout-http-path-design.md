# Phase 2.11 Design: The GitHub HTTP path

**Date:** 2026-10-11
**Phase:** `2.11`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

## Goal

Make every call Daedalus sends to GitHub and Azure DevOps go through generated, AOT-safe ZeroAlloc.Rest clients with
typed errors. A write is sent exactly once, repeated reads cost no GitHub quota when nothing changed, and the
remaining rate limit is visible in the dashboard.

## Decisions (owner, 2026-10-11)

| # | Decision |
|---|---|
| D1 | **Re-scope the phase to the GitHub transport.** The roadmap row said "ZeroAlloc.Rest replaces the 6 hand-rolled `HttpClient` API clients, and `ZeroAlloc.Cache` fronts the rate-limited GitHub API the scout hits on every digest". Research showed that premise does not hold (see "Current state"). This phase moves `GitHubApi` and the Azure DevOps pull-request client to ZeroAlloc.Rest, adds a conditional-request cache and a rate-limit gauge, and fixes the defects found on the way. **ZeroAlloc.Cache is not adopted.** The three Blazor clients for Daedalus's own API stay hand-written, apart from one bug fix. |
| D2 | **Typed errors reach the consumers.** `IGitHubReader` and `IGitHubWriter` return `Result<T, GitHubError>`, so a consumer can tell "rate-limited, retry later" apart from "forbidden". The agent tools turn the error into the text the agent sees. |
| D3 | **Writes are never retried automatically.** POST, PATCH, PUT and DELETE go out once. GitHub has no idempotency keys, so a retried write after a timeout can create a duplicate issue, comment or pull request. Recovery stays with the checks that are already safe: `file-findings` finds its own earlier output by marker, and the publisher looks for an open pull request before creating one. |
| D4 | **The conditional-request cache lives in memory, bounded.** One process-wide cache of `200` responses that carry an `ETag`, capped by entry count, least recently used evicted. A restart costs one full request per URL. No table. |
| D5 | **Measure the rate limit; do not throttle.** A gauge reports the remaining quota per GitHub resource. A refusal becomes `GitHubError` kind `RateLimited` with the time to retry, for primary limits, `429`s and secondary limits alike. Nothing waits or fails early before GitHub refuses. |
| D6 | **A facade over a generated client.** `GitHubApi` stays as the one class that knows GitHub's HTTP surface. It is rebuilt over an internal generated client; the five consumers never see HTTP. |

## Current state (research, 2026-10-11)

- **The "6 hand-rolled clients" are 3 + 3.** Only `GitHubApi` and `AzureDevOpsPullRequestFactory` call external APIs;
  `GitHubPullRequestFactory` delegates to `GitHubApi`. The other three, `ApiClient`, `AgentApiClient` and
  `ProjectApiClient`, are the Blazor app's clients for Daedalus's own API, which is not rate-limited. Ollama,
  Anthropic and Telegram go through SDKs or Thalos packages.
- **The scout is not where the pressure is.** One digest calls `daedalus__repo_activity` once: six GitHub GETs, one
  run a day, and the schedule ships disabled. A personal token allows 5,000 requests an hour.
- **A TTL cache would not help.** `GetActivityAsync(repo, sinceUtc)` keys on the previous occurrence, which changes
  every digest. ZeroAlloc.Cache 1.2.0 also caches whatever the inner call returns, failed results included, has no
  ETag support and no invalidation API.
- **The real pressure is the manufacture path.** `file-findings` reads up to 10 pages of issues and 10 pages of
  comments per issue; `issues__search` uses `/search/issues`, limited to 30 requests a minute; creating issues and
  comments is subject to GitHub's secondary content-creation limits.
- **Conditional requests are what saves quota.** A `304 Not Modified` answer to an authenticated `If-None-Match`
  request does not count against the primary rate limit.
- **Defects found:**
  1. `GitHubApi` documents that writes are never retried (`GitHubApi.cs:26-27, 260-263`), but
     `AddStandardResilienceHandler` retries every method, so a comment, issue or pull request can be sent up to four
     times. No `DisableForUnsafeHttpMethods` call exists.
  2. `AzureDevOpsPullRequestFactory` clears and sets `DefaultRequestHeaders` on every call (`:63-64`), which is not
     thread-safe on a shared client.
  3. `ProjectApiClient` deserializes with default, case-sensitive options (`:30, :54`), so camelCase responses do
     not bind.
  4. `GitHubOptions.MaxItemsPerCategory` defaults to 15 since PR #251, but `Daedalus.Api/appsettings.json:393` still
     sets 50 and overrides it.
  5. Only a `403` with `X-RateLimit-Remaining: 0` reads as rate-limited (`GitHubApi.cs:584-604`); a `429` and a
     secondary limit read as "forbidden".

## Approach

### Packages

- `ZeroAlloc.Rest` and `ZeroAlloc.Rest.Generator` at 3.3.2 or later. Their floors raise `ZeroAlloc.Results` from
  1.2.4 to 1.4.0 or later and add `ZeroAlloc.Collections` 1.2.0, under central transitive pinning. Each raised pin is
  commented with the package that set its floor, as in phase 2.9.
- ZeroAlloc.Cache is not added.

### GitHub

**`IGitHubRestApi`**, an internal `[ZeroAllocRestClient]` interface in `Daedalus.Infrastructure/Services/GitHub/`,
has one method per endpoint `GitHubApi` calls today:

- repository: `GET /repos/{owner}/{repo}`;
- commits: `GET /repos/{owner}/{repo}/commits`;
- pull requests: list, get, find open by head, create;
- issues: get, list updated since, create, comment, add labels, update state;
- issue comments since;
- `GET /search/issues`;
- workflow runs;
- `GET /user`.

Paths use `{owner}`/`{repo}` tokens and `[Query]` parameters; write bodies are `[Body]` DTOs. The API version and
accept headers are static method headers; the bearer token is added by a handler from `GitHubTokenSource`, as today.
An `[ErrorMapper]` turns `HttpError` into `GitHubError`.

**`GitHubJsonContext`** is a source-generated `JsonSerializerContext` over DTOs whose fields are nullable, so a missing
field stays an empty value, as `TryGetProperty` gives today. A body that cannot be read becomes kind `Unreadable`,
replacing `ReadShape`. This removes the `IL2026` suppression and the reflection serialization in `GitHubApi.cs`.

**`GitHubError`** is a `readonly record struct` with:
- `Kind`: `RateLimited`, `NotFound`, `Unauthorized`, `Forbidden`, `Validation`, `Conflict`, `Server`, `Transport`,
  `Timeout` or `Unreadable`;
- the status code, when there was one;
- `RetryAt`, from `X-RateLimit-Reset` or `Retry-After`, when GitHub gave one;
- a short message built from the kind, the status and the reset time. It never copies a response body.

A refusal is `RateLimited` when it is a `403` with `X-RateLimit-Remaining: 0`, a `429`, or a `403` carrying
`Retry-After` (a secondary limit).

**`GitHubApi`** stays the facade and implements `IGitHubReader` and `IGitHubWriter`, which now return
`Result<T, GitHubError>`. It keeps everything that is not HTTP: the six-category activity aggregation with its
per-category failures, `page=` paging that stops at the first short page, and `MarkerScan`'s memoisation. Where a caller
expects a missing resource to be a null success, as `GetIssueAsync` does today, the facade maps kind `NotFound` to
that success.

**Handlers**, from the outside in:
1. **`GitHubConditionalCacheHandler`** keys on the method and the full URL. For a `GET` with a stored entry it sends
   `If-None-Match`; on `304` it returns the stored body as a `200`; on a `200` with an `ETag` it stores the response;
   everything else passes through and is not stored. It is bounded by entry count with least-recently-used eviction.
   The process holds a single GitHub token, so no identity goes into the key; the code says so.
2. **`AddStandardResilienceHandler`**, with retries disabled for unsafe methods. Reads keep retrying on `5xx`, `408`,
   `429` and timeouts, honouring `Retry-After`.
3. **`GitHubRateLimitObserver`** records the gauge `daedalus.github.ratelimit.remaining`, tagged with
   `X-RateLimit-Resource` (`core`, `search`, ...), from every attempt's headers, `304`s included. The meter is a
   `daedalus.*` meter, so phase 2.9's wiring already collects it.

### Azure DevOps

`IAzureDevOpsRestApi`, an internal generated client with one `CreatePullRequest` method. The Basic PAT goes in as a
per-call `[Header("Authorization")]`, which removes the shared `DefaultRequestHeaders` mutation. Its write is sent
once, like GitHub's. `AzureDevOpsPullRequestFactory` keeps its `Result<T>` contract with the publisher.

### Consumers

- `DaedalusRepoTools`, `DaedalusIssueTools` and `DaedalusRepoActionTools` turn a `GitHubError` into the text the
  agent sees, as `MapError` does today; a rate limit reads "rate-limited until HH:mm UTC".
- `FileReviewFindingsAction` and the pull-request publisher branch on `Kind`: `RateLimited` fails the node with its
  retry time, so an admin retry (phase 2.5) knows when to try again.
- `GitHubPullRequestFactory` maps `GitHubError` into its existing `Result<T>` with the publisher.

### Small fixes in the same phase

- `ProjectApiClient` deserializes with the web defaults.
- `Daedalus.Api/appsettings.json` drops its `MaxItemsPerCategory` key, so the code default of 15 applies on every
  host and has one source.
- The roadmap row for 2.11 records this re-scope; the 2.10 row's "ZeroAlloc.Jev" becomes Minos.NET, and 2.10 is
  marked blocked on Minos.NET 1.0.

### Privacy (phase 2.9's no-content rule)

`GitHubError` messages carry no response body. The gauge's only tag is the resource name. Outgoing HTTP spans already
export only the origin, so request paths with repository names stay out of traces.

## Tests

- **Characterisation first.** Before any code moves, pin today's `GitHubApi` behaviour: the existing tests (about 54)
  plus tests for each endpoint's request shape (method, path, query, body, headers), paging, the six-category
  aggregation and the 404-to-null mapping. They run unchanged against the rebuilt facade; error assertions move from
  strings to `Kind`.
- **Error mapping:** each `Kind` from its status and headers, including a `429`, a secondary `403` with `Retry-After`,
  and `RetryAt` from `X-RateLimit-Reset`.
- **Handlers:**
  - the conditional cache replays a `304`; never stores an error or a `200` without an `ETag`; evicts at the cap;
    never caches a write;
  - a write is sent exactly once on a `503` and on a timeout, the regression test for the duplicate-issue defect;
  - reads still retry;
  - the gauge reports values and the resource tag.
- **Azure DevOps:** the per-call authorization header, and parallel calls that do not interfere.
- **Consumers:** the agent-facing text for each kind, and `RateLimited` failing a host-action node with its retry
  time.
- **Small fixes:** `ProjectApiClient` binds a camelCase response; `MaxItemsPerCategory` is 15 on the Api host.
- **Full regression:** all seven suites, Playwright included.
- Every assertion carries a `Red:` line naming the change that turns it red, verified by making that change.

### Live proof (owner-gated)

Default: one manufacture run on the sandbox repository, from a board task through the gate to a pull request. It
exercises the pull-request create, `file-findings` and the issue reads through the new transport. Then a repeated
`issues__get` must be answered from a `304` replay, which the gauge shows by not dropping, and the dashboard shows
`daedalus.github.ratelimit.remaining` for `core`.

Cheaper alternative, if the owner prefers: call `issues__get` twice and run one digest scout call through the API,
with no manufacture run. That proves the transport, the replay and the gauge for almost no model spend, but not the
pull-request create or `file-findings`.

## Open Questions

- Which live proof: the full manufacture run (the default above) or the cheaper alternative.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Typed DTOs change failure behaviour where today's lenient `TryGetProperty` reading tolerated odd shapes | Reads that worked start failing as `Unreadable` | Characterisation tests against recorded GitHub responses first; nullable DTO fields; compare old and new on the same fixtures |
| ZeroAlloc.Rest gives no access to success-response headers | The ETag cache and the gauge cannot live in the generated client | Both are `DelegatingHandler`s below the client, which see every response |
| A mapper cannot turn a failure into a success | The 404-to-null behaviour needs a home | The facade maps `NotFound` to a null success per method, as today |
| Raising ZeroAlloc.Results to 1.4.0 changes behaviour elsewhere | Breakage outside the GitHub path | Read its release notes; full regression |
| A stale cached body served after a `304` | An agent sees outdated data | GitHub's `304` means unchanged by definition; only `200`s with an `ETag` are stored; writes are never cached |
| Changing `IGitHubReader`/`IGitHubWriter` signatures touches five consumers and their tests | A larger diff | One task per consumer; the facade keeps all HTTP knowledge |
| Removing write retries surfaces more transient failures to agents and host actions | A run fails where a retry would have succeeded | That failure is visible and recoverable by an admin retry; a silent duplicate issue is not |
