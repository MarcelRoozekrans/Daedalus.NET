# Phase 2.12 Design — Manufacturing console

**Date:** 2026-10-12
**Phase:** 2.12
**Surface:** UI
**Stage:** phase (one phase, implementation-ready)

Brainstormed with the owner on 2026-10-12. Decisions D1–D7 below are owner-approved.

## Goal

An operator follows a manufacture run live in the browser, from Manufacture on a board task to its pull request,
and approves or cancels it at the human gate without touching the REST API.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Scope is a Runs list, a run detail page and the gate, plus the backend those need | Today the only UI for a run is a status badge and a PR link on its task; approving needs a raw `POST` |
| D2 | `ZeroAlloc.Flux` is the Web state layer for the whole app; 2.12 introduces it for runs and the Tasks page, and new phase 2.13 moves the remaining pages | Owner decision. The Tasks page shows run status, so it shares the runs state from the start |
| D3 | Live updates go over SignalR: a content-free `RunChanged` notification, and the client re-fetches through REST | Owner decision, replacing polling. Keeps one read path, and the hub never carries task content |
| D4 | Viewing and acting both stay on `WorkflowResume` (developer or admin); retry stays admin-only. No new policy | A run view holds findings and write paths; widening who reads it is a separate decision |
| D5 | Listing runs is a Thalos.NET 0.16.0 read API, `IWorkflowRunQuery` | Thalos owns the run tables; querying them from Daedalus couples it to a private schema |
| D6 | Change notification is a Thalos `IWorkflowRunObserver`, not a Daedalus store decorator | Daedalus sends resume, cancel and several readers through the undecorated `IWorkflowStore` on purpose, so a decorator misses exactly the gate actions |
| D7 | The step timeline is projected from Thalos 0.15's `IWorkflowRunHistory`; no Thalos change for it | `ListEventsAsync` already returns seq, kind, nodes, status, outcome, error, usage, time and actor |

## Approach

### Part A — Thalos.NET 0.16.0

Released and consumed before Part B starts.

- **`IWorkflowRunQuery.ListAsync(WorkflowRunFilter, WorkflowRunPage, CancellationToken)`** in
  `Thalos.NET.Workflow`, implemented over the ORM store in `Thalos.NET.Workflow.Orm`. Newest first by creation
  time, then id; keyset paging (an opaque `after` cursor and `take`, capped); filters by status and process name.
  A row is `WorkflowRunSummary`: id, process, process version, status, current node, awaiting signal, started-by,
  created and updated times. **No variables and no last error**, so no task content can leave through a list.
- **`IWorkflowRunObserver.OnChangedAsync(WorkflowRunChange, CancellationToken)`**, invoked after every committed
  change: start, node completion, resume, failure, stranded failure, cancellation and retry. `WorkflowRunChange`
  carries the run id, status, current node, awaiting signal and the change kind, nothing else. Observers run after
  the transaction commits, never for a rolled-back change. An observer that throws is logged by exception type and
  swallowed; it never fails or retries the change.
- Thalos tests against real Postgres for filters, ordering, paging and the cursor; for one observer call per
  committed change and none for a refused one (a lost concurrency race, a signal mismatch); and for a throwing
  observer leaving the change committed.

### Part B — Daedalus API

- **`GET /api/workflow-runs?status=&process=&after=&take=`**, `WorkflowResume`, over `IWorkflowRunQuery`. Each row
  adds the linked board task's id and title when one exists (one query by run ids over `Tasks.WorkflowRunId`).
- **The run view** (`GET /api/workflow-runs/{id}`) gains:
  - `Steps[]`, from `IWorkflowRunHistory.ListEventsAsync`: seq, kind, from node, to node, status, outcome, error,
    token usage, time and actor.
  - `Checked[]` per lens, from `ApprovingReview`'s latest review visit, the same evidence the PR body uses.
- **`WorkflowRunsHub` at `/hubs/workflow-runs`**, `[Authorize(Policy = "WorkflowResume")]`. A Daedalus
  `IWorkflowRunObserver` sends `RunChanged { Id, Status, CurrentNode, AwaitingSignal }` to all connected clients.
  Single API instance, no backplane; a scaled-out API needs one, the same limit the outbox lease already notes.
- **Bearer token on the socket.** WebSockets cannot send headers, so the client sends the token as `access_token`
  on `/hubs/*` only, and JWT bearer reads it from there for that path only. The token must not reach a span, a log
  or a metric: incoming request spans already export no query string by default, and a test asserts it.
- DTOs bound by Web pages live in `Daedalus.Application/DTOs/` (MASTER.md rule).

### Part B — Web

- `ZeroAlloc.Flux` and `ZeroAlloc.Flux.Blazor` in `Directory.Packages.props`. **Task 1 is a spike** that proves
  a `FluxComponent`, a reducer and an async effect in Blazor WASM, including the effect's DI scope. If the spike
  fails, the controller rules (fix upstream in ZeroAlloc.Flux, or a stated fallback) and records it, the way 2.11
  dropped ZeroAlloc.Cache.
- **Features:** `RunsState` (list page and filters, the selected run, the gate draft: dropped finding ids and the
  apply-standing-instructions flag, in-flight action) and `TasksState` (the board list, in-flight starts).
- **Effects:** API calls dispatch `…Loaded` or `…Failed`. A `RunHubConnection` dispatches `RunChanged`; its effect
  re-fetches the run if it is the selected one, refreshes the list page if the run is on it, and updates the task
  whose `WorkflowRunId` matches. A reconnect re-fetches everything on screen, since messages sent while disconnected
  are lost. The connection is opened only for a user who holds `developer` or `admin`.
- **Navigation:** a **Runs** menu item (Material icon `precision_manufacturing`), shown to `developer` and `admin`,
  with the count of runs awaiting approval.
- **`/runs`:** a `RadzenDataGrid` in the `Executions.razor` pattern: status badge, process and version, current
  node, linked task, started by, started and updated. Filters by status and process; keyset paging.
- **`/runs/{id}`:**
  - Header: status badge, process and version, current node, started by, the PR link or the unreadable-link text,
    and `LastError` in a `RadzenAlert`.
  - **Gate panel**, only while `AwaitingSignal` is `human_approval`: deferred findings with a drop checkbox each,
    the standing-instructions diff in a monospace block with an apply checkbox (off by default), **Approve**
    (`resume { Signal: "human_approval", DropFindings, ApplyStandingInstructions }`) and **Cancel** behind a
    confirm dialog with an optional reason.
  - **Retry**, admin only, on a failed run the API would retry.
  - Tabs: **Timeline** (`Steps[]`: node, outcome badge, error, duration, actor, tokens), **Review** (`Checked[]`
    per lens, deferred and filed findings with issue links), **Usage** (per node, cache reads and writes, totals),
    **Writes** (the write audit).
  - A 409 or 422 shows the server's ProblemDetails reason; a 409 because the run moved on also re-fetches.
- **`/tasks`:** on `TasksState`. The derived status badge links to `/runs/{RunId}`; `RunChanged` updates it in
  place; Manufacture navigates to the new run instead of showing a toast with its id.
- All of it follows `docs/design/MASTER.md`: Radzen only, `--rz-*` tokens, status as badge text plus colour.

## Tests

Every assertion names the change that turns it red, and the red is verified by making it.

- **Thalos (Part A):** query filters, order, cursor paging and the cap against Postgres; one observer call per
  committed change, none for a refused change; a throwing observer leaves the change committed.
- **Unit:** Flux reducers (loaded, failed, `RunChanged`, gate draft toggles); effects (a `RunChanged` for the
  selected run re-fetches it and for another run does not; a reconnect re-fetches what is on screen); the steps
  projection from history events; the `Checked[]` mapping; the serialized `RunChanged` has exactly its four fields.
- **Integration:** the list endpoint answers 401, 403 and 200, filters, pages, and carries no variables; the hub
  refuses a caller without `WorkflowResume`; a resume through the undecorated gateway path produces a `RunChanged`;
  the `access_token` value appears in no exported span or log record.
- **Playwright.Api:** the list endpoint and the extended run view.
- **Playwright.Browser:** the fixture keeps the engine disabled and seeds runs through the Thalos store. The list
  renders and filters; the detail tabs render; Approve with one dropped finding sends the exact body; Cancel needs
  the confirm; Retry is hidden from a non-admin; the Tasks badge links to its run.
- **Live proof (AppHost, `daedalus-sandbox`):** Manufacture on a task lands on `/runs/{id}`; the timeline advances
  live without a reload through implement, review, retrospect and the gate; approve from the gate panel with one
  finding dropped; publish and file-findings arrive live and the run ends `Succeeded` with its PR link; the Tasks
  and Runs pages updated without a reload; the run's spans carry no content and no URL carries a token.

## Open Questions

None. D1–D7 settled the design.

## Out of scope

- Moving Projects, Executions, Schedules, Costs, Agent, Git Repositories, PRD Generator and the Dashboard onto
  Flux: **phase 2.13**.
- A SignalR backplane for more than one API instance: a recorded limit.
- A reject path at the gate other than cancel: rejection is review's job, which routes to `adjudicate`.
- Starting a run from `/runs` without a task: `POST /api/workflow-runs` stays API-only; the board is the entry.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| ZeroAlloc.Flux's effect wiring does not work in Blazor WASM, or its docs are thin (the README marks them a placeholder) | The state layer stalls | Task 1 spike; a failure is fixed upstream or ruled and recorded before the pages are built |
| The SignalR `access_token` query value leaks into a span, log or proxy log | A bearer token in telemetry | Token read only on `/hubs/*`; an integration test scans exported spans and logs for the value |
| An observer runs inside the store's transaction or blocks it | Slower or failed workflow changes | Thalos invokes observers after commit and swallows their failures; a test proves a throwing observer changes nothing |
| A missed `RunChanged` during a reconnect leaves a stale page | The operator approves from stale state | Re-fetch on reconnect; the resume's 409 on a moved run re-fetches and says so |
| Browser tests need runs while the engine is disabled | No UI coverage | Seed runs through the Thalos store in the fixture, as the 2.8 tests seed tasks |
| Thalos release ordering | Part B blocked | Part A ships 0.16.0 first, as 2.9 shipped 0.15.0 |
