# Phase 2.10 Design — Per-node model and tool selection with Minos.NET

**Date:** 2026-10-13
**Phase:** `2.10`
**Surface:** `Backend`
**Stage:** phase (one phase, implementation-ready)

Brainstormed with the owner on 2026-10-13. Where this document says **owner**, the owner decided it in that
conversation. Where it says **my call**, the brainstorm settled it and the owner can overrule it.

## Goal

A manufacture run costs less and its agents are no longer handed tools they do not need: before a node runs, cheap
Minos.NET decisions choose its model and tool families from the sets its role allows, and fall back to today's
behaviour whenever a decision cannot be trusted.

## Why

**The owner's words:** "My account is draining", and "we should slim down". The owner's sense is that a simple pull
request costs EUR 3-6. Two goals, both the owner's: **fewer tokens** and **no confusion**.

**What the records show.** Recorded live runs, priced at list prices with uncached input counted as cache writes, so
leaning high:

| Run | Shape | Cost | Review share |
|---|---|---|---|
| `4949a215` (2.9) | approved first time | about $1.32 | review $0.98 |
| `65270f1c` (2.11) | one rejection | about $2.17 | the two reviews $1.74 |
| `e47eeac0` (2.12) | five rejections, #346 | not priced; about 3.6M input tokens | |

- **Review is 70-80% of a run.** Each lens is a full Opus 5 turn of about 230k input tokens, three per review, and a
  rejection repeats the review.
- **Tool definitions are about 13-14k tokens per call** for the implementer and the reviewer: 54 and 53 Roslyn tools,
  about 11k tokens, plus the Daedalus and Thalos families. They sit in the cached prefix, so they are a large share of
  input tokens but an estimated 10-20% of the money.
- **Confusion is independent of cost.** Phase 2.6's implementer misread a 74-tool list and reported the wrong run mode.

These figures are estimates: the run records hold tokens per node, not per call, and no exact token count was taken.
The comparison below replaces them with measurements.

## Goals

1. **A Minos foundation in Daedalus.** A decision client over Jev's `/v1/systemone` protocol, called through
   **OpenRouter** (owner), with every decision recorded against the run.
2. **Model per node.** Before an agent node runs, a decision rates the work and Daedalus picks that node's model from
   the role's allowed list.
3. **Tools per node.** A decision picks which tool families the node's turn is offered, from the role's configured
   list.
4. **A measured comparison** that decides whether the cheaper setup becomes the default.

## Non-goals

- **Task triage before Manufacture**, a decision on whether a task is specified well enough to build. Owner: later,
  folded into phase 2.13, which reworks the path from a board task to a pull request.
- **The smaller wins:** skill selection per node, skipping `retrospect`, ranking scout digest items, routing
  channel messages, deciding whether a turn needs memory recall. Owner: one later phase on this foundation.
- **A UI for configuring the workflow and choosing models per stage.** Owner: a later phase. 2.10 keeps the choices
  in configuration that UI can later edit.
- **Non-Claude models for agent turns.** My call: agent turns stay on Anthropic. Serving other models through
  OpenRouter is the parked second-chat-provider idea and belongs with the later UI.
- **Skipping review lenses.** Considered and dropped: it weakens the guard that makes a cheaper reviewer safe.

## Anti-goals: it fails even if it works when

- **A decision ever widens what a node may do.** A tool or model outside the role's configured set reaches a
  turn. Tool absence is a security boundary here: the implementer holds no `git__*` tool because it is not in its list.
- **A decision ever stands in for evidence.** No review verdict, no human gate, no publish decision is made or skipped
  by Minos. A probability is not evidence, and the review contract requires file, line and scenario to reject and a
  non-empty `checked[]` to approve.
- **Minos being down, slow or wrong breaks a run.** The worst case is today's behaviour and today's cost.
- **Selection costs more than it saves.** Per-turn variation that breaks the cached prompt prefix turns every turn into
  a cache write, which costs more than the reads it replaces.
- **A cheaper reviewer quietly approves more.** That would look cheap and be expensive later.
- **A decision is made again on a redelivery** and gives the replayed dispatch a different model or tools from the
  attempt it replaces. An admin retry cannot replay an agent node: Thalos' `RetryFailedNodeAsync` moves only host-action
  nodes, so a redelivery is the only replay.

## Constraints

- **Thalos cannot do this today.** `SubagentRunRequest` carries the agent, task, caller, budget and outcome schema,
  but no model and no tool list. Part A below adds them, which means a Thalos release before Daedalus can use
  them, the same shape as phases 2.2 and 2.12.
- **Minos.NET 1.0.1 is not on nuget.org yet.** Its publish hit a reserved package-ID prefix, and the owner has asked
  NuGet for it. Publishing is another agent's job. Daedalus develops against 1.0.1 packed from its `v1.0.1` tag into a
  local package folder that is never committed. The phase PR stays in draft until the packages are on nuget.org,
  because CI restores from nuget.org only. Nothing in what merges depends on the local folder.
- **Caching.** Caches are tied to a model and to the exact prefix of tools, then system prompt. Decisions are made once
  per node dispatch, before the first call, and the same inputs must give the same sets.
- **Central package management:** versions only in `Directory.Packages.props`.
- **Secrets:** the OpenRouter key is a secret like the GitHub token. Owner: it lives in the AppHost's user secrets on
  the machine that runs Daedalus, and Aspire passes it to the API. It never reaches a log, a span, a run variable or a
  record.
- **Telemetry:** decisions get spans and metrics under a `daedalus.*` source, carrying the question set, the chosen
  option and the confidence, never task content. Phase 2.9's privacy rules apply.
- **Cost analytics:** every model an allowed list can pick must have a price entry, or
  `CostAnalyticsPricingDriftTests` fails, which is the guard working.

## What the owner decided

- **Scope:** model and tool selection per node, on a shared foundation. The rest is later phases.
- **Skill selection is out.** The builder check found that each role lists only the skills its nodes need, so there is
  at most one skill to remove. It moves to the phase of smaller wins, or to when roles hold more skills.
- **Task text may go to OpenRouter, to zero-data-retention endpoints only.** The model decision reads the work intent,
  because the node, role and diff size alone make it barely more than a fixed rule. Requests reach only endpoints
  that do not keep or train on data.
  - **How that is enforced, found while planning:** Minos.NET 1.0.1 sends only the state, the model and the
    questions, with no OpenRouter provider preferences, so zero retention cannot be requested per call. It is an
    OpenRouter account setting (openrouter.ai/settings/privacy), under which a non-zero-retention model answers 404
    `zdr-violation-by-account`. Daedalus enables decisions only when configuration states that the account is
    restricted that way, and the live proof checks it by asking a model that retains data and seeing the 404.
    Per-request provider preferences are a Minos.NET feature, tracked there rather than patched around in Daedalus.
- **Provider:** Jev through OpenRouter.
- **Key placement:** AppHost user secrets on the Daedalus machine.
- **Configurable menus, gated by keys.** Each role has a configured list of allowed models, and a model is offered only
  when its provider's API key is set. Without an OpenRouter key, Minos is off and every node runs as today.
- **Cheaper models on review are in scope.** The lenses exist to make a model look at the change from separate angles,
  and the evidence rules stop an empty approval, so a cheaper reviewer guided by them is a fair candidate.
- **Prove it before it becomes the default.** About five sandbox tasks, each run under today's setup and the new one,
  at about EUR 15-25 in API spend plus the decisions' OpenRouter cost. Approved.
- **The bar:** at least **40% cheaper on routine tasks**, and **no finding the expensive reviewer caught is missed** by
  the cheaper setup. The 40% figure was my proposal, accepted.

## Approach

### Part A, Thalos: a turn can be narrowed, never widened

`SubagentRunRequest` gains optional per-request overrides: a **model** and a **tool list**. Thalos
resolves the agent as today, then intersects:

- **Tools:** the turn is offered the agent's resolved tools filtered by the request's list, glob for glob, so a request
  can only remove. A request naming a tool the agent does not hold is refused, not ignored, so a selector bug is loud.
- **Model:** a request model is accepted only if it is in the agent definition's own allowed-model list, which Thalos
  reads from configuration the same way it reads the agent's `Tools`. The request cannot carry or change that list, so
  the check is the engine's and a selector bug cannot pass it. My call, after the builder check found that a set passed
  with the request would be checked against itself.

**Placement, from the parked note:** a generic selection port in Thalos with a deterministic default that changes
nothing, and the Minos client in Daedalus. Thalos ships no dependency on Minos.

**Telemetry:** the turn span records the effective model and the number of tools offered, never their
names.

**Release** as a Thalos minor, after its own review, before Part B wires it in.

### Part B, Daedalus: the decisions

**The client.** Minos.NET.SystemOne and Minos.NET.DependencyInjection, registered with the OpenRouter preset when the
key is set and not at all when it is not. Minos's own retries and time-out apply. A decision has a time budget short
enough that a slow answer costs seconds, not a stalled node. The exact budget is for the builder, measured.

**The questions.** Declared as Minos `[Questions]` types, so the request and its parsing are generated at compile time:

- **Model:** a `Score` or `Choice` question rating how demanding the node's work is, from the work intent, the node
  and, on a revisit, how many review rejections came before it. Each level maps to a model in the role's configured
  menu.
- **Tools:** one `Noul` per tool family the role holds, such as `roslyn`, `workspace`, `sandbox`, `memory`, `skills`,
  `context7`, `issues` and `daedalus`. A family whose answer is yes, or is not confident enough, stays. Selection is by
  family, never by single tool, so the sets stay few and stable and the prefix caches.

**Never removable, my call.** Some tools a node cannot work without are kept whatever a decision says: the node's
outcome tool, `daedalus__report_review_outcome` on a review lens, and the workspace read tools. The builder lists them
from the skills' own requirements.

**Confidence.** Each answer carries a calibrated confidence. Below a threshold, the node keeps its configured default
for that choice: the role's default model, the family kept. Thresholds are configuration with a drift guard, because
the parked note found that a `Score` rescales silently when a criterion is added. The guard is a test that pins the
question set's shape, so a changed question set fails until its thresholds are looked at again.

**Where it runs.** A decorator on the dispatcher's runner chain, beside `RunModeRunner` and `ReviewFindingsRunner`,
once per node dispatch, before `ReviewLensRunner`, so the three lens passes share one decision and one cached prefix.
The one exception is a stronger model for the falsifiability lens, below.

**The falsifiability lens.** The lens most likely to need a stronger model, since it is the one that caught "all three
tests pass when `Contains` ignores its argument". Configuration may pin one lens to a model regardless of the decision.
Whether to pin it is settled by the comparison, not assumed.

**Recording.** Each decision is a run record, a new `WorkflowRunRecord` kind, keyed by the node visit, with the question
set, each answer and its confidence, the fallback taken, if any, and the effective model and tools. On a
redelivery of the same visit the record is read back and reused rather than re-asked, so the replayed dispatch gets
what the original attempt got. The run view lists the recorded choices. Showing them on the run page beside phase
2.12's timeline is in scope if it is small. If it is not, it goes with #354, which already covers what the run page
does not show.

**After a rejection, the run gets full tool sets, my call.** A `blocked` implement ends the run at `adjudicate`, so the
only revisits are the `implement` and `review` visits that follow a rejected review. From the first rejection on, tool
narrowing is off for the rest of the run and both nodes are offered their role's full configured list. A narrowed set
that caused the rejection, for example a review that rejected because a tool it needed was missing, must not be asked
for again and loop the run to its review cap. The model decision still runs.

**Configuration, my call.** The allowed models, never-removable families and thresholds live in
`src/Daedalus.Api/appsettings.json` on each `Thalos:Agents` entry, beside `Tools`, behind the same reviewed deploy.
`roles/README.md` keeps tool lists out of charters for that reason, and model menus are the same kind of boundary. The
charter's `model:` stays the default. Per role:

- an allowed model list, in order of cost;
- a default model, today's charter model;
- the tool families that may never be removed;
- the confidence thresholds.

A model is offered only when its provider's key is set. With every list empty, or no OpenRouter key, behaviour is
exactly today's.

### The comparison

My call on the shape, after the builder check showed that two full runs review different code. It has two halves,
inside the approved EUR 15-25:

- **Cost, end to end.** Four sandbox tasks on `daedalus-sandbox`, chosen to span routine and harder work, each run once
  with Minos off and once with it on, against the same commit. Per run, from the per-node and decision records: cost by
  node, rejections, cache reads against writes. Pass when the routine tasks are at least 40% cheaper. Tool narrowing's
  own effect is read from the per-node input and cache figures, not from a third arm of runs.
- **Review quality, on the same code.** The Minos-off run's implement output is kept as a worktree, and review is
  replayed on it under both reviewer setups. Pass when the cheaper setup raised every finding the Opus setup raised on
  the same worktree. This needs a small replay harness, which is part of the plan. The results go in
the phase rulings, as earlier live proofs did. A failed bar ships 2.10 with cheaper models off by default and tool and
tool narrowing on, if it passes on its own, and says so.

## What is left to the builder

- The exact `SubagentRunRequest` API shape in Thalos and its validation messages.
- Question wording, the score scale, the family list, and the thresholds, measured.
- The decision time budget and how a time-out shows in telemetry.
- Whether model and tools are one Minos call or two. One call is cheaper; the builder decides from Minos's
  limits.
- Which five sandbox tasks, chosen with routine and harder work both present.
- The local package folder's location and how it is wired for development only, never committed.

## Tests

- **Thalos unit:** a request can narrow tools and model; naming a tool or model outside the agent's set
  is refused; no override behaves exactly as today.
- **Daedalus unit:** each question set's mapping to a choice; a low-confidence answer keeps the default; the
  never-removable families survive a "no"; no key means no client and no change; the record is reused on redelivery;
  the drift guard pins the question shapes.
- **Integration:** the scripted run harness in `SquadHandoffEndToEndTests`, with a fake `IDecisionClient`, asserts the
  dispatched turn carries the chosen model and only the kept families, that three lens passes share one decision, and
  that a retried node reuses the recorded one.
- **Falsifiability:** every assertion red-verified by the change that breaks it, as CLAUDE.md requires.
- **Live:** the comparison above, plus one live run proving the decisions reach OpenRouter, the key appears in no
  span, and the records match what the turns were given.

## Open Questions

None blocking. Minos.NET 1.0.1 on nuget.org is a merge prerequisite, not a design question.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Minos.NET stays off nuget.org because NuGet refuses the prefix | 2.10 cannot merge | Develop against the local folder meanwhile; fall back to changing only `<PackageId>` in Minos.NET, which the owner can decide then |
| A cheaper reviewer approves what Opus would reject | Defects reach pull requests | The comparison's no-missed-finding bar, the lens evidence rules, optional pinning of the falsifiability lens |
| Narrowing breaks the cached prefix | Runs cost more | Family-level, deterministic sets, decided once per node, measured in the comparison |
| A decision removes a tool the node needed | The node fails or reports `blocked` | Never-removable families, confidence fallback, recorded decisions for diagnosis |
| Jev scores rescale when questions change | Thresholds silently change meaning | Drift guard on the question shapes |
| OpenRouter is down or slow | Slower nodes | Time budget, fallback to today's behaviour |
| The OpenRouter key leaks into telemetry | Secret exposure | Phase 2.9's redaction rules, a privacy check in the live proof |
| Task text reaches an endpoint that keeps it | The owner's task content stored by a third party | Zero-data-retention routing only, a start-up refusal for a model not available that way, checked in the live proof |
