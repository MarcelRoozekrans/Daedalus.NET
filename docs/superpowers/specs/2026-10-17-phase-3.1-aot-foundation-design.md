# Phase 3.1 Design: AOT toolchain, gates, baseline and ORM gap audit; the native sandbox host

**Date:** 2026-10-17
**Phase:** 3.1
**Surface:** Infra
**Stage:** phase (one phase, implementation-ready)

The owner skipped the design questions on 2026-10-17 and asked for a spec drafted from recon. The milestone design
(`docs/superpowers/specs/2026-10-17-milestone-3-design.md`) fixes the scope. Every decision below that the owner has
not made is marked **(my call)**.

## Goal

Native publishing works and is guarded in CI. Every target's AOT warnings are counted and can only fall, the sandbox
host ships as a native binary, the JIT "before" numbers are recorded, and ZeroAlloc.ORM's gaps against Daedalus are
known and filed upstream.

## Why

- Every later phase needs a native toolchain and a way to see its progress.
- The milestone measures gains "before (JIT) and after (native)". The "before" must be taken before 3.2 changes
  anything.
- The sandbox host is the closest target, at 8 warnings, so it proves the whole path end to end first: library fix,
  Thalos release, native publish, image, run.
- 3.5 depends on ZeroAlloc.ORM covering what EF Core does for Daedalus. Recon on 2026-10-17 found it does not yet, so
  the gaps must reach ZeroAlloc-Net long before 3.5 starts.

## What recon found (2026-10-17)

- **Toolchain:** the agent VM now has clang 19.1.7, the zlib headers and the `wasm-tools` workload. A native
  hello-world linked and ran. CI runs on `ubuntu-latest`, and the Docker images are built by a `docker` matrix that
  covers `daedalus-api` and `daedalus-web` only. **CI never builds the sandbox image.** The AppHost and the
  integration fixtures build it locally.
- **Warnings fail builds:** `Directory.Build.props` sets `TreatWarningsAsErrors`, so an AOT-analysis publish fails on
  its first IL2026. The analysis has to override that and count the warnings instead. The trim analyzer is off in
  Api, Agents, Cli, Migrations, Web and Sandbox today.
- **Sandbox host warnings:** all 8 come from Thalos' `Thalos.NET.Sandbox.Host` 0.17.0.
  - 6 are the `MapPost`/`MapGet` delegate overloads in `SandboxHost.cs:142-144`. The Request Delegate Generator must
    run in that library.
  - 2 are `SandboxHost.CreateBuilder`'s own `[RequiresUnreferencedCode]`/`[RequiresDynamicCode]`. They are caused by
    reflective tool discovery: `AddLocalTools(…, typeof(SandboxTools))`, and `WorkspaceTools` through
    `LocalToolSource`, which calls `AIFunctionFactory.Create` with reflection-based JSON on every invocation.
  - The sandbox image stays SDK-sized, 1.44 GB today, because runs build and test inside it. Only the host binary
    becomes native.
- **ZeroAlloc.ORM is raw SQL only.** It is source-generated `[Query]`/`[Command]` methods, with "no LINQ provider".
  So every EF query in Daedalus becomes hand-written SQL in 3.5. That is 32 source files, 20 entity configurations
  and 26 EF migrations. Confirmed gaps against Daedalus' usage:
  - **No adoption of an existing schema or of `__EFMigrationsHistory`.** `MigrationRunner` only knows its own
    `__zaorm_migrations`.
  - **No array parameters.** `text[]` is used by Skill, SkillVersion, RoleCharterVersion, AgentMemory and Task, plus an
    `unnest` query.
  - **No first-class jsonb parameter type.** It works today as a `string` with a `::jsonb` cast.
  - Optimistic concurrency, `Include`-style loading, `GroupBy`/`Join` aggregations, `ExecuteUpdate`/`ExecuteDelete`
    and the outbox/scheduling EF stores all map to hand-written SQL, multi-result queries, `IAsyncDbTransaction` and
    `ZeroAlloc.Outbox.Orm`. They are supported, but they are work.
  - pgvector is not used by the EF model any more. Rag.NET owns the vectors, so the extension is only a migration
    concern.
  - `Thalos.NET.Workflow.Orm` uses raw `NpgsqlCommand` and only the ORM's migration runner, not its generator. That
    is relevant to 3.2.
- **No measurement harness exists.** The API's `/health` checks Postgres. The sandbox has `/control/ready`, behind a
  bearer token. The CLI is a long-running console pump with no one-shot mode. `benchmarks/` holds microbenchmarks
  only.

## Goals

1. **An AOT-analysis gate in CI.**
   - A new `aot-analysis` job runs on every PR and every push to main, as a matrix over Api, Cli, Migrations, Sandbox
     and Web.
   - Each target runs `dotnet publish -c Release -r linux-x64 -p:PublishAot=true`. Web uses
     `-p:RunAOTCompilation=true` after `dotnet workload install wasm-tools`. Warnings-as-errors is overridden for this
     job only.
   - The job counts each target's **distinct** trim and AOT warnings (IL2xxx and IL3xxx, deduplicated by code and
     location) and compares them with a checked-in baseline, `eng/aot/baseline.json`.
2. **A ratchet in both directions (my call).**
   - The job fails if a count rises above its baseline.
   - It also fails if a count falls *below* its baseline without the baseline being lowered in the same PR.
   - So the file always states the truth, and a later phase cannot accidentally give back a gain. A falling count is
     progress that the PR records.
3. **One counting tool, used everywhere.** `eng/aot/count-warnings.sh` is the single implementation, so a contributor
   reproduces the CI number locally with one command. It runs the publish, parses the output and prints per-target
   counts, plus the top root-cause assemblies as a summary.
4. **The sandbox host ships native.**
   - **In Thalos:**
     - `Thalos.NET.Sandbox.Host` sets `IsAotCompatible` and runs the Request Delegate Generator;
     - its control endpoints bind through generated delegates;
     - its tool registration becomes AOT-clean. `SandboxTools` and `WorkspaceTools` are registered without
       reflective discovery, with a source-generated JSON context for their parameters and results;
     - `CreateBuilder` loses its `Requires*` attributes, and `CreateSlimBuilder` is used if it keeps everything the
       host needs **(my call)**;
     - it ships as Thalos 0.18.0.
   - **In Daedalus:**
     - `Daedalus.Sandbox` publishes with `PublishAot=true`;
     - the Dockerfile's build stage publishes the native host, and the runtime stage, still `sdk:10.0` because runs
       need the SDK, runs that binary as its entrypoint;
     - `SandboxImagePinTests` keeps passing.
   - **Proof:**
     - the sandbox target's AOT count reaches **0** in the baseline;
     - the integration suite's sandbox tests, which build the real image and drive runs through it, pass against
       the native host;
     - one live run uses the sandbox if Anthropic credits allow. If they don't, that run is carried to 3.6's live
       proof and recorded. **(my call)**
   - **CI:** the image is now built in CI as a third `docker` matrix entry, so a broken native host fails CI rather
     than the next local run **(my call)**.
5. **The JIT baseline is recorded before anything else changes.**
   - A harness under `eng/measure/` measures on the agent VM, with `--cpus 2` and the median of 10 cold starts
     **(my call)**:

     | Target | How it runs | What is measured |
     |---|---|---|
     | **API** | Its image, beside Postgres, Keycloak and migrations from `docker-compose.full.yml` | Time from container start to the first 200 on `/health`; resident memory after 60 s idle; peak resident memory after a fixed scripted load on an authenticated read endpoint; image size |
     | **CLI** | Against the same Postgres | Time from start to its ready prompt; idle resident memory. "Time to answer a turn" needs model credits and is left out of the baseline **(my call)** |
     | **Sandbox host** | Its image | Time to the first 200 on `/control/ready`; image size and `/app` size |

   - The numbers go in `docs/plans/2026-10-17-phase-3.1-aot-baseline.md` and the rulings. The harness stays in the
     repo so 3.6 measures "after" the same way.
   - The JIT baseline is measured on the code as merged **before** this phase's sandbox change, the `main` this phase
     starts from, so the sandbox host's "before" really is JIT **(my call)**.
6. **The ZeroAlloc.ORM gap audit, filed upstream.**
   - `docs/plans/2026-10-17-zeroalloc-orm-gap-audit.md` maps every EF Core feature Daedalus uses, across all 32 files,
     to its ZeroAlloc.ORM equivalent: supported, supported-with-work, or gap, with a file:line for each use.
   - **Verification:** each gap is confirmed before it is filed, from the ORM's source and tests at its latest release,
     2.3.4, since Daedalus pins 2.3.1.
   - **ORM scope (owner, 2026-10-17):** ZeroAlloc.ORM grows by **only the three hard gaps**. Those are adopting the
     EF-created schema and its `__EFMigrationsHistory`, array parameters, and jsonb parameters. There is no query
     layer, and Daedalus' queries become hand-written SQL in 3.5.
   - **Who fixes the gaps:** the owner runs that work in a separate agent.
   - **This audit is the handover to that agent (owner).** It is a human-readable table, and each gap has a minimal
     description of what Daedalus needs. 3.1 files **no** ZeroAlloc.ORM issues, so the separate agent doesn't meet
     duplicates.
   - **Follow-on:** the audit's estimate of 3.5's size, all queries as hand-written SQL, updates the milestone design.
7. **Record the owner's 2026-10-17 decisions in the milestone design.**
   - **3.5 depends on the three ZeroAlloc.ORM gaps being fixed.** There is no query layer and no new phase (owner).
   - **3.3's client lives in `ZeroAlloc.Rest.Anthropic`,** a ZeroAlloc-Net package with no Microsoft.Extensions.AI
     dependency. `Thalos.NET.Anthropic` keeps only the `IChatClient` adapter and the cache translator. Ollama follows
     the same pattern as `ZeroAlloc.Rest.Ollama`.
   - **The Anthropic issue is filed only once it is proven.** That means checking against the latest SDK release, and
     a native reproduction that fails at run time, not warnings alone.
8. **Documentation.**
   - A "Native AOT" section in the development guide: the toolchain (clang, zlib headers, `wasm-tools`), the counting
     script, the ratchet rule, and how to lower a baseline.
   - The README's build section points at it.

## Decisions from the builder check (my calls unless marked)

- **The MCP path is proven early, by a native run, not by warning counts.**
  - Before the Daedalus side starts, a native publish of a minimal Thalos sandbox host runs its MCP endpoint and one
    tool call. That covers `AddMcpServer`, `MapMcp`, `McpServerTool.Create`, the Roslyn proxy and the run-scoped MCP
    registry.
  - If the ModelContextProtocol SDK or anything else blocks it, the milestone's blocking-dependency policy applies.
  - If tool registration can only become reflection-free through the source-generated tool registry, that design
    moves from 3.2 into this phase. The controller rules on it and records it, and the plan is extended rather than
    worked around.
- **Tool registration:**
  - The plan picks the mechanism from that evidence: hand-written `AIFunction`s with a source-generated JSON context,
    or a small generator.
  - It may add public Thalos API, for example an explicit registration overload. `AddLocalTools(typeof …)` stays for
    JIT hosts, so other Daedalus hosts are untouched.
  - Thalos is 0.x, so this is a minor version bump.
- **Process spawning in the container:**
  - The plan checks that child processes (dotnet, git, `roslyn-codelens-mcp`) still find the SDK through
    `DOTNET_ROOT` and `PATH` when the parent is native, and that nothing reads `Assembly` locations or a content root
    the native binary lacks.
  - The proof is the integration sandbox tests plus one test that runs a build and a Roslyn call through the native
    host; it is added if missing.
- **The image build:**
  - The Dockerfile's build stage installs `clang` and `zlib1g-dev` and restores with `-r linux-x64`.
  - The target is linux-x64 only.
  - The image is built in CI's `docker` job but not published by `publish-release`, which is unchanged. Runs still
    build it locally through the AppHost.
- **What is counted:**
  - `eng/aot/baseline.json` holds one integer per target: distinct IL2xxx/IL3xxx warnings, deduplicated by code and
    location.
  - For Web it counts ILLink's trim warnings from the `RunAOTCompilation` publish, with trim warnings not suppressed.
  - A publish that fails for any reason other than warnings fails the job. It is never counted as 0.
  - A dependency bump that lowers a count must lower the baseline in the same PR, which is intended.
  - The job needs no secrets, so forks and Dependabot run it.
- **The baseline's code:**
  - The JIT numbers are measured on this phase's base commit, `main` `8173fd55`, checked out in a scratch worktree.
  - The harness runs from this branch against that build, and the commit SHA and image digests are recorded.
  - The load is 200 authenticated `GET /api/projects` requests at concurrency 10, with a token from the `dev` user
    in `keycloak-realm.json`, read at run time and never printed.
  - The variance between two runs is recorded; a run is not failed for it.
  - 3.6 measures on the same VM in the same way.
- **Release order:**
  - The Thalos change goes first, as a Thalos PR the owner merges, and release-please ships 0.18.0. All Thalos
    packages move to 0.18.0 together.
  - The Daedalus side then bumps and builds on it.
  - If the Thalos release is blocked, the Daedalus sandbox work waits, and the rest of 3.1 goes ahead.
- **`global.json`** pins SDK `10.0.402` with `rollForward: latestFeature`, which matches CI's `setup-dotnet 10.0.x`
  and the `sdk:10.0` images.

## Non-goals

- Fixing any target's warnings other than the sandbox host's. That is what 3.2 to 3.7 are for.
- Making the AOT job a **required** status check on `main` within this phase. The owner decided (2026-10-17) that it
  becomes required once it is green and stable on 3.1's PR, as a branch-ruleset change only they can make. STATE
  asks for it. Until then, every PR in this milestone treats a red `aot-analysis` as blocking.
- Any change to ZeroAlloc.ORM itself, or filing its issues. The owner's separate agent does that from this phase's
  audit.
- A one-shot mode for the CLI.

## Anti-goals

- **A gate that can't fail.** The ratchet must be proven red both ways:
  - raise a count and see the job fail;
  - lower one without updating the baseline and see it fail.
- **A suppression to make the sandbox host count 0.** The milestone's no-suppression rule applies. A
  `[RequiresUnreferencedCode]` moved somewhere else is not a fix.
- **A baseline measured on code this phase already changed.**
- **An ORM issue filed on a guess.** Each gap is confirmed in source or a test first.

## Tests

- **Gate:**
  - the counting script run on a recorded sample output gives known counts;
  - the CI job is proven red when a count is raised, and red when a count is lowered without a baseline change;
  - both red runs are recorded in the rulings.
- **Thalos:**
  - `Sandbox.Host` builds with zero trim and AOT warnings under `IsAotCompatible`;
  - its existing tests pass;
  - a native publish of a minimal host starts and answers `/control/ready`.
- **Daedalus:**
  - the sandbox target's count is 0;
  - the integration sandbox tests pass with the native host image;
  - `SandboxImagePinTests` passes;
  - every other suite passes.
- **Measurement:** the harness run twice gives medians within 10% of each other, or the variance is recorded.

## Open Questions

None blocking.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| `AIFunctionFactory` with source-generated JSON still needs reflection somewhere for the sandbox tools | The sandbox host can't reach 0 | Prove it with the native publish early in Thalos, before the Daedalus side. If it can't, the tool registry design moves from 3.2 into this phase |
| The native host behaves differently in the run container: Roslyn proxy, MCP transport, process spawning | Runs break | The integration sandbox tests drive real runs through the built image |
| Warning counts are not deterministic across runs or SDK patch versions | A flaky gate | Distinct warnings deduplicated by code and location; a `global.json` added to pin the SDK band, since the repo has none today **(my call)**; and the count checked twice in the PR that introduces it |
| ubuntu-latest lacks clang or zlib | The CI job fails at link | Install them with apt in the job, explicitly |
| Measurements are noisy on a shared VM | A meaningless baseline | `--cpus 2`, the median of 10, the variance recorded, and 3.6 measured on the same VM the same way |
