# Phase 2.7 Design — Issues as a first-class output

**Date:** 2026-10-09
**Phase:** `2.7`
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

Brainstormed with the owner on 2026-10-09. The owner made five decisions, labelled D1–D5 below.

## Goal

Daedalus's agents can read GitHub issues, and developers can file them through chat. A manufacture run files
the review findings it deliberately did not fix, so they are tracked instead of being lost in the event log.

## Decisions

| # | Decision |
|---|---|
| D1 | A run's "unfixed finding" is a **deferred finding recorded on an approval**: a real defect outside the change's scope. A rejection's findings are fixed in the review loop, so a run that reaches publish has none outstanding. The final rejection of a run that failed at the cap is **not** filed, because its `file:line` points at a branch that was never published. |
| D2 | **The reviewer decides whether a finding is a duplicate**, using read-only search. A deferred finding may name `existingIssue: N`, and the host re-checks it before commenting. Judgment stays with a model, and every write stays in host code. |
| D3 | **At the gate, findings are shown and filed by default.** The resume request may name findings to drop, and the drop is recorded with the resumer's id. Each finding ends up fixed, filed or explicitly dropped. |
| D4 | **Filing is its own host-action node after publish.** Issues link to the PR, and a filing failure never undoes or re-enters the publish step. |
| D5 | **The issue read tools get their own `issues__*` source**, named only by the reviewer and the chat Architect, rather than joining `daedalus__*`, which the implementer and the scout also carry. This keeps the tool-definition cost off agents that never call these tools. Choosing tools per turn with ZeroAlloc.Jev is a separate, later Milestone 2 phase, after 2.9. |

## Amendments made while writing the plan (2026-10-09)

Reading the code changed five details. These amendments override the sections below wherever the two differ.

| # | Amendment | Why |
|---|---|---|
| A1 | The drop list and each finding's filing progress are stored as `WorkflowRunRecord`s, of kind `findings-dropped` and `finding-filed`, not as run variables. | A Thalos host action can return variables only when it finishes, and a failed result merges none, so a run variable cannot record progress partway through the action. `WorkflowRunRecord` is already the host-written, insert-only store that review evidence and the write audit use. It needs no migration and no Thalos change, and its `PrincipalId` column records who dropped the findings. |
| A2 | The fallback check against duplicates scans GitHub with `since` the gate's resume time: the repository's issues, and the comments on each issue the action touches. It does not use the search API. | The search index can lag by minutes, and whether it indexes text inside HTML comments is undocumented. A listing filtered by `since` is exact and returns only a few items. |
| A3 | `file-findings` declares only the outcomes `filed` and `none`. Every failure is a failed result. | A failed result leaves the run `Failed` at `file-findings`, where phase 2.5's admin retry re-runs that node alone. A `failed` outcome would branch to `adjudicate` and leave nothing to retry. |
| A4 | The repository and PR number come from the run's `pr_url`, and the action checks the repository against the allow-list again. | This needs no workspace, which the sweeper may already have removed, and the PR is the thing the issues link to. |
| A5 | `issues__search` refuses a query that contains a `repo:`, `org:`, `user:` or `owner:` qualifier, and drops any hit from another repository. | GitHub combines several `repo:` qualifiers with OR, so prepending `repo:<r>` alone does **not** keep a query inside one repository. Section 1's original claim was wrong. |

## Approach

### 1. Agent-facing issue tools

**`issues__get(repo, number)`** and **`issues__search(repo, query, state = open)`** are ungated reads in a new
`issues` tool source.
- `issues__get` returns the title, state, labels and the body truncated to about 2 KB. It refuses a number that is a pull request.
- `issues__search` prepends `repo:<repo> is:issue` to the query. It refuses a query that carries its own `repo:`, `org:`, `user:` or `owner:` qualifier, and drops any hit whose repository is not `<repo>` (A5). It returns at most 10 hits, each as number, title, state and URL, with no bodies.
- Both tools label issue text as third-party content. Anyone can write an issue on a public repository, so the text is untrusted. The worst a planted body can do is steer an `existingIssue` pointer, and the host re-checks that pointer (section 3).
- Only the `reviewer` role's `Tools` list and the chat Architect's `Tools` list name `issues__*`. The implementer, the scout and the other agents do not see these tools at all.

**`repoaction__create_issue(repo, title, body)`** joins `DaedalusRepoActionTools`.
- The existing `repoaction__* → developer` policy binding covers it.
- A `WorkflowCaller` fails that policy, and no workflow role lists `repoaction__*`, so no run can call it. It exists for developer chat sessions.
- The Architect's instructions, which say "comment, label or close", gain "or file".

**`GitHubApi`** gains `GetIssueAsync`, `SearchIssuesAsync` and `CreateIssueAsync`. All three return `Result<T>` like the existing methods. The tools and the host action use the same three methods.

### 2. Deferred findings in the review evidence, and the gate

**The review tool gets a `deferred` argument.** `daedalus__report_review_outcome` takes an optional `deferred`
JSON array, which is accepted **only with an approval**. On a rejection everything is in scope to fix, so a `deferred` there is refused.
- Each entry is `{file, line, title, scenario, reason, existingIssue?}`.
- `reason` is one of `different-area`, `needs-decision`, `too-large` or `blocked`, the owner's own criteria for filing instead of fixing. A finding that fits none of them is not deferrable, and the reviewer must reject so that it is fixed.
- `ReviewEvidence.Validate` refuses a hollow entry: one with no file, a non-positive line, an empty title or scenario, or a reason outside the set.
- The limits match the existing ones: at most 32 entries, 1000 characters per field with a `title` capped at 200, and no NUL.

**The host records the evidence.** The tool writes `deferred` into the same review evidence that
`ReviewHandoffWorkflowStore` already owns. An agent cannot plant a finding through a run variable, which closes the same hole phase 2.4's final review found for standing-instruction proposals.

**Only the approving visit counts.** The host keeps only the deferred findings recorded by the three lens
passes of the final review visit, the one that approved. Earlier visits ended in a rejection, and their
`file:line` points at code that was edited afterwards. Each kept finding gets a stable id, `<lens>-<n>`.

**At the gate:**
- `GET /api/workflow-runs/{id}` shows `deferredFindings` with their ids, beside the standing-instructions proposal.
- `ResumeWorkflowRunRequest` gains `DropFindings: string[]?`. `WorkflowRunGateway` refuses an id that is not in the run's deferred set with a 422, so a typo cannot silently file a finding.
- The accepted drop list is written as a `findings-dropped` record, with the resumer as its principal (A1). A run that has deferred findings always gets one, even when the list is empty, so the latest record is the one that applies.

### 3. The `file-findings` host action

**Process v9:**

```
publish(published) -> file-findings
file-findings(filed)  -> done
file-findings(none)   -> done
```

Any failure fails the run at `file-findings`, where the admin retry re-runs that node alone (A3).

Runs pinned to v8 are unaffected. `file-findings` runs the `file-review-findings` host action. No model runs it, and no agent holds a tool that could.

**Inputs**, all host-owned:
- the run's allow-listed repository;
- the PR URL and head commit that `publish` recorded;
- the deferred findings of the approving visit;
- the drop list.

**For each finding that was not dropped:**
- **The finding names `existingIssue: N`:** the host re-reads #N. If #N exists, is an issue and is open, the host comments on it with the finding and the PR link. Otherwise the host files a new issue whose body says which number the reviewer pointed at and why it was not used.
- **Otherwise:** the host files a new issue. The title is the finding's title. The body holds:
  - a permalink to `file:line` at the PR's head commit;
  - the scenario;
  - the reason;
  - the lens;
  - the run id;
  - the PR link.
- **No labels.** A label that does not exist in the target repository would have to be created there, and that is an extra write.

**After the findings,** the host posts one comment on the PR. It lists:
- the issues filed;
- the issues commented on;
- the findings the gate dropped, and who dropped them.

**Outcomes:**
- `none`: nothing remains after the drops, so no GitHub call is made.
- `filed`: every remaining finding was handled.
- On the first GitHub error the run fails, and the error names the finding id and GitHub's answer, never a host path (compare #319).

**A retry must not duplicate anything.**
- Every issue, issue comment and PR comment carries the hidden marker `<!-- daedalus-run:<runId> finding:<id> -->`. The PR comment uses `finding:summary`.
- Each finding's result is written as a `finding-filed` record as soon as the finding is handled, and the admin retry skips any finding already recorded (A1).
- A crash between the GitHub write and the record is caught before writing, by scanning the issues and comments updated since the resume for the marker (A2).

## Tests

Each assertion must name the code change that turns it red, and the author makes that change once to see it fail (per `CLAUDE.md`).

- **Unit, `ReviewEvidence`:** `deferred` is refused on a rejection, and so is an entry with a reason outside the set, a missing or empty field, or a non-positive line. The limits are enforced.
- **Unit, the issue tools:**
  - `issues__search` prepends the scope, refuses a query containing `repo:other/x`, and drops a hit from another repository;
  - `issues__get` refuses a PR number;
  - bodies are truncated.
- **Unit, the approving-visit selection:** a deferred finding recorded in an earlier, rejected visit never reaches the gate.
- **Unit, `FileReviewFindingsAction`**, run against a fake GitHub:
  - `none` makes no calls;
  - dropped ids are skipped;
  - an open `existingIssue` is commented on;
  - a closed `existingIssue`, or one that is a PR, falls back to a new issue;
  - a retry after partial success duplicates nothing, through both the `finding-filed` record and the marker scan;
  - a failure's text contains no host path.
- **Integration:**
  - v9 loads, validates and activates;
  - a resume with an unknown `DropFindings` id is refused with a 422;
  - the drop list is recorded with the resumer's id;
  - `repoaction__create_issue` is denied to a `WorkflowCaller`;
  - `issues__*` is absent from the implementer's resolved tool list and present in the reviewer's.
- **Architecture:** `CleanArchitectureTests` stays green.
- **Live proof** on `daedalus-sandbox`:
  - First, confirm that the fine-grained token has `Issues: Read and write`. Phase 2.5's first publish failed with a 403 on `Contents` for this reason.
  - Seed a work intent that provokes a real out-of-scope finding, and have one open issue that is the right `existingIssue` target. At the gate, drop one finding.
  - It passes when the event log shows a filed issue linking the PR, a comment on the existing issue, the dropped finding absent with its dropper recorded, the PR summary comment, and `Succeeded`.
  - Per-node token usage goes into the rulings doc, so the cost of `issues__*` is measured rather than estimated.
  - If the reviewer defers nothing, the live-proof table records that. The filing path then rests on the integration tests, and the table says so.

## Open Questions

None. The one open question, whether a Thalos host action can save variables partway through a node, was answered while writing the plan: it cannot, so amendment A1 stores progress as records instead. No Thalos change is needed.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The reviewer over-defers to approve sooner, deferring what it should have rejected | Defects ship and are merely tracked | The closed reason set; the skill states that a finding fitting no reason is a rejection; the gate shows every deferred finding to a human, who can reject the run |
| The token lacks `Issues: write` | `file-findings` fails after the PR is open | A pre-flight check in the live proof, and the admin retry re-runs only this node |
| A crash between a GitHub write and its `finding-filed` record | A retry could duplicate a finding | The `since`-filtered marker scan finds the earlier write before writing again (A2) |
| A planted issue body steers `existingIssue` | A finding is posted as a comment on an unrelated issue | The host re-checks that the issue exists, is an issue and is open; the PR comment lists every target, so a human sees where each finding went |
| The search API's rate limit (30 requests a minute) | Reviewer searches are throttled | At most 10 hits per search. The host action does not use the search API at all (A2). |
