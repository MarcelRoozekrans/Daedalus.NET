# Phase 3.6 Design — `Native API, CLI and Migrations`

**Date:** 2026-11-11
**Phase:** `3.6`
**Surface:** `Infra`
**Stage:** phase (one phase, implementation-ready)
**Status:** approved 2026-11-11

## Goal

`Daedalus.Api`, `Daedalus.Cli`, `Daedalus.Migrations` and `Daedalus.Sandbox` publish with `PublishAot=true` in CI with
zero trim or AOT warnings and no suppressions. The native Api passes the API suites, a live manufacture run succeeds on
it, and start-up, working set and image size are measured before (JIT, phase 3.1) and after.

## Why

Milestone 3 exists to ship native binaries. Phases 3.2 to 3.5 removed the reflection Daedalus owned, the old SDK
clients, controllers and EF Core. 3.6 is where that is proven: until the binaries publish clean and run the real
workload, "native" is a claim, not a result.

## Starting point (measured on main, CI run 42902084735)

`eng/aot/baseline.json`: Api 49, Cli 2, Migrations 0, Sandbox 0. Web 196 belongs to phase 3.7.

The 49 Api warnings are:

- **46 from YamlDotNet 18.1.0.** It arrives through `Thalos.NET.Workflow` 0.20.0 (`Thalos.NET.Skills` is not the
  source). Daedalus has no YamlDotNet reference and no source file uses it. The warnings are the reflection-based
  `Serializer()`, `Deserializer()`, `ObjectFactories`, `TypeConverter` and `ReflectionExtensions` paths. A string scan of
  `Thalos.NET.Workflow.dll` shows only `StaticDeserializerBuilder`, so the static context is used there and the
  reflection path is reached some other way. **Finding the root is task 1.** It is not yet known.
- **3 from `ChannelOutboxServiceCollectionExtensions.cs:129`**, `WithSystemTextJsonSerializer`
  (IL2026 and IL3050). The warning names `AddSerializerDispatcher` as the AOT-safe call (R136).

The Cli's 2 warnings are probably the same outbox call, to be confirmed from the Cli keys file.

`PublishAot` is `false` in the Api, Cli and Migrations csproj files today. CI forces it with `-p:PublishAot=true`.
Sandbox already has it `true`. The Api csproj comment saying Aspire and AI.Sentinel need reflection, and that agent
session JSON has no source-generated contexts, predates 3.2 and must be re-checked, not trusted.

## Goals

- Zero warnings for Api, Cli and Migrations, `eng/aot/baseline.json` at 0 for all four server targets.
- `PublishAot=true` set in the csproj files, so a plain publish is native and the CI flag stops being the only guard.
- The outbox warning gone through `AddSerializerDispatcher`.
- The YAML warnings gone **at the source**: the package that reaches the reflection path is changed, released and
  consumed. Owner decision, 2026-11-11.
- Native suites in CI (below), the carried native CLI turn, a live run, before and after measurements.
- README and development guide describe the native build and the AOT rules for contributors.

## Non-goals and anti-goals

- No `UnconditionalSuppressMessage`, no `NoWarn` for IL codes, no rd.xml or trimmer roots to hide a warning.
- No change to the HTTP contract or to what the suites assert.
- No local Native AOT publish on the agents VM (CI only).
- Web (WebAssembly AOT) is 3.7. EF Core is already gone.
- A passing suite with warnings kept by a baseline raise is a failure of this phase.

## Approaches considered

**Where the native suites run.**

1. *CI runs the suites, owner runs the live run (chosen, owner decision 2026-11-11).* Extend `native-publish.yml`, which
   is gated on the `native-publish` label: after the publish, start the native Api against Postgres and run
   Playwright.Api against it. The measurements come from the same job with the
   existing `eng/measure` scripts. The owner runs the live manufacture run once with a real key.
2. Everything in CI, with a secret-backed live run. Reproducible but needs a repo secret and costs real spend each time.
3. Native publish and suites on every PR. Strongest guarantee, but 21 to 30 extra runner minutes per PR.

**How the YAML warnings are cleared.**

1. *Fix at the source (chosen, owner decision 2026-11-11).* Trace the caller, fix it in the owning package, release,
   bump. Costs a release cycle and may make 3.6 wait on it.
2. Stop loading YAML on the Api path. Larger behaviour change, not chosen.

## Approach

Order of work:

1. **Trace the YAML root.** Build a Cli or Api publish in CI with the ILC `--verbose` or the existing warning log plus a
   dependency graph to find which type reaches `Serializer()` and `Deserializer()`. Candidates: Thalos.NET.Workflow
   code, a Thalos or ZeroAlloc type in the Api composition, or YamlDotNet's own static path. Output: a one-page finding
   in the rulings doc and, if the fix lives upstream, an issue and PR there.
2. **Outbox serializer.** Replace `WithSystemTextJsonSerializer` with `AddSerializerDispatcher` in
   `ChannelOutboxServiceCollectionExtensions.cs`, with a source-generated context for the outbox payloads. The Cli count
   should fall to 0 here.
3. **Upstream YAML fix and bump** (task 1's result). Drives Api to 0.
4. **Flip the csproj files** to `PublishAot=true`, drop `EnableTrimAnalyzer=false` where it hides analysis, and set the
   baseline to 0 for Api, Cli, Migrations and Sandbox. The ratchet then guards it.
5. **Native suites.** Playwright.Api hosts the Api in memory through `WebApplicationFactory` with stubs and a test
   auth handler, so it cannot target a production binary (found while planning, owner decision 2026-11-11). Move the
   overrides into one shared class, add `tests/Daedalus.Tests.NativeApiHost`, a web project that references
   `Daedalus.Api`, applies them and is published natively, and run Playwright.Api against it over `E2E_BASE_URL`,
   which `ApiTestBase` already reads. The production Api binary is also started and health-checked in the same job.
   The API integration suite stays JIT: it uses `WebApplicationFactory` too. Failures are native-only defects to fix.
6. **Native CLI turn and sandbox host**, as 3.5's R136 left them. The CLI turn needs a key, so it runs with the owner's
   live run.
7. **Measurements**: start-up, working set and image size for Api, Cli and the sandbox host, native now against the JIT
   figures recorded in 3.1, written into a measurements doc.
8. **Live run** by the owner, from a board task to a pull request on `daedalus-sandbox`, spend on `/costs`.
9. **Docs**: README and development guide.

## Tests

- The ratchet in the `aot-analysis` job: all four server targets at 0.
- Native suites job: Playwright.Api against the natively published test host, plus a start and health check of the production binary.
- A unit test that the outbox payload round-trips through the new JSON context (it must fail if the context lacks a
  type, so it is not a vacuous pass).
- The unchanged JIT suites keep running on every PR.
- Live run and CLI turn: manual, owner, recorded with run id and cost.

## Open questions

- Who calls the YAML reflection path, and is its fix in Thalos, a ZeroAlloc package, or YamlDotNet? Task 1 answers it.
  If the fix needs an upstream release, 3.6 waits on it, and per the milestone convention the phase notes the tracking
  issue.
- Do the Api's remaining reflection needs named in its csproj comment (Aspire, AI.Sentinel, session JSON) still exist?
  The warning list says no more warnings come from them, but a native-only runtime failure is possible. The native suites
  decide.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| The YAML fix needs an upstream release that takes time | 3.6 cannot reach zero | Start task 1 first; file the upstream issue the same day; do the other tasks in parallel |
| Native-only runtime failures (missing metadata) show up in the suites | Suites red on the native Api | Fix in code with source generation; never a trimmer root as the fix |
| Suites job is long (publish about 21 minutes plus suites) | Slow feedback | Label-gated, runs only on the phase PR |
| `codecov/project` stays red until main carries a clean report | PR cannot merge normally | Known; no admin merge without the owner saying so |
| Live run and CLI turn need the owner's key | Phase waits on a person | Everything else lands first; the owner is asked once, with the binary and steps ready |
