# Phase 2.13 Navigation and Flow Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A person goes from sign-in to a merged pull request in the Web app without dead ends, on desktop and phone,
and a run explains why it failed and what review found.

**Architecture:** Three API additions on the existing endpoints:
- an optional task Prompt;
- a run's derived failure reason, plus the PR link on run list items;
- per-visit review history.

Then the Web changes against the approved UI contract: sign-in, shell and menu, Tasks, Home and the run page. Pages
already on ZeroAlloc.Flux (Tasks, Runs) change inside their Flux state, and the others keep their current approach.

**Tech Stack:** .NET 10, Blazor WebAssembly, Radzen.Blazor 8.7.5, ZeroAlloc.Flux, ZeroAlloc.Results, xUnit,
AwesomeAssertions, Playwright (Api and Browser projects).

**Spec:** `docs/superpowers/specs/2026-10-15-phase-2.13-navigation-and-flow-design.md`
**UI contract (approved):** `docs/plans/2026-10-15-phase-2.13-navigation-and-flow-ui-contract.md`

## Global Constraints

- **Design system:** only `--rz-*` tokens. No new gradients, fonts, colours or component libraries; Radzen only
  (MASTER.md).
- **Copy:** every page has an `H4` title and a `Body2` caption, with no icon beside a heading. Status is never shown by
  colour alone.
- **Status mapping:** `RunStatusLabels` is the only mapping for runs and steps, and no page writes its own.
- **Web references:** `Daedalus.Web` references only `Daedalus.Application`, so every DTO it binds lives in
  `Daedalus.Application/DTOs/`.
- **Validation:** a `[Validate]` DTO change needs both its `ValidatorFor<T>` and its `IValidationAdapter` registration
  (CLAUDE.md).
- **Results:** expected failures return `Result<T>`, never an exception. Logging uses `[LoggerMessage]`, and services
  use primary constructors.
- **Privacy:** a run view never sends `review_response` or findings to a reviewer dispatch. The withholding is a
  projection on the dispatch, and the operator view is allowed to show them.
- **Tests:** falsifiability is checked per assertion. Every assertion carries a `Red:` line naming the change that turns
  it red, and that change is applied, seen failing and restored.
- **Commits:** conventional, with body lines at most 100 characters, no nested parentheses, ending with the trailer
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
- **Integration and browser runs on the agent host:** set `DOTNET_USE_POLLING_FILE_WATCHER=1` while an Aspire stack
  runs.

## Review Focus

1. **A token refresh that fails mid-form.** The user is sent to sign in and returns to the same page. Test: Task 4,
   `An_expired_session_redirects_to_sign_in_and_back`.
2. **Create and manufacture where the task is created but manufacture is refused**, for example because the project's
   repository is not allow-listed. The task exists, and Tasks shows the refusal reason. Test: Task 6,
   `A_refused_manufacture_after_create_keeps_the_task_and_says_why`.
3. **A run that failed at a terminal node no derivation path knows.** The reason falls back to `lastError`, else "The
   run ended at <node>". It is never empty and never throws. Test: Task 2,
   `An_unknown_failure_path_falls_back_to_the_terminal_node`.
4. **A review visit with no `review-response` record**, from a run before this phase. It shows "No response recorded",
   not an error. Test: Task 3, `A_visit_without_a_response_record_reads_as_none_recorded`.
5. **A phone with the menu open, followed by navigation.** The overlay closes and the content is full width. Test:
   Task 5, `On_a_phone_the_menu_overlays_and_closes_on_navigation`.

  - unreadable records give `ReviewVisitsError` naming their seqs, as `NodeSelectionsError` does.
