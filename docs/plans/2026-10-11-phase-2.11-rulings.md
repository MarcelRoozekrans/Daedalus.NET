## What this phase produced

Every call Daedalus sends to GitHub and Azure DevOps now goes through a generated, AOT-safe ZeroAlloc.Rest client with
typed errors. A write is sent exactly once, a repeated read costs no GitHub quota when nothing changed, and the
remaining rate limit is a gauge in the dashboard. The defects fixed on the way: writes were retried up to four times,
the Azure DevOps token sat on a shared header, `ProjectApiClient` ignored the web JSON options, the Api's
`appsettings.json` overrode `MaxItemsPerCategory`, a 429 or secondary limit read as forbidden, and a Polly timeout
escaped as an exception.

- **Packages (Task 1).** ZeroAlloc.Rest and ZeroAlloc.Rest.SystemTextJson 3.3.2 in `Daedalus.Infrastructure`, with the
  generator bundled in the first. The floors they set: ZeroAlloc.Results 1.2.4 to 1.4.0 and ZeroAlloc.Collections 1.2.0.
  No other pin needed raising.
- **The transport (Tasks 3 and 4).**
  - `GitHubError`, a readonly record struct with kinds `NotFound`, `Unauthorized`, `Forbidden`, `Validation`,
    `Conflict`, `RateLimited`, `Timeout`, `Server`, `Transport`, `Unreadable` and, from the last fix, `Rejected`. Its
    `Message` is built from the kind, the status and the retry time only. It never copies a body.
  - `GitHubErrorMapper` turns every ZeroAlloc.Rest failure into a `GitHubError`. It reads at most 2 KiB of an error
    body, to classify a secondary limit and to fill the agent-only `GitHubSaid`.
  - `IGitHubRestApi` has one method per endpoint, with a source-generated `GitHubJsonContext` over all-nullable DTOs.
- **The facade (Task 5).** `GitHubApi` builds two generated clients over two named `HttpClient`s, `GitHub.Read` and
  `GitHub.Write`. It keeps the aggregation, the paging, the 404-to-null rule of `GetIssueAsync` and the shape checks.
  `IGitHubReader` and `IGitHubWriter` return `Result<T, GitHubError>`, and the three agent tool classes print
  `ForAgent()`.
- **Consumers (Tasks 6 and 9).** A rate-limited `file-findings` node fails with its retry time. The pull request
  publisher shows the platform's body-free, repository-free failure text on the run. The catch-all that copied an
  exception's message into a failure is gone, and caller cancellation propagates.
- **Write once (Tasks 7 and 8).** `GitHub.Write` keeps the timeouts, circuit breaker and limiter, and its retry never
  handles. `GitHub.Read` retries 5xx, 408, timeouts and connection failures, and does not retry a 429. Azure DevOps got
  its own generated client, a per-call `Authorization` header and the same never-retry rule.
- **Cache (Task 10).** `GitHubConditionalCache`, a singleton of at most 200 entries of 256 KiB, a true LRU, under one
  lock. `GitHubConditionalCacheHandler` sits on the read client only and replays a stored 200 on a 304.
- **Gauge (Task 11).** `daedalus.github.ratelimit.remaining`, a `Gauge<long>` on meter `daedalus.github`, recorded by
  `GitHubRateLimitObserver` from every response that carries the header. Its one tag, `daedalus.github.resource`, goes
  through an allow-list of GitHub's documented resource names.
- **Small fixes (Task 12).** `ProjectApiClient` reads with the web JSON defaults. The `MaxItemsPerCategory` key is gone
  from the Api's `appsettings.json`, so the code default of 15 applies, pinned by an Integration test.
- **Docs (Task 13).** The README section "The GitHub client", the development guide's "External HTTP APIs", and roadmap
  rows 2.10 and 2.11.

## The things worth remembering

**1. A test's Red line is a claim, and several were false.** Review found Reds that could not fire: a route-escape
assertion that `Uri` satisfied by itself, a 429 count that the total timeout ended first, a URL parse test with no
mutation that reached its assertion, a cache post-read size check with no test, and a cache test that stayed green
under the very mutation its Red named. Each was found because a reviewer applied the mutation, not because the Red read
well. "Red-verification notes" lists them.

**2. Body-free is not content-free.** The plan's first rule, no response body in an error, was not enough. The
pre-flight found the publisher's new texts named the repository, the auth provider returned an exception's text, and a
URL-parse failure echoed a remote that can carry `user:token@`. The rule became: texts a run shows, and logs on the
publish path, carry no URL, repository slug or exception text (P30). Task 9, Task 13 and the final review each found
one more place it had not reached.

**3. A fix wave can introduce its own defect.** The final fix for M1 added `Rejected()` on top of the `Transport` kind.
`ForWrite` then still appended "It may still have been applied" to a rejected issue or pull request create, so the text
said both "not sent" and "may have landed". The re-review caught it with a probe test. The root fix was a kind of its
own, which an allow-list `ForWrite` skips without a logic change.

## Red-verification notes

Every task report carried a table of Reds, each applied, run and restored, and every review checked it. Reds that did
not fire as written, and what replaced them. Where a literal mutation did not compile under the analyzers, an equivalent
behavioural mutation was used and the assertion it turned red is the same one.

- **Pre-flight K6 to K10.** Five Reds in the plan were wrong: dropping the `>= 500` arm, since 502 falls through to
  `Server` anyway; mapping 404 to a null success in a helper that already does it; the end-to-end replay test's real
  failing assertion; "send the request before the URL is checked", which cannot be written; and the cache write test's
  unstated key. Each was reworded before execution.
- **Task 3.**
  - The truncated-body Red did not fire; the body became valid JSON.
  - Three Reds did not compile: dropping the `exhausted` guard (S1481), ignoring `X-RateLimit-Reset` (CS0019) and
    dropping the 60 s fallback (CA1823 and S1144). They became a never-true compare, a misspelled header name and an
    always-false guard.
- **Task 4.**
  - The Reds renaming `Login`, `Name` and `PullRequest` only gave compile errors; they now bind the property to a
    different JSON name.
  - **The route-escape assertion could not fail.** `Uri` escapes a space itself, so `o w` proved nothing. The owner
    segment became `o#w`, expected as `o%23w`. The generated client cannot be mutated, because the generator output is
    in memory, so this Red was shown with a `Uri` probe and **not verified red against the real generator**. The
    re-reviewer accepted it.
  - The "head declared non-nullable" Red did not change the query, so it was dropped; passing an empty head replaced it.
- **Task 5.** The `Unexpected` mutation hit S3981, so its Red wording was changed to the mutation that ran. The
  malformed `html_url` row cannot go red through the fallback, which led to `d416d14`. Several Task 2 Red lines named
  code that no longer existed and were retargeted in `266e3d8`.
- **Task 7, the 429 count.** The M6 mutation, neutralising the 429 clause, was red only through the timeout path. The
  test used `Retry-After: 120`, longer than the 60 s total timeout, so the call ended as `Timeout` and the `Count == 1`
  assertion stayed green. It could not fail on its own. The fix used `Retry-After: 1`, asserts `RetryAt` within 5 s of
  now plus 1 s, and the count assertion now goes red by itself, "found 4". The M8 doc said `RetryAt` is null; it is now
  plus 60 s.
- **Task 8, the Azure DevOps URL-parse test.** The reviewer's finding was that no Red reached either assertion. The K9
  mutation, "send before the URL is checked", is not implementable, and the one that ran failed by exception on a null
  `Uri`, not on a sent request. The test became a theory with rows `not a url` and a URL carrying `u:SECRET`, with
  `NotContain SECRET` asserted before the exact text, and three Reds that each reach an assertion: append the URL to the
  text, change the text, and send a create with placeholder segments. A direct client test pins
  `MaxErrorBodyBytes = 0`. The log Red did not compile (CA1873 on an inline argument) and used a local variable.
- **Task 9.** A misplaced Red summary above the wrong test was moved back in `7aff7e1`.
- **Task 10.**
  - **The cache post-read size check had no test.** Decompressed chunked bodies have no `ContentLength`, so the
    post-read check is the production guard. Dropping only it stayed green, because the pre-read check also caught the
    case. A test whose content has no computable length (`5559ddb`) now goes red when it is dropped.
  - `A_200_without_an_etag_is_not_stored` reaches its count assertion only after the header assertion, so the shared
    mutation trips the header one. The Red was reworded to store with an empty tag and send `If-None-Match` only for a
    non-empty one. The count assertion is not independently proven.
  - A `ContentLength` assertion was dropped, since buffering sets the length afterwards.
- **Task 11.** No cache-replay test was added to the observer tests: no compiling mutation distinguishes it. The "abc"
  and overflow rows have no Red beyond the `TryParse` itself, and none is claimed.
- **Task 12.** Its Red is the original code: both unit tests failed with `ProjectName` null, and the Integration test
  failed with 50 against 15 before the key was removed.
- **Final review I1, the cache test.** `The_answer_that_is_stored_still_reaches_the_client_whole` read the answer with
  `ReadAsStringAsync`, which re-serialises from the content's own bytes and never touches a consumed read stream. The
  named mutation left it green. Only the 304 replay test went red, by accident. The test now reads through
  `ReadAsStreamAsync` and a `StreamReader`, as the generated client does, and goes red under the mutation, "differ at
  index 0". The reviewer re-ran it in a temporary worktree.
- **The final fix wave.** Each Red was made, run, seen red and reverted. Two did not compile literally: a bare `false`
  in the `IsFailure` check trips Sonar S1125, so a guarded form was used, and dropping the log call became
  `_ = ex.Message.Length`.
