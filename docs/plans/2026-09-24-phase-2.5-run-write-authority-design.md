# Phase 2.5 Design — Run Write Authority

**Date:** 2026-09-24
**Phase:** `2.5`
**Surface:** Backend
**Stage:** phase (one phase, implementation-ready)

## Goal

A manufacture run goes from a written intent to a **real pull request** against an allow-listed
repository, and every step in between is observed live.

- `implement` makes real edits in an isolated per-run workspace.
- The review lenses record `checked[]` and `retrospect` proposes or declines.
- A human approves at the gate, and host code, not a model, commits, pushes and opens the PR.
- Along the way the token budget becomes a real ceiling, and prompt caching cuts the cost of every
  agent loop.

Phase 2.4 proved every run pins what it runs. It also proved that review, retrospect and the gate
are unreachable, because a workflow turn cannot write. Phase 2.4's rulings list that as carried
forward item 1. This phase makes the process reachable end to end and closes Milestone 2's second
definition-of-done criterion.

## Decisions taken in brainstorming (owner, 2026-09-24)

1. **The live proof goes all the way to a real PR.** This builds 2.2's "Option C": host code opens
   the PR after the gate, so no model is in the path that pushes.
2. **The PR targets a dedicated sandbox repository**, `MarcelRoozekrans/daedalus-sandbox`, with a
   tiny C# solution. The owner creates it.
3. **`implement` gets real editing:** workspace-confined file tools, not only Roslyn-offered code
   actions. Phase 2.4 showed code actions alone end `blocked` for most real work.
4. **Each run gets a fresh, isolated workspace:** a git worktree from a host-managed mirror, on
   branch `manufacture/<run-id>`, with its own Roslyn server, removed when the run ends.
5. **The split is the usual one.** Generic mechanisms go in Thalos.NET, released as 0.11.0.
   Content, hosting and policy stay in Daedalus. Direction recorded 2026-09-21.
6. **Write grants are declared in Daedalus config, which is deploy-reviewed**, not in the process
   YAML. With interval resync, a YAML-declared grant would widen a capability live, without
   review.
7. **Host code writes the PR title and body from recorded facts.** Any agent-written text appears
   only in a section labelled as such.
8. **`MaxTotalTokens` stops the loop before the next model call and counts every token,** cache
   reads included. A turn that finishes within budget keeps its outcome.
9. **Prompt caching is provider-neutral in Thalos core, with a per-provider translator.** Only the
   Anthropic translator is built now.
10. **`AGENT.md` resolves inside the run's workspace,** so an approved change ships in the PR.

## Approach

### Ownership split

| Part A — Thalos.NET 0.11.0 | Part B — Daedalus |
|---|---|
| `StartedBy` on `WorkflowStartRequest`/`WorkflowRun`, persisted | `repository` on `POST /api/workflow-runs`, checked against an allow-list |
| Tool methods may receive the calling `ISecurityContext` | Reads the starter at the endpoint and in `manufacture__start` |
| `IRunWorkspaceProvider` plus a git worktree implementation | `Repositories`, `DataRoot` and `CommitAuthor` config |
| Run-scoped tool sources, plus the `workspace__*` file tools | `WriteGrants` config, the `workspace-writer` role and `WorkspaceWritePolicy` |
| Host action nodes: `action: <name>` and `IWorkflowHostAction` | The `open-pull-request` host action and process v6 |
| The budget checked before each model round trip | `AGENT.md` resolved inside the worktree |
| `PromptCachingChatClient`, the Anthropic translator, cache counts in `TurnUsage` | Per-node usage shown on the run view; the live proof |

Part B starts only once 0.11.0 is released, and pins the released version.

### Run identity and the write grant

- **At start.**
  - `WorkflowRunsController.Start` reads the authenticated user: the principal id from the `sub`
    claim, and their roles.
  - `manufacture__start` reads the same from the calling turn's `ISecurityContext`. That relies on
    Thalos's new ability to bind a tool method parameter to the caller.
  - Both pass `StartedBy` through `ManufactureRunStarter` to Thalos, which stores it in a new,
    nullable `workflow_run` column and never changes it.
  - `StartedBy` is not a run variable, so no node can overwrite it. Phase 2.4's C1 was exactly a
    node overwriting a variable.
- **Per turn.**
  - The `resolveCaller` lambda in `WorkflowNodeDispatcherFactory` reads `run.CurrentNode`,
    `run.StartedBy` and `Thalos:Workflow:WriteGrants`.
  - `WorkflowCaller` keeps the role `workflow`. It adds `workspace-writer` only when all three hold:
    the (process, node) pair is listed, `StartedBy` holds `developer` or `admin`, and the node is a
    task node.
  - It carries the claims `started_by` and `node`.
  - A run with no `StartedBy` never gets the role. This fails closed, including for runs that
    existed before this phase.
- **Policy.**
  - `WorkspaceWritePolicy`, registered under the policy name `workspace-write`, passes for
    `developer`, `admin` or the role `workspace-writer`.
  - `ToolPolicies` binds `workspace__write_*`, `workspace__edit_*` and `roslyn__apply_*` to
    `workspace-write`.
  - It binds `roslyn__set_active_solution` to `developer`. Today that tool is unbound, so a workflow
    turn could call it.
  - `git__*` and `repoaction__*` stay `developer`-only.
- **Audit.** Every allowed write-tool call is appended to the run's event log with node, tool,
  path and the `started_by` id.

### The run's workspace

- **Allow-list.** `Thalos:Workflow:Repositories` holds entries of the shape
  `{ Name, Remote, DefaultBranch, Solution }`. A start naming anything else gets a 422.
- **Start.**
  - The host keeps a bare mirror per repository under `<DataRoot>/mirrors/<name>` and fetches it.
  - It adds a worktree at `<DataRoot>/runs/<run-id>` on a new branch `manufacture/<run-id>`, cut
    from `origin/<DefaultBranch>`.
  - The workspace is ready before the first node dispatches.
- **Durability.** A parked run keeps its worktree on disk across host restarts.
- **Removal.** A worktree is removed after a successful push, or when a run ends before the gate.
  A run that fails after approval keeps its worktree, and `lastError` names the path. A startup
  sweeper removes only worktrees of ended, pre-gate runs.
- **Roslyn per run.**
  - The `roslyn` MCP entry becomes run-scoped, with `${run.workspace.solution}` in its arguments.
  - The server starts when the workspace is ready, not inside a turn, so the solution load does not
    consume a turn's `DeadlineSeconds`.
  - `implement` dispatches only once Roslyn reports ready. If it is not ready within a configured
    timeout, the run fails with an explicit error.
  - The server is disposed with the workspace.
- **`workspace__*` tools.**
  - The tools are `read_file`, `list_files`, `write_file` and `edit_file`, where `edit_file` replaces
    exact text.
  - Every path is canonicalised and must resolve inside the worktree, following symlinks and
    junctions to their final target.
  - Paths under `.git/` are refused.
  - Reads are ungated; writes need the grant.
- **`AGENT.md`.**
  - It resolves to `<worktree>/AGENT.md`, is pinned at start from the freshly checked-out tree, and
    is written back there on an approved resume.
  - It ships in the PR as its own commit, so the standing-instructions change is reviewed on GitHub
    like the code.
  - The worktree-confinement guard replaces 2.4's content-root guard.

### Publishing after the gate

- **Host action nodes, in Thalos.** A node may declare `action: <name>` with `outcomes` and
  `branch`, instead of `agent` and `skill`.
  - A registered `IWorkflowHostAction` runs through the same outbox dispatch as task nodes, so it
    gets the same retry and restart durability.
  - It returns an outcome and variables. No model is involved.
  - The validator rejects:
    - an unregistered action name;
    - an action node that also names an agent or a skill;
    - an action node without `outcomes`.
  - Action nodes are not pinned in the run manifest, because they are deployed code.
- **Process v6.** `publish` becomes an action node:

  ```yaml
  publish:
    action: open-pull-request
    outcomes: [published, failed]
    branch: { published: done, failed: adjudicate }
  ```

  Version 5 stays in history. The `manufacture-publish` skill is no longer referenced by the active
  version.
- **`open-pull-request`, in Daedalus.** It runs in the run's worktree:
  1. **Commit.** Commit the code changes as one commit and an approved `AGENT.md` change as a
     second, authored as `Thalos:Workflow:CommitAuthor`. An empty diff gives the outcome `failed`,
     "nothing to publish".
  2. **Push.** Push `manufacture/<run-id>` with the host's `GITHUB_TOKEN`, through Thalos.Git.
  3. **Open the PR.** Open it through phase 2.1's `IPullRequestPublisher` against `DefaultBranch`.
     Record `pr_url` as a run variable, shown on `GET /api/workflow-runs/{id}`.
- **PR body template.** The body contains:
  - the work intent;
  - the changed files, from `git diff --stat`;
  - the review lenses' `checked[]` items;
  - who approved at the gate, and when;
  - the run id and the process version;
  - an "Agent-written summary" section, labelled as such, holding `implement`'s reported summary.
- **Idempotent.**
  - Before creating a PR, the action asks for an existing open PR on that head branch, and reuses it
    if one exists.
  - It commits only when the tree has uncommitted changes.
  - Pushing the same commits again is a no-op.

  An outbox redelivery therefore never opens a second PR.

### Budget as a ceiling

- **Where the check runs.** The subagent budget travels on the turn request into
  `ThalosAgentRuntime`'s model loop. Before each model round trip, the runtime compares the tokens
  accumulated so far with `MaxTotalTokens`. If the next call would start at or above the ceiling, the
  turn ends with `SubagentBudgetExceeded`, and the error names the round trip and the count.
- **No post-hoc discard.** `SubagentRunner`'s post-hoc check, which discarded a finished turn's
  outcome, is removed. A turn that ends normally keeps its outcome, even when its last call went
  over.
- **Unchanged.** `DeadlineSeconds` is unchanged.
- **Counting.** Every input token counts, cache reads included. The ceiling bounds how much context
  a turn processes, not money; money is cost analytics' job.

### Prompt caching

- **Thalos core, provider-neutral.**
  - **Stable-first prompt order.** The runtime assembles tools, then the system prompt, then
    history. Per-turn content, meaning recalled memories and the variable block, goes after the
    stable part. Every provider's cache needs a byte-identical prefix, so this order helps every
    provider, including those with automatic caching.
  - **`PromptCachingChatClient`.** A `DelegatingChatClient`, wired with `UsePromptCaching()`, places
    Thalos-owned neutral breakpoint hints on the last tool definition, the end of the system prompt,
    and the latest message. It works from message roles alone, never reorders messages, and is
    reusable by any Microsoft.Extensions.AI user.
  - **Cache counts in `TurnUsage`.** `TurnUsage` gains `CacheReadTokens`, from
    `UsageDetails.CachedInputTokenCount`, and `CacheWriteTokens`, from the provider's additional
    counts. `InputTokens` stays the total.
  - **Per-node usage.** Each node's completion event records its usage: input, output, cache read
    and cache write.
- **Thalos.NET.Anthropic.**
  - The Anthropic chat client translates hints to `cache_control` breakpoints, using three of the
    four Anthropic allows.
  - It is configured as `Thalos:Anthropic:PromptCaching { Enabled: true, Ttl: "5m" }`, on by default.
- **Other providers.** They ignore the hints but still benefit from the stable order. Their
  translators are written when they are added.

## Tests

Every assertion names the change that turns it red, and that red is recorded. Boundary tests build
from the shipped configuration, not hand-built principals.

- **Grant.**
  - `implement` of a developer-started run can call `workspace__write_file`.
  - `review` and `retrospect` of the same run cannot.
  - A run with null `StartedBy` cannot.
  - A `WriteGrants` entry for another process or node grants nothing.
  - The shipped `appsettings.json`, in both hosts, binds each pattern.
  - `roslyn__set_active_solution` is denied to `workflow`.
- **Starter.**
  - `POST` records the token's `sub` and roles.
  - `manufacture__start` records the calling turn's principal.
  - No node's variables can change `StartedBy`.
- **Workspace.**
  - Start creates a worktree on `manufacture/<run-id>` from a local bare "remote".
  - An unlisted repository gives 422.
  - `..`, rooted paths, a symlink or junction pointing out, and `.git/` are all refused.
  - The worktree is removed on pre-gate failure, kept on post-approval failure, and removed by the
    sweeper only when eligible.
- **Roslyn readiness.** `implement` does not dispatch before ready. The timeout fails the run with an
  explicit error.
- **Host action.**
  - Unregistered, mixed and outcome-less action nodes are rejected at load.
  - A full pass produces one commit and one PR against a fake publisher.
  - A redelivery still produces one PR.
  - An empty diff gives `failed`.
  - A push failure keeps the worktree.
  - The PR body contains `checked[]`, the approver and the run id, with agent text labelled.
- **End to end.** An Integration test runs v6 with scripted agents through the real endpoint: start
  → implement edits → review → retrospect → gate → resume with apply → `publish` → `Succeeded`. It
  asserts the approved `AGENT.md` change is committed separately in the pushed branch.
- **Budget.**
  - A scripted five-call loop with a budget for two stops before call three.
  - The phase 2.4 regression: a turn that records `blocked` within budget keeps `blocked`.
- **Caching.**
  - The core places hints at the three boundaries and orders the prompt stable-first.
  - The Anthropic translator emits three `cache_control` markers, and none when caching is off.
  - A provider ignoring hints still gets stable order.
  - Cache counts flow from usage to `TurnUsage` to the node event.

### Live proof, the phase's closing step

1. Push the `daily-digest` schedule's `NextRunAt` forward, so it does not fire on host start as it
   did in 2.4.
2. Start one run through `POST /api/workflow-runs` against `daedalus-sandbox`, with a small real
   intent chosen with the owner.
3. Observe and record:
   - `implement` editing through `workspace__*`;
   - the lenses with `checked[]`;
   - retrospect;
   - the run parking at the gate;
   - the owner approving and resuming over HTTP;
   - `publish` opening a real PR;
   - the run reaching `Succeeded`.
4. Record tokens per node and the cache-read share, against phase 2.4's 737,634-token `implement`
   turn.

## Open Questions

Each is settled early in the plan, by a spike or by reading the code, before dependent tasks.

1. **Roslyn staleness.** Does RoslynCodeLens re-read files changed by `workspace__*` edits, or does
   it need a reload? This is the first Part A task: a spike with a throwaway harness, answered before
   the workspace tools are designed around it.
2. **Run-scoped MCP servers.** Can Thalos's MCP configuration express a run-scoped server with
   argument substitution, or does the run-scoped Roslyn source need its own tool-source type? Read
   the MCP source code before choosing.
3. **The Keycloak claim** that carries a stable principal id in this realm: `sub`, or
   `preferred_username`.
4. **Values the owner supplies before the proof:** `DataRoot`, the `CommitAuthor` identity, and the
   sandbox repository itself.

## Out of Scope

These are carried forward:

- cache translators for other providers;
- aggregating agent-turn usage into cost analytics;
- the two hosts both syncing the shared content tables;
- `skills__load` returning the latest skill body instead of the pinned one;
- unifying the standing-instructions escaping with Thalos's escaping;
- concurrent-run limits and Roslyn memory per run.

## Risks

- **An unattended loop can now write files.** The mitigations:
  - confinement to a throwaway worktree;
  - a grant tied to a developer-started run and one configured node;
  - an audit entry per write;
  - the review lenses;
  - a human gate before anything leaves the machine.

  The residual risk is that a prompt-injected `implement` writes harmful changes into the PR. The
  gate and PR review are the controls for that, by design.
- **Per-run Roslyn cost.** A solution load per run adds latency and memory, and several concurrent
  runs multiply it. This is acceptable at today's one-run-at-a-time usage. Concurrency limits are
  carried forward.
- **`GITHUB_TOKEN` scope.** The host action pushes and opens PRs with the host token. It can reach
  only allow-listed repositories, because the action pushes only a run's own `manufacture/<run-id>`
  branch to that run's `Remote`.
- **The PR idempotency lookup** depends on the publisher being able to find an open PR by head
  branch. If phase 2.1's `IPullRequestPublisher` cannot, it gains that query in this phase.
- **Prompt-cache hit rate** depends on the prefix staying byte-stable within a turn. The live proof
  measures it rather than assuming it.

## Amendments from plan research (2026-09-24)

Reading the real code for the plan
(`docs/plans/2026-09-24-phase-2.5-run-write-authority-plan.md`, its "Pre-plan findings" section)
changed the following. **This section overrides the body where they disagree.**

1. **Run-scoped MCP (open question 2).**
   - Today's config cannot express it. There is no argument substitution, and `McpToolSource`
     connects once per host.
   - A new `RunMcpServerRegistry` starts one server per run workspace, and `RunScopedMcpToolSource`
     routes each call by the caller's run claim.
   - The `roslyn` entry keeps a host server for non-run callers, so the Architect and the scout keep
     Roslyn on Daedalus's own solution. A run's turns reach only their own server, so the grant
     cannot let `roslyn__apply_*` edit Daedalus itself.
2. **Keycloak principal (open question 3).**
   - The id is `sub`. It is not stable today, because the realm users have no fixed `id` and the
     AppHost's Keycloak has no data volume. Fixed user ids are added to the realm.
   - The realm has no `developer` role, so only `admin` can start a run that is granted writes.
3. **Workspace before first dispatch.** `OrmWorkflowStore.StartAsync` creates the run id and queues
   the first dispatch in one transaction. `WorkflowStartRequest` therefore gains a caller-supplied
   `RunId`, so the worktree exists before dispatch.
4. **The budget check** cannot sit in `RunModelLoopAsync`, because the round trips happen inside
   MAF. It is a chat client placed directly over the provider.
5. **The approver.** Nothing records who resumed a run. `ResumeAsync` gains the resuming principal,
   which is a breaking Thalos change.
6. **`checked[]` is never stored,** because `ReviewLensRunner` returns only the last lens pass.
   Review evidence goes to a host-written, append-only run-record table. The per-write audit
   entries go there too.
7. **A separate `AGENT.md` commit** needs path-scoped commits, because the Thalos.Git commit stages
   everything today. Thalos.Git gains that, a diff stat, and an open-PR lookup by head branch.
8. **Failure after approval.** Branching to a failed terminal never sets `last_error`, so push and
   PR failures are node failures, not the `failed` outcome. An empty diff stays the `failed`
   outcome.
9. **Worktree removal** happens after a successful push **and** PR, not after the push alone.
10. **Authority must not travel in node-writable variables** — the phase 2.4 C1 lesson.
    - `AGENT.md` is write-protected from `workspace__*`, so the gate stays the only way to change
      it.
    - The work intent is pinned at start.
    - `summary`, which the PR body quotes, may be set only by the implement node.
11. **Stable-first order.** Recalled memories move from the system prompt to after the history.
    That is a breaking change to where memories appear.
12. **Thalos 0.11.0 carries three breaking changes:** the `ResumeAsync` request, the budget
    semantics, and memory placement. The release PR's title and body list all three, so the squash
    commit carries them.
13. **Live-proof preconditions.**
    - At the shipped `DetachedRuns:MaxTotalTokens` of 150,000, `implement` cannot finish; it was
      measured at 358,703 and 737,634 tokens. The proof raises it with an uncommitted AppHost
      `.WithEnvironment("DetachedRuns__MaxTotalTokens", ...)` line.
    - The AppHost's `github-token` needs repo scope on `daedalus-sandbox`.
