## What this phase actually produced

A durable workflow engine with four primitives — sequence, branch, loop-back, gate — surviving a
full process-tree kill and resuming over an authenticated REST boundary. The engine lives in
`Thalos.NET.Workflow`/`.Orm`; Daedalus holds only hosting glue. Built on `ZeroAlloc.ORM` and
`ZeroAlloc.Outbox.Orm` rather than EF Core, which makes 2.2 the pilot for Milestone 3's data-layer
migration.

## The three things worth remembering

**1. The roadmap's premise was false, and a spike proved it before any code was written.**
Phase 2.2 was scoped as "compose `ZeroAlloc.StateMachine`". Its entire runtime assembly is seven
attribute types and zero non-attribute types, so a process shape can never be loaded from data.
`ZeroAlloc.EventSourcing` has no step or branch vocabulary; `ZeroAlloc.Saga` enforces a contiguous
linear order with neither loops nor branching. The whole ZeroAlloc thesis is compile-time
resolution, so a runtime-interpreted engine is its negation, not a missing feature. Writing the
engine was the conclusion, not the starting assumption.

**2. The signature defect of this phase was prose, not code: nine instances of a sentence
crediting one mechanism with a guarantee a different mechanism actually provided.** One landed
inside the commit that fixed three others. One landed in the process file written to demonstrate
the phase. The ninth landed in the close-out itself — ROADMAP and STATE described the end-to-end
restart proof as if it had run process version 2, when every live run executed version 1, whose
`publish` node pointed at a different agent and declared no `outcomes`. That one reached `main`
before it was caught and needed PR #271 to repair.

The review lens that found them generalises: **treat every mechanism claim as an assertion to be
checked.** It works on documentation exactly as it works on test assertions. This is the same
defect class `CLAUDE.md` already warns about under "Tests that pass for the wrong reason" — prose
passing for the wrong reason is the same failure wearing different clothes.

**3. Four correct fixes shipped in Part B with nothing that would catch their removal** — a budget
decorator whose wiring nothing tested, a CLI config line whose deletion nothing caught, a gateway
registration removable with all ten tests still green, and a `.csproj` glob whose only detector was
the crash it then disabled. The habit that closes this: for every control added, name what turns
red if it is removed, and verify it by actually removing it.

## Where the process caught what a human reviewer would not have

- The **falsifiability demand** on a single test exposed a latent bug that two reviews and the
  controller had already approved in writing: single-statement activation self-conflicts against a
  partial unique index, because PostgreSQL checks uniqueness per row rather than at statement end.
- The **whole-branch review** found that `StartAsync` never enqueued the first dispatch. Every
  task-scoped test had hidden it by hand-constructing the message — the defect lived only in the
  seam between tasks, where a task-scoped diff review is blind by construction.
- **Decompiling the packages instead of trusting our own composition doc** found that the
  documented `AddOutbox().WithOrm()` wiring would have last-wins-replaced the store the live
  RepoDigest poller resolves, stopping production. The doc's first real consumer found it would
  break production, which is the doc working in the only way that counts.
- A ruling **blocked its own author's final fix**: content-hash immutability refused a same-version
  content change. The resolution was to bump to version 2 rather than widen the rule.

## Carried forward

1. The `AGENTS.md` self-improvement loop is trapped in `RalphPromptTemplateBuilder`; it must move
   before phase 2.5 deletes Ralph.
2. No "start a workflow run" surface exists in Daedalus. Task 11's proof used a throwaway console
   harness calling `OrmWorkflowStore.StartAsync` directly.
3. **Process version 2 has never been executed anywhere.** It is proven to load, validate and
   activate; never to run. Its first execution will be a deliberate act.
4. `implement` still declares no `outcomes`, so it completes on any turn output — the same hole
   that was closed for `publish`. Closing it means a version 3 and a skill edit.
5. `FetchPendingAsync` has no `FOR UPDATE SKIP LOCKED`, so multi-instance duplicate dispatch stays
   open. The entire mitigation is batch-size 1 plus one line in one `appsettings.json`, guarded by
   configuration assertions rather than by demonstrated behaviour.
6. `ProcessDefinitionSyncHostedService` also runs activation on every API boot, so two replicas
   booting together race. Same mitigation, same limitation.
7. `OrmProcessDefinitionStore` has no `catch` anywhere — a Thalos-side defect. Daedalus guards its
   own host locally; the deeper fix belongs upstream.
8. `ZeroAlloc.ORM`'s `__zaorm_migrations` silently skips a colliding version number. Worth filing
   upstream; guarded here by a test that applies both chains to one database and asserts specific
   tables exist.
9. Cross-node handoff via `memory__remember`/`recall` does not work at a live run's latency —
   every `AgentMemories` row observed stayed `IndexPending = true`, so semantic recall had nothing
   to search.
10. `Daedalus.Tests.Playwright.Browser` was never run against this work.
11. `main` is not `dotnet format` clean — roughly 130 pre-existing files.

## Cost of the honest limit

Reaching `Succeeded` proves each node called the outcome tool its schema demanded. It does not
prove the work was real. The successful run demonstrates the gap rather than papering over it:
`review`'s `approved` outcome almost certainly came from a documented fallback rather than a
reading of `implement`'s output, because semantic recall was empty. Phase 2.3's per-role memory
scoping is where that gets addressed.

- Task 2: Ruling: a task node requires BOTH `agent` and `skill`, not either — the implementer had used

- Task 2: cannot-verify 2 resolved. Ruling: models/lenses/quorum are MODIFIERS on a task node, not a

    and nothing executes them until a second chat provider exists.

- Task 3: Ruling: a node with MaxVisits set and no OnExceeded must be rejected at LOAD time in
    ProcessValidator, not only guarded at run time in Advance. The implementer found the hole and
    guarded it correctly at run time, but a runtime-only guard means a file validates clean, a run
    starts, several agent turns are paid for, and only then does the missing onExceeded surface. That
    is exactly the failure load-time validation exists to prevent. The runtime guard stays as defence
    in depth and is now unreachable through the validated path.
    Cost if wrong: a process legitimately wanting maxVisits with no onExceeded would be rejected;
    relaxing it is a one-line change plus its paired test.
- Task 3: Ruling: IWorkflowDispatcher is DispatchAsync of runId, seq, node, ct. The brief specified
    IWorkflowStore member by member but left the dispatcher unspecified — a real plan gap. seq is
    load-bearing rather than decorative: the redelivery defence drops a message whose seq no longer
    matches the run's current_seq, so seq must travel with the dispatched message or that check has
    nothing to compare against. Cost if wrong: Task 4 reshapes one interface before implementing it.

- Task 3: Ruling: WorkflowRun.Visits counts ENTRIES, not completions. The formula Visits+1 > MaxVisits
    is right and unchanged; the counter's documented meaning was wrong. Under the completion reading a
    maxVisits 5 node runs SIX times and the sixth agent turn's result is discarded — the exact waste
    the cap exists to prevent. Both cap tests pass identically under either reading because Advance
    never increments the counter, so no test could have caught this. Docs-only fix in three places,
    including IWorkflowStore.CompleteNodeAsync, because Task 4 implements whichever increment that doc
    describes and the off-by-one becomes unfixable in the decision layer afterwards.
    Cost if wrong: every capped loop runs one iteration short.
- Task 3: Ruling: `terminal:` values restricted at load time to succeeded and failed only. `cancelled`
    is excluded deliberately — cancellation is an operator action through CancelAsync, not a
    destination a process graph may declare. Without this, `terminal: banana` fails a paid run and
    `terminal: running` yields an endpoint the validator counts as terminal that parks the run on
    itself forever. Cost if wrong: a process wanting a cancelled terminal needs a one-row change.

- Task 3: Ruling: THE CAP IS EVALUATED AGAINST THE TARGET OF THE EDGE, NOT THE NODE THAT JUST
    FINISHED. This overrides the brief's mandated evaluation order, which I wrote wrong. Surfaced by
    the re-reviewer as an out-of-scope observation and promoted here because it is a functional defect,
    not a nitpick: under cap-first-on-current-node, `review` completing `approved` on its fifth run is
    redirected to `adjudicate`, so the pipeline DISCARDS AN APPROVED RESULT and sends passing work to
    adjudication purely because it landed on the last allowed iteration. The cap exists to bound a
    loop, not to pre-empt a successful exit. New order: gate, resolve the edge, cap-check the resolved
    target, terminal. Traced against the fixture: approved-on-fifth now reaches `gate`; rejected-on-
    fifth still trips the cap one hop later when `implement` resolves back to `review`, so the loop
    stays bounded at five. Cost if wrong: the cap fires one hop later than a reader might expect, and
    the two existing cap tests needed their setup adjusted — a new test now pins the motivating case.
- Task 3: Ruling: terminal casing is case-INSENSITIVE at load, matching the interpreter's ignoreCase
    TryParse. The round-1 fix used an ordinal comparison, which silently turned `terminal: Succeeded`
    — valid and working before that commit — into a validation failure. A validator's job is to reject
    what the interpreter cannot handle, not what it can. Cost if wrong: casing typos load rather than
    failing the file.

- Task 3: Ruling: A GATE CAN NEVER BE LEFT — promoted from an out-of-scope observation because it is
    load-bearing and two later tasks build on it. Advance parks whenever node.Await is not null and
    consults neither run.Status nor run.AwaitingSignal, so after ResumeAsync clears the signal the
    next Advance parks again and the gate's `next` edge is unreachable. The approval gate, one of the
    four primitives and the thing phase 2.4's process parks on before publishing, is a one-way door.
    WorkflowEventKind.Resumed exists and is produced by nothing, which is the tell.
    Fix belongs in Advance, NOT in the store: a gate with run.Status != Awaiting parks as today; a
    gate with run.Status == Awaiting resolves its outgoing edge and returns kind Resumed. ResumeAsync
    then verifies the signal, flips the status, and defers to the interpreter — so the store never
    learns the graph and the two cannot drift. Cost if wrong: resume routes through one extra Advance
    call per gate, which is free.
- Task 3: Ruling: a node's OnExceeded must not name that same node. ApplyCap returns the redirect
    without re-entering the cap logic and the validator only checked the target exists, so
    `x.onExceeded: x` was accepted and spins forever. Same class as every other rule added here: fail
    the file, not a paid run.

- Task 3: Ruling: A GATE RESOLVES VIA `next` ONLY. The validator currently accepts a gate that also
    carries branch/outcomes, and on resume ResolveBranch would demand a declared outcome — leaving the
    signal-payload-to-outcome mapping as an unstated calling convention Task 4 would have to invent.
    Rather than invent it, forbid the shape. Implement as a load-time rule in TASK 6, which is the
    next task touching validation; Task 4 may assume gates resolve via `next`.
    Cost if wrong: a branching gate would need the rule relaxed plus a defined payload mapping.

- Task 4: Ruling: ADD WorkflowRun.Variables AND THE variables COLUMN. Verified the gap myself: the
    migration has no variables column and WorkflowRun has no such property, yet the design spec
    specifies `variables jsonb` on workflow_run and NodeResult already carries Variables. So nodes
    produce variables today with nowhere to land — a publish node cannot read the branch name a plan
    node chose, and ResumeAsync's payload evaporates into the event log. The omission came from my
    plan's Task 3 interface list, not from the implementer. Merge semantics, not replace: a node
    returning no variables must not wipe what earlier nodes wrote. Retrofitting after the store ships
    would need a migration, so it lands now.
    Cost if wrong: a jsonb column nothing reads until Task 5.

- Task 4: Ruling: DELETE IWorkflowDispatcher FROM THE CORE PACKAGE — my interface design was wrong.
    I ruled its shape in Task 3 as DispatchAsync of runId, seq, node, ct, with no transaction
    parameter. Nothing can therefore join the store's transaction THROUGH that interface, and adding a
    transaction parameter would drag ADO types into Thalos.NET.Workflow, which has no such dependency.
    The honest conclusion is that dispatch is not backend-agnostic: it must enlist in the backend's
    transaction, so it belongs in the .Orm package. The wire contract — WorkflowDispatchMessage and
    the thalos.workflow.node-dispatch type name — becomes PUBLIC there, so Task 8's consumer binds to
    a real type instead of hand-writing a DTO and re-typing a magic string across a process boundary
    where a rename breaks silently with no compile error.
    Cost if wrong: a consumer wanting a non-outbox dispatch backend has no seam and must add one.
- Task 4: Ruling: REVOKE UPDATE on workflow_run_event is DISCHARGED without writing one. Owner
    privileges are unaffected by REVOKE, so the statement would be untested theatre. Append-only rests
    on there being no UPDATE code path, which review can check and did.
- Task 4: Ruling: ResumeAsync's payload lands under the literal key "payload"; now documented in the

- Task 4: Ruling: REORDER ApplyTransitionAsync SO THE XMIN-CHECKED UPDATE RUNS FIRST. The unique index
    on run_id and seq — which I ordered as Minor C — shadows the xmin guard: concurrent completions
    collide on the event INSERT, which ran before the UPDATE, so losers died on PostgresException
    23505 and never reached the guard at all. Measured, not inferred: the concurrency test is 3/3 RED
    run in isolation with --filter and 16/16 green only in full-suite ordering, where scheduling
    happens to serialise the racers enough that losers bail on the seq check first. Full-suite green
    is what hid it. Statement order within a single transaction is free, so reordering costs nothing
    and makes the guard the first thing a loser hits. The index stays; it is correct. 23505 on that
    index is additionally mapped to WorkflowConcurrencyException as defence in depth.
    This regression traces to MY ruling, not the implementer's work.
    Cost if wrong: none identified — the event still lands in the same transaction.
- Task 4: Ruling: FailAsync and CancelAsync become IDEMPOTENT NO-OPS on an already-terminal run.
    Both insert an event at row.CurrentSeq without advancing it, so under the new index a FailAsync
    retry or a CancelAsync on an already-Failed run collides on 23505 — reachable from ordinary
    operator retries. The terminal state is already recorded; re-recording it has no meaning.

- Task 4: Ruling: THE 23505 MAPPING I ORDERED ERASED THE DISCRIMINATOR THAT MADE TWO TESTS
    FALSIFIABLE. Mapping the index collision to WorkflowConcurrencyException — the same type the
    guards throw — means both tests, which assert on type alone, now pass with their guard removed.
    Delete the xmin clause and seven losers collide, get mapped, get caught, and all three assertions
    stay green. Delete the status guard and the resurrection test stays green the same way. My own
    defence-in-depth instruction undid the Step-4 demonstration the brief exists to require.
    Fix is test-only: the mapped exception carries an inner PostgresException, both guards throw with
    none, so asserting InnerException is null on the losers restores the RED. Step-4 must then be
    re-demonstrated and pasted.
    Cost if wrong: none — production behaviour unchanged, the tests simply regain the ability to fail.
- Task 4: Ruling: reorder FailAsync and CancelAsync UPDATE-first too, rather than reword the comment
    claiming the mapping is unreachable. Those two insert before updating TODAY, so two concurrent
    FailAsync calls on a Running run collide and the loser takes 23505 — the comment is false as
    written. Reordering makes it true and closes the trap: if someone later deletes the mapping as
    "unreachable" on the strength of that comment, those methods would leak raw PostgresException.

- Task 6: Ruling: PLACEMENT CONFIRMED. ProcessDefinitionSync and IProcessDefinitionStore belong in

- Task 6: Ruling: the missing DI registration gets added now rather than deferred. AddWorkflowOrm
    already registers OrmWorkflowStore, so leaving OrmProcessDefinitionStore out makes the package
    HALF-WIRED — one call to the only extension the package offers yields a workflow store but no
    definition store, and the host discovers it as a confusing null rather than a clear error.
    ProcessDefinitionSync and IProcessDefinitionSource deliberately stay unregistered there: the sync
    is engine-level and the source is host policy.

- Task 6: Ruling: PLAN AMENDMENT — ADD TASK 6b. ProcessDefinitionSync writes YAML into a table NOTHING
    READS. Both WorkflowNodeDispatcher and OrmWorkflowStore resolve a run's definition from
    WorkflowOrmOptions.Processes, a host-populated in-memory dictionary, so activating a synced
    version does not make it runnable and the hot-reload story is decorative. Same shape as 5b: a
    carrier built correctly with nothing consuming it.
    Populating the dictionary at startup is NOT the fix — a static dictionary defeats the reload the
    sync exists to provide. The dispatcher must resolve through the store, cached on (process,
    version); a pinned version is immutable so the cache is safe and bounded by live versions.
    Spans the dispatcher and the store, both already reviewed, so it gets its own task and review
    rather than being bolted onto 6.

- Task 7: Ruling: ADD A SEQ-GUARDED FAIL. The sweep can DESTROY AN APPROVAL GATE. FailAsync's
    idempotency guard covers only the three terminal states, so a run selected while Running that a
    concurrent dispatcher completes into an Awaiting gate between the SELECT and that run's FailAsync
    passes the guard — and since FailAsync re-reads the row in its own transaction, the xmin check
    passes too. With 500 runs failed sequentially from one snapshot the window is seconds wide. Every
    transition bumps seq, so a seq guard closes it exactly as CompleteNodeAsync's already does.
    FailAsync itself is NOT weakened; other callers legitimately use it.
- Task 7: Ruling: ADD THE PARTIAL INDEX rather than soften the comment. The cap's stated justification
    — that it bounds a sweep's work — is false: workflow_run has only the correlation-key index, so the
    query is a sequential scan plus top-N sort over a table accumulating every run ever started,
    including terminal ones. An index on updated_at where status is Running makes the claim TRUE and
    makes the ORDER BY free. Correcting the comment to claim less would have been the cheaper lie.

- Task 6b: Ruling: MAKE THE IMMUTABILITY PREMISE TRUE — reject a same-version re-sync whose content
    differs. Write-through eviction only fixes staleness WITHIN one process; another instance's cache
    is untouched, so two hosts could execute DIFFERENT GRAPHS for the same pinned version. That
    defeats both properties Task 6 exists to establish — an in-flight run keeping its version, and a
    version staying resolvable while pinned — because both are meaningless if what a version MEANS can
    change. Store a content hash: identical content stays an idempotent no-op, since re-syncing
    unchanged files is the normal startup case; differing content is an error naming process, version
    and the instruction to bump. The test must assert the stored definition is UNCHANGED after the
    rejection — an error return with the row already rewritten would be worse than no check.
    Cost if wrong: an author must bump a version to change a definition, which is the intended
    discipline anyway.
- Task 6b: Ruling: OrmWorkflowStore's required constructor parameter stays required — an optional one
    reintroduces the silent unwired path this task exists to delete. Release notes item, same as the
    ThalosAgentRuntime change in 5b.

- Task 6b: Ruling: DROP `AND is_active` FROM THE DEACTIVATE — the split traded one race for another.
    With that predicate, two concurrent syncs of the same process at DIFFERENT versions leave the
    loser raising an unhandled 23505 out of a Result-returning API: under READ COMMITTED B's snapshot
    predates A's commit, so the newly-active row reads as inactive and `AND is_active` filters it out
    of B's scan entirely — no row means no EPQ re-check to rescue it. The OLD SINGLE STATEMENT DID NOT
    HAVE THIS PROBLEM: its WHERE carried no is_active predicate, so the row stayed in scan, B blocked,
    and the EPQ re-check gave clean last-writer-wins. Dropping the predicate restores that, costs a few
    no-op row versions, and cannot reintroduce 23505 since a deactivate never sets anything active.

- Task 9: Ruling: THE BRIEF'S PINNED VERSIONS ARE STALE AND MUST NOT BE USED AS WRITTEN. It says bump
    ZeroAlloc.Outbox to 2.6.0 and add ZeroAlloc.ORM 1.6.6. But renovate PRs #149 and #150 merged
    BETWEEN the feature merge and the release tag, so Thalos 0.7.0 actually ships against ORM 1.7.1

    built against, not to the numbers the plan recorded weeks earlier — a consumer pinning lower than
    its dependency's own pins invites a resolution conflict that central package management turns into
    NU1109, which this repo treats as an error and cannot suppress.
    Cost if wrong: a version bump to correct, caught immediately at restore.

- Task 9: Ruling: EnsureSchemaOnStartup = false, migrations run explicitly through Daedalus.Migrations.
    Accepted — it sidesteps the 1004 rolling-deploy hazard by construction rather than by procedure.
- Task 9: Ruling: CLOSE THE BUDGET GAP IN DAEDALUS VIA A DECORATOR, not by changing Thalos. Justifying
    the architecture-guard widening is what surfaced it: the factory replicates everything
    SubagentRunExecutor does EXCEPT budget enforcement, since WorkflowNodeDispatcher never sets
    SubagentRunRequest.Budget and falls to Thalos's global default instead of DetachedRunOptions.
    That matters more here than anywhere else in the phase — maxVisits bounds how many TIMES a node
    runs, the budget bounds what a SINGLE TURN may spend, and with it unset the only per-turn control
    is missing from the one path that runs agents unattended, in a loop, with nobody watching.
    Bounding iterations while leaving each iteration unbounded is not a spend control.
    A decorator over ISubagentRunner stamping Budget from the same configuration SubagentRunExecutor
    reads keeps the fix local, needs no Thalos release, and gives both paths one source rather than
    two that can drift. Cost if wrong: a Thalos-side budget hook later supersedes it.
