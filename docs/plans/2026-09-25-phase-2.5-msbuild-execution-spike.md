# Phase 2.5 security spike: does loading/reloading a solution in RoslynCodeLens execute agent-controllable code on the host?

Harness: throwaway console app (`ModelContextProtocol` 2.2.0), launching
`dnx RoslynCodeLens.Mcp --yes -- <sln>` with
`ROSLYN_CODELENS_OPEN_PROJECT_TIMEOUT_SECONDS=600`, exactly as
`src/Daedalus.Api/.mcp.json` does. Readiness = poll `list_solutions` until
`status: "ready"` (per the A1 spike doc). Each vector used a fresh
`dotnet new sln` + `classlib` solution (RoslynCodeLens's `dotnet new sln`
on this box produces `.slnx`, not `.sln`). Every payload only appended to a
uniquely named `marker-<vector>-*.txt` file; nothing else was executed.
Harness and target solutions lived entirely under
`...\scratchpad\msbuild-spike` and were deleted after this file was written.

## MSBuild / design-time-build facts

- RoslynCodeLens 1.0.15 (`%USERPROFILE%\.dotnet\tools\.store\roslyncodelens.mcp\1.0.15\...\tools\net10.0\any\`) ships `Microsoft.Build.Locator` **1.11.2** and `Microsoft.CodeAnalysis.Workspaces.MSBuild` **4.14.0** (from its `.deps.json`), plus `Microsoft.CodeAnalysis.CSharp.Workspaces` and friends. It uses `MSBuildLocator.RegisterDefaults()` (string-confirmed in `RoslynCodeLens.dll`) and `MSBuildWorkspace` (string-confirmed).
- It ships both a `BuildHost-net472` and a `BuildHost-netcore` folder next to the main DLL — this is `Microsoft.CodeAnalysis.Workspaces.MSBuild`'s modern **out-of-process BuildHost**: project evaluation happens in a separate `Microsoft.CodeAnalysis.Workspaces.MSBuild.BuildHost.dll` process, not merely "load an assembly and reflect over MSBuild types" in-proc. That BuildHost is still a **real MSBuild evaluation/execution engine** — it's a different process boundary, not a sandbox with restricted target execution.
- `Microsoft.CodeAnalysis.Workspaces.MSBuild.BuildHost.dll` contains the literal strings `DesignTimeBuild`, `BuildingProject`, `BuildProjectReferences`, `SkipCompilerExecution`, `ProvideCommandLineArgs`, `BuildingInsideVisualStudio` — the standard Roslyn `MSBuildWorkspace` global-property set (`DesignTimeBuild=true`, `BuildingProject=false`, `BuildProjectReferences=false`, `SkipCompilerExecution=true`, ...). These properties are read by *conditions inside* individual SDK targets (e.g. the SDK's own `CoreCompile` skips invoking `csc.exe` when `SkipCompilerExecution=true`); they do **not** gate `BeforeTargets`/`AfterTargets`/`InitialTargets` hooks added by a project or its imports. MSBuild schedules a `BeforeTargets="CoreCompile"` target to run before `CoreCompile` regardless of whether `CoreCompile` itself ends up a no-op — which is exactly why vectors 1, 3 and 4 fired even though the "real" C# compiler is never invoked in this design-time build.
- No restore target participates in this build (vectors 2f and 6 both show no evidence of `Restore` running), and no `dotnet restore`/NuGet network activity was observed for a bad `PackageReference`.
- `CompileDesignTime` and `_CheckForInvalidConfigurationAndPlatform` hooks never fired — RoslynCodeLens's build does not reach those targets, so hooking them is not a viable vector against this server (unlike hooking `CoreCompile`, `ResolveAssemblyReferences`, or `ResolvePackageAssets`, or using `InitialTargets`, all of which fired).
- The RoslynCodeLens `README.md` documents no restore-disabling flag, no "safe"/"readonly" mode, and no target-execution opt-out; `DotnetToolSettings.xml` exposes a single fixed entry point with no relevant CLI switch found. There is no configuration knob that would have blocked any of the vectors above.

## Conclusion

Yes — **agent-written files can execute arbitrary code on the host through this server**, both on the very first solution load and again every time the host calls `rebuild_solution` after a write, because RoslynCodeLens loads projects with a real, out-of-process MSBuild evaluation (`Microsoft.CodeAnalysis.Workspaces.MSBuild` 4.14.0 + `MSBuildLocator`) whose `DesignTimeBuild=true`/`BuildingProject=false`/`SkipCompilerExecution=true` properties only suppress the final `csc.exe` invocation, not the rest of the target graph: a malicious `Directory.Build.props` (or `.targets`, or an edited `.csproj`) with an `<Exec>`, `WriteLinesToFile`, or `RoslynCodeTaskFactory` inline-C# task hung off `BeforeTargets="CoreCompile"`, `BeforeTargets="ResolveAssemblyReferences"`, `BeforeTargets="ResolvePackageAssets"`, or `InitialTargets` runs with full host privileges on both load and reload (vectors 1, 2a-c, 3, 4). Three vectors were empirically closed off: MSBuild's default property-function allow-list blocks arbitrary evaluation-time code (`$([System.IO.File]::WriteAllText(...))`, vector 5), no restore or network call is triggered by a bad `PackageReference` (vector 6), and a referenced third-party analyzer DLL was not loaded by any of the 67 tools tested, `get_diagnostics` included (vector 7, caveat noted above). `CompileDesignTime` and `_CheckForInvalidConfigurationAndPlatform` hooks also never fired, and `AfterTargets="Restore"` never fired because no restore runs at all — so the exploitable surface is specifically the pre-compile target chain (`CoreCompile`, `ResolveAssemblyReferences`, `ResolvePackageAssets`, `InitialTargets`), not every MSBuild extension point. For phase 2.5, this means an unattended agent that can write `.csproj`/`Directory.Build.props`/`.targets` files into the worktree the RoslynCodeLens server has loaded has arbitrary code execution on the host the moment the host calls `rebuild_solution` (or even on the server's first load, if the file already existed) — no separate "execute" step is required.
