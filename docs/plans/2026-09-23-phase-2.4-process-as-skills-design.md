# Phase 2.4 Design — The Process as Skills

**Date:** 2026-09-23
**Phase:** 2.4
**Surface:** Mixed
**Stage:** phase (one phase, implementation-ready)
**Milestone:** 2 — Software Manufacturing
**Depends on:** 2.3 (manufacturing squad, Thalos.NET 0.9.0)
**Roadmap entry:** "The process as skills: the manufacturing steps written as skills rather than code,
including an explicit review stage, so the process can change without a redeploy"

---

## Goal

A manufacturing run can be started through a real surface with a stated intent, runs against a
pinned, immutable snapshot of the process, its skills and its role charters, and proposes
improvements to its own standing instructions that only a human can accept.

## What the roadmap entry already has, and what it does not

The roadmap's wording is **mostly already true**, and this spec does not re-do it:

- The process shape is data — `processes/manufacture.yaml`, hot-synced, content-hash pinned per
  version (phase 2.2).
- Each step's procedure is a skill — `skills/manufacture-implement`, `-review`, `-publish` — and the
  review rubric has been a skill since 2.3 §6.1.

What 2.4 actually owes are four gaps earlier phases handed to it:

1. **Skills are not pinned.** `PostgresSkillStore.UpsertAsync` keeps only the latest body per name.
   A run pinned to process v4 loads whatever the skill says *now*, so a mid-run skill edit silently
   changes an in-flight run. That re-opens the hole 2.2's content-hash immutability closed for the
   graph.
2. **Roles are configuration.** `implementer` and `reviewer` instructions and model live in
   `appsettings.json`, so changing a role is a redeploy. 2.3 §11 deferred charter-as-markdown here.
3. **Nothing starts a run.** Nothing in `src` calls `StartAsync`, so `work_intent` has no producer
   and the reviewer judges changes without knowing what was asked (2.3 carried item 1).
4. **The `AGENT.md` standing-instructions loop lives only in Ralph.** `RalphPromptTemplateBuilder`
   instructs agents to maintain `@AGENT.md`; phase 2.5 deletes Ralph (2.2 carried item 1).

A fifth — no live observation of a reviewer turn, and process v4 never executed — is closed as a side
effect of this phase's live proof, credits permitting (see Tests).

## Decisions taken in brainstorming

| # | Decision | Rejected alternative, and why |
|---|---|---|
| D1 | All four gaps are in scope | — |
| D2 | Start surface is **REST + agent tool** (`POST /api/workflow-runs`, `workflow__start`) | Task-queue intake: that is Ralph's replacement and belongs to 2.5 |
| D3 | Role charters own **prose, description, model and skills; the `Tools` envelope stays in config** | Charter owns tools: a hot markdown edit could hand the reviewer a write tool with no redeploy and no policy check — 2.3's reviewer independence rests entirely on tool absence |
| D4 | `AGENT.md` loop is a **`retrospect` node whose proposal rides the human gate**; only host code writes the file, only on a human request | Unattended host write: a persistent prompt-injection channel into instructions later agents follow. Memory-backed: depends on recall 2.2/2.3 measured unreliable at run latency |
| D5 | Pinning is **at run start**, via an immutable run manifest | Pin at process version: every rubric typo needs a YAML bump, defeating "without a redeploy". Inline skills in the process: kills skill reuse and 2.3's rubric-as-skill |

## Approach

### Ownership split

Following the 2026-09-21 direction that Thalos.NET is the reusable framework: generic mechanism in
Thalos, content and hosting in Daedalus. Part A ships **Thalos.NET 0.10.0**; Part B adopts it — the
same shape as 2.2 and 2.3.

| Piece | Thalos.NET 0.10.0 | Daedalus |
|---|---|---|
| Run manifest | `workflow_run.manifest jsonb NULL` (migration `1004`), written once by `StartAsync`, never updated. `IRunManifestResolver` port consulted at start. `WorkflowRun.Manifest` exposed read-only | Resolver implementation: per task node → role, charter hash, skill hash |
| Content-addressed skills | `ISkillStore.GetAsync(SkillName, ContentHash)`; stores retain (name, hash) history. `InMemorySkillStore` too | `PostgresSkillStore` gains a `SkillVersions` table (EF migration) and retention |
| Role charters | `RoleCharter` document, `IRoleCharterStore`, file loader + sync service mirroring skills. An `IAgentCatalog` that composes `AgentDefinition` = charter (instructions, description, model, skills) + **config-owned tool envelope**. Charter frontmatter naming `tools` is rejected at sync | `roles/implementer.md`, `roles/reviewer.md`; `appsettings.json` keeps each role's `Tools` and drops its `Instructions`; Postgres charter store |
| Start surface | — | `WorkflowRunStarter`; `POST /api/workflow-runs`; `workflow__start` tool; `workflow__*` → `developer` in `Thalos:ToolPolicies` in both hosts |
| Standing-instructions loop | — | `learnings[]` on `implement`'s outcome; `retrospect` node + `skills/manufacture-retrospect`; resume endpoint's `applyStandingInstructions`; `AGENT.md` loaded as a start variable |

**Why the manifest is a column, not a variable.** The variable bag is merged by every node result and
rendered to agents; 2.3 needed a projection decorator in front of it. A pin must be immutable and
invisible to the model — the bag is neither.

**Only the `Squad` roles move to charters in this phase.** `Daedalus Architect`, `scout` and `writer`
stay in configuration. The catalog composes both sources; a role defined in both is a startup
validation failure, not a precedence rule.

### Start

`POST /api/workflow-runs { process: "manufacture", workIntent }` or `workflow__start(work_intent)` →
`developer` policy → `WorkflowRunStarter`:

1. Resolve the process's active version.
2. `IRunManifestResolver` walks that version's task nodes. For each: role through
   `SquadAgentResolver` — so squad-disabled mode pins the fallback agent, **and the manifest records
   `squad_mode`** — then the charter's content hash (config-only agents record `charter: none`), then
   the node skill's content hash.
3. `StartAsync(process, version, correlationKey, startNode,
   { work_intent, standing_instructions: <AGENT.md contents, or empty> }, manifest)`.

Any node failing to resolve means **no run is created**; the endpoint returns 422 naming the node and
the tool returns the same as an error. No partial pin. The correlation key includes a freshly minted
attempt id, per `StartAsync`'s documented global-and-permanent key space.

`WorkflowCaller` holds only role `workflow`, and the detached-run principal holds only `reader`; both
fail `developer`, so neither a run nor a scheduled digest can start a run.

### Dispatch

The dispatcher loads each node's charter and skill **by pinned hash**. A pinned version that cannot be
found fails the node, with the hash in `last_error`; there is **no fallback to latest**, because that
fallback is exactly the drift this phase closes. A run with a `NULL` manifest — v4 runs in flight at
upgrade — keeps latest-wins behaviour and its node events record `pinning: none`, so the difference
is auditable rather than assumed.

### Process v5

```
implement ──changed──▶ review ──approved──▶ retrospect ──proposed|none──▶ gate ──▶ publish ──▶ done
    │blocked              │rejected (maxVisits 5, onExceeded adjudicate)
    ▼                     ▼
 adjudicate           implement
```

- `implement`'s outcome may carry `learnings[]` — build, run and test facts only. The skill carries
  Ralph's rule verbatim in spirit: no status reports.
- `retrospect` runs as `reviewer` — which holds no write tool — and sees `learnings` plus the current
  `standing_instructions`, never `summary` or `rationale`. It reports `proposed` with
  `proposed_standing_instructions` (full replacement text), or `none`. Both branch to `gate`. Its
  output is agent-written and passes through the 2.3 projection like any other value.
- The gate is unchanged. **The write happens in host code at resume.** The resume endpoint accepts
  `{ applyStandingInstructions: bool }`; when true and a proposal exists, the Daedalus resume handler
  writes `AGENT.md` at the configured `Workflow:StandingInstructionsPath` **before** calling
  `ResumeAsync`, in the same human-triggered request. Cancel writes nothing. This avoids a new engine
  node kind: the only thing that ever writes standing instructions is a human's request.
- The write leaves an uncommitted change in the tree, consistent with `implement`'s documented
  behaviour; committing it stays human.

### Retention

A skill or charter version is prunable only when no run in `Running` or `Awaiting` status references
it in its manifest. The latest version of every active document is never pruned.

### Error handling

All expected failures are `Result<T>`; nothing throws for flow control.

| Condition | Response |
|---|---|
| Charter frontmatter declares `tools` | Sync rejects the file; previous version stays active; sync report names the file |
| Charter for a role with no config tool envelope | Rejected at sync; startup validation fails, as `ValidateSquadConfig` does today |
| Role defined both in config `Instructions` and as a charter | Startup validation failure |
| Resolver cannot pin a node | 422 / tool error naming the node; no run row |
| Pinned hash missing at dispatch | Node fails; `last_error` carries name + hash |
| `applyStandingInstructions: true` with no proposal | 409; gate not consumed, run stays parked |
| `AGENT.md` write fails | 500 with cause; `ResumeAsync` not called, run stays parked |

## Tests

Falsifiability is checked **per assertion**; each row names the change that turns it red, and that
change is made during implementation to confirm red before green.

| Assertion | Red when… |
|---|---|
| A skill edited mid-run does not change that run's next dispatch | dispatch loads by name instead of pinned hash |
| A run started after the edit receives the new body | resolver caches, or pins by process version |
| A pinned version is not pruned while a `Running`/`Awaiting` run references it | retention query ignores run status |
| A charter declaring `tools` is refused **and the previous charter stays active** — over a seeded store | sync validator removed |
| The reviewer's composed `AgentDefinition` holds no write-capable tool, built from the **shipped** `appsettings.json` + `roles/reviewer.md`, not a hand-built definition | a write tool added to the reviewer's config envelope |
| `workflow__start` is denied to `WorkflowCaller` and to the detached `reader` principal, resolved from the **built host** | `workflow__*` → `developer` binding removed |
| A start with an unresolvable node creates no run row | resolver failure ignored / partial manifest written |
| `AGENT.md` is not written on cancel, nor on resume without the flag | resume handler writes unconditionally |
| The `retrospect` turn's rendered variables contain no `summary`/`rationale` | projection bypassed for the new node |
| Squad-disabled start records `squad_mode` in the manifest | resolver skips `SquadAgentResolver` |

- **Unit:** Thalos stores, resolver, charter composition, sync validation.
- **Integration:** Orm store manifest round-trip against real Postgres; Daedalus built-host boundary tests; start endpoint; resume handler.
- **Live proof (last task):** start a run through the **real** `POST /api/workflow-runs` against the
  AppHost — no harness — drive implement → review → retrospect → gate, resume with
  `applyStandingInstructions: true`, confirm `AGENT.md` changed and the run reached `Succeeded`. This
  is also the first observed reviewer turn, lens pass and `checked[]`. `MaxTotalTokens` is raised for
  the proof run only, through environment configuration, and measured usage is recorded; budget sizing
  stays carried.

## Out of Scope

- Replacing Ralph's task-queue intake — phase 2.5.
- `publish` opening a real pull request (Option C).
- A second chat provider; the shared configuration repository (parked — pinning makes its provenance
  design easier later, it does not do it).
- Cost aggregation of agent turn usage.
- Tool envelopes as documents (D3).
- Sizing `MaxTotalTokens` properly.

## Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Two stores gaining history changes `ISkillStore`, a public Thalos interface | Breaking change for other Thalos consumers | Additive overload; 0.10.0 release notes; Daedalus is the only known consumer |
| Manifest column added to a live table | Existing runs have `NULL` | `NULL` is defined behaviour (latest-wins + `pinning: none` event) |
| A charter change is hot but a tool change is not — two change cadences for one role | Confusion about what a markdown edit can do | Sync rejects `tools` loudly; charter files carry a header stating the envelope lives in config |
| `retrospect` proposes a wholesale rewrite of `AGENT.md` | Human rubber-stamps a large diff | `GET /api/workflow-runs/{id}` on a parked run returns the proposal as a diff against the current file, so it is visible before resume; the skill still emits full replacement text but restricts content changes to brief, additive edits |
| Tests pass for the wrong reason — this codebase's recurring defect | False confidence | Per-assertion red/green, seeded stores, built-host resolution (table above) |
| No credits for the live proof | Phase closes without end-to-end observation, again | Accepted and stated; the proof is scripted so it runs the moment credits exist |
