# Phase 2.1 Implementation Plan — git write tooling

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give agents branch, commit, push and open-pull-request capability, gated behind the `developer` policy so an unattended run cannot use it.

**Spec:** `docs/plans/2026-09-21-phase-2.1-git-write-tooling-design.md`

**This phase spans TWO repositories.** Tasks 1-4 are in `C:\Projects\Prive\Thalos.NET`; tasks 5-8 are in `C:\Projects\Prive\daedalus`. Each repo gets its own branch and its own PR. Every task states which repo it is in — check before committing, because the default assumption will be wrong half the time.

## Global Constraints

- **Never commit to `main`** in either repository. Check `git rev-parse --abbrev-ref HEAD` before every commit.
- **Thalos.NET must never reference Daedalus.** Not a package reference, not a project reference, not a type. Where something host-specific is needed, Thalos defines the abstraction and Daedalus implements it — never the reverse.
- **Capture the test baseline before changing anything**, per repo, and leave it unchanged except for tests you add. Run tests in the FOREGROUND with an explicit timeout. **Never background a test run** — three agents were lost to that in phase 1.7.
- Central package management in Daedalus: `PackageReference` carries **no `Version`**. `NU1109` is an error and cannot be suppressed.
- Commit message bodies must contain **no nested parentheses** — release-please silently drops the entire commit from the changelog while the workflow still reports success.
- No `claude.ai/code/session_*` URLs.
- **Verify the member, not the type.** Phase 1.8 found interfaces documented with wholly fictional method signatures, `Guid` properties that were not foreign keys, and registered handlers never invoked. Grep the member.
- **No test may be one that cannot fail.** Phase 1.7 found eight passing for the wrong reason, two in guards written to catch exactly that. For every test, name what would break it; demonstrate the security-relevant ones failing.

# Part A — Thalos.NET

Repository: `C:\Projects\Prive\Thalos.NET`. One branch, one PR covering tasks 1-4.

### Task 1: Local git write capability

**Read first:** how Thalos structures a package — `Thalos.NET.Skills` and `Thalos.NET.Channels` are the closest precedents for a self-contained capability with its own abstractions.

- [ ] **Step 1: Decide the package.** A new `Thalos.NET.Git`, or an existing package. Justify it in the report — a new package is a public surface and a release obligation, so it should not be created casually.

- [ ] **Step 2: Define the local git contract** — create branch, commit, push. Document for each: what happens when the branch already exists, whether commit stages anything, and what push does when there is no upstream. State these in XML docs rather than leaving them to be discovered.

- [ ] **Step 3: Implement on LibGit2Sharp.** Daedalus's `GitWorkflowService` is a working reference for LibGit2Sharp usage in this ecosystem — read it for technique, but do **not** copy Daedalus-specific behaviour, and do not reference it.

- [ ] **Step 4: Test against real temporary repositories**, covering the documented edge cases, not just the happy path.

- [ ] **Step 5: Commit.**

### Task 2: The pull-request publisher abstraction

Thalos states the capability; it must know nothing about GitHub, Azure DevOps or any host.

- [ ] **Step 1: Define the abstraction** — enough to open a pull request from a branch with a title and body, returning a result carrying at least the PR identifier or URL.

- [ ] **Step 2: Do NOT implement it.** No GitHub client, no HTTP. Daedalus implements it in Task 6. If you find yourself adding an HTTP dependency to Thalos for this, stop — that is the direction inverting.

- [ ] **Step 3: Commit.**

### Task 3: The `git__*` tool class

**Read `DaedalusRepoActionTools` in the Daedalus repo for the pattern** — `[ThalosToolType]`, `[ThalosTool("name")]`, `[Description]` on parameters. Read it for shape only; it stays where it is.

- [ ] **Step 1: Write the tool class** with `create_branch`, `commit`, `push`, `open_pull_request`.

- [ ] **Step 2: One dependency, no read surface.** `DaedalusRepoActionTools` is deliberately constructed with only `IGitHubWriter`; its own doc comment says pairing read and write in one class would quietly defeat the boundary. Same rule here.

- [ ] **Step 3: Tool descriptions must convey ordering.** An agent that commits without pushing has changed nothing anyone can see; one opening a PR with no branch has nothing to offer. Say so, rather than letting the agent discover it by failing.

- [ ] **Step 4: Test that the class cannot reach a read surface**, and **demonstrate it failing** by temporarily adding a second dependency.

- [ ] **Step 5: Commit.**

### Task 4: Prove the independence, then PR

- [ ] **Step 1: Add a test asserting Thalos references nothing of Daedalus** — no package reference, no project reference, no type. Scan the `.csproj` files and the source.

- [ ] **Step 2: Demonstrate it failing.** Temporarily add a Daedalus reference, observe RED, remove it, confirm a zero-line diff, observe GREEN. This guard exists because the failure is otherwise **silent until someone tries to consume Thalos standalone** — exactly the scenario it protects.

- [ ] **Step 3: Full Thalos test suite, then push and open the PR.**

# Part B — Daedalus

Repository: `C:\Projects\Prive\daedalus`. One branch, one PR covering tasks 5-8. **Tasks 5 onward depend on Part A's PR being merged and a Thalos version being consumable.** If it is not yet published, report that rather than working around it.

### Task 5: One GitHub HTTP client, dispatch preserved

**The hazard:** `PullRequestFactory` is a **multi-platform dispatcher** — it calls `IRepositoryPlatformDetector` and routes to `GitHubPullRequestFactory` or `AzureDevOpsPullRequestFactory`. `RalphLoopOrchestrator` and `WorkspaceOrchestrator` both depend on it. Consolidating across that boundary would silently drop Azure DevOps.

- [ ] **Step 1: Write the dispatch test FIRST**, against current behaviour: a GitHub URL routes to the GitHub factory, an Azure DevOps URL to the Azure DevOps factory. Confirm it PASSES unmodified. This is the guard for everything after it.

- [ ] **Step 2: Add PR creation to `GitHubApi`**, matching its existing conventions — `RepoRef`, `Result<T>`, the `GitHubTokenSource` auth path.

- [ ] **Step 3: Make `GitHubPullRequestFactory` delegate to it.** It keeps its place behind `IPullRequestFactory`; only its internals change. `AzureDevOpsPullRequestFactory` is **not touched**.

- [ ] **Step 4:** Confirm the Step 1 test still passes unchanged and only one GitHub HTTP client remains. Commit.

### Task 6: Implement the publisher abstraction

- [ ] **Step 1: Implement Thalos's pull-request publisher** over the existing `IPullRequestFactory`, so it inherits platform dispatch for free and both GitHub and Azure DevOps work through the agent tool.

- [ ] **Step 2: Test both platforms** reach the publisher correctly.

- [ ] **Step 3: Commit.**

### Task 7: Registration and the authorization boundary

**This is the point of the phase.** Phase 1.9 established that the boundary is enforced by **authorization, not tool naming**: a detached run holds only `reader`, so the authorizer denies every gated tool whatever the agent's tool list contains.

- [ ] **Step 1: Register the Thalos tool class** in Daedalus's agent wiring.

- [ ] **Step 2: Bind `git__*` to the `developer` policy** in `ToolPolicies`, alongside `repoaction__*`.

- [ ] **Step 3: Check EVERY host.** Phase 1.9 shipped with the CLI missing its `repoaction__*` policy — same tools, third layer absent. Enumerate every host configuring `ToolPolicies` and confirm each. Report the list.

- [ ] **Step 4: Test that a detached run is denied**, building the principal from **real configuration**, not by hand. Phase 1.6 found a hand-built principal left a boundary test green while the boundary was gone.

- [ ] **Step 5: Demonstrate it failing.** Temporarily grant `developer` to the detached-run roles, observe RED, restore, confirm a zero-line diff, observe GREEN. A security boundary never seen to fail is not yet a boundary.

- [ ] **Step 6: Commit.**

### Task 8: Verification and close-out

- [ ] **Step 1: Full suite** — unit projects, then Integration and Playwright.Api. Compare against the baseline. No pre-existing failure may change.

- [ ] **Step 2: Confirm the phase goal** — enumerate the `git__*` tools, show each bound to `developer`, and show the detached-run principal denied all of them.

- [ ] **Step 3: STOP before any real write.** Do **not** create a branch, push, or open a pull request against a real remote as a test. That is outward-facing and irreversible. If an end-to-end proof is wanted, report that it is ready and wait — phase 1.9 proved its read path against live GitHub, and the write equivalent needs a human decision about which repository and what it leaves behind.

- [ ] **Step 4: Update ROADMAP and STATE.** Record what was consolidated, what moved to Thalos, and any carried-forward items. Commit and open the PR.
