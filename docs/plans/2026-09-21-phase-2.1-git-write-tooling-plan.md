# Phase 2.1 Implementation Plan — git write tooling

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give agents branch, commit, push and open-pull-request capability, gated behind the `developer` policy so an unattended run cannot use it.

**Spec:** `docs/plans/2026-09-21-phase-2.1-git-write-tooling-design.md`

## Global Constraints

- **Never commit to `main`.** Check `git rev-parse --abbrev-ref HEAD` before every commit.
- **Capture the test baseline before changing anything**, and leave it unchanged except for tests you add. Run the four unit projects individually, in the FOREGROUND with an explicit timeout. **Never background a test run** — three agents were lost to that in phase 1.7.
- Central package management: `PackageReference` entries carry **no `Version` attribute**. `NU1109` is an error and cannot be suppressed.
- Commit message bodies must contain **no nested parentheses** — release-please silently drops the entire commit from the changelog while the workflow still reports success.
- No `claude.ai/code/session_*` URLs.
- **Verify the member, not the type.** Phase 1.8 found interfaces documented with entirely fictional method signatures, `Guid` properties that were not foreign keys, and registered handlers never invoked. If you reference a method, grep that method.
- **No test may be one that cannot fail.** Phase 1.7 found eight that passed for the wrong reason, two of them in guards written to catch exactly that. For every test added, name the change that would break it, and demonstrate at least the security-relevant ones failing.

### Task 1: One GitHub HTTP client, dispatch preserved

**Files:**
- Modify: `src/Daedalus.Agents/GitHub/GitHubApi.cs`, `IGitHubWriter.cs`
- Modify: `src/Daedalus.Infrastructure/Services/CodeAnalysis/GitHubPullRequestFactory.cs`
- Test: alongside the existing CodeAnalysis tests

**Interfaces:**
- Produces: PR creation on `GitHubApi`, consumed by Task 3's tool surface

**The hazard.** `PullRequestFactory` is a **multi-platform dispatcher** — it calls `IRepositoryPlatformDetector` and routes to `GitHubPullRequestFactory` or `AzureDevOpsPullRequestFactory`. `RalphLoopOrchestrator` and `WorkspaceOrchestrator` both depend on it. Consolidating across that boundary would silently drop Azure DevOps.

- [ ] **Step 1: Write the dispatch test FIRST, against current behaviour**

Assert that a GitHub URL routes to the GitHub factory and an Azure DevOps URL routes to the Azure DevOps factory. Run it against unmodified code and confirm it PASSES. This is the guard for everything that follows — without it, consolidation could quietly break one platform and no test would notice.

- [ ] **Step 2: Add PR creation to `GitHubApi`**

Match the existing `GitHubApi` conventions — `RepoRef`, `Result<T>`, the `GitHubTokenSource` auth path. Read the existing methods before writing; do not invent a shape.

- [ ] **Step 3: Make `GitHubPullRequestFactory` delegate to it**

It keeps its identity and its place behind `IPullRequestFactory`. Only its internals change. `AzureDevOpsPullRequestFactory` is **not touched**.

- [ ] **Step 4: Verify** the dispatch test from Step 1 still passes unchanged, and that only one GitHub HTTP client remains. Commit.

### Task 2: Branch creation on the local git surface

**Files:**
- Modify: `src/Daedalus.Application/Abstractions/IGitWorkflowService.cs` and its implementation
- Test: alongside the existing git workflow tests

`IGitWorkflowService` has **zero** mentions of branches today. This is the one genuinely missing capability.

- [ ] **Step 1: Read the existing implementation first.** It uses LibGit2Sharp, not shell git. Match its error handling, its `Result` conventions and how it locates the working copy.

- [ ] **Step 3: Test it against a real temporary repository**, as the existing tests do. Cover: creates a branch; behaves as documented when it already exists; leaves the working copy in the documented state.

- [ ] **Step 4: Run the unit gate, confirm baseline unchanged plus your additions. Commit.**

### Task 3: The agent tool surface

**Files:**
- Create: an `IGitWriteOperations` abstraction and `src/Daedalus.Agents/Tools/DaedalusGitTools.cs`
- Test: alongside `RepoToolBoundaryTests`

**Follow `DaedalusRepoActionTools` exactly** — read it first. It is `[ThalosToolType]`, its methods are `[ThalosTool("name")]`, parameters carry `[Description]`, and it is constructed with **only** `IGitHubWriter`.

**That single-dependency rule is structural, not stylistic.** Its own XML doc says pairing the reader and writer in one class would quietly defeat the boundary. `DaedalusGitTools` must likewise have exactly one dependency and no path to any read surface.

- [ ] **Step 1: Define `IGitWriteOperations`** covering branch, commit, push and open-pull-request. Local git and remote PR creation are different mechanisms — LibGit2Sharp against a working copy versus an HTTP call — so the abstraction must not pretend they are the same.

- [ ] **Step 2: Write `DaedalusGitTools`** with `git__*` tools: `create_branch`, `commit`, `push`, `open_pull_request`.

Tool descriptions must make the **ordering** obvious. An agent that commits without pushing has changed nothing anyone can see; an agent opening a PR with no branch has nothing to offer. Say so in the descriptions rather than letting the agent discover it by failing.

- [ ] **Step 3: Test that the class cannot reach a read surface** — assert its constructor takes exactly one dependency and that no read interface is reachable. **Demonstrate it failing** by temporarily adding a second dependency.

- [ ] **Step 4: Unit gate, commit.**

### Task 4: The authorization boundary

**Files:**
- Modify: `src/Daedalus.Api/appsettings.json` and the CLI equivalent
- Test: `tests/Daedalus.Tests.Integration/Agents/RepoToolBoundaryTests.cs` or a sibling

**This is the point of the phase.** Phase 1.9 established that the boundary is enforced by **authorization, not tool naming**: a detached run holds only `reader`, so the authorizer denies every gated tool whatever the agent's tool list contains.

- [ ] **Step 1: Bind `git__*` to the `developer` policy** in `ToolPolicies`, alongside `repoaction__*`.

- [ ] **Step 2: Check EVERY host.** Phase 1.9 shipped with the CLI missing its `repoaction__*` policy — same tools, third layer absent. Enumerate every host that configures `ToolPolicies` and confirm each one. Report the list.

- [ ] **Step 3: Test that a detached run is denied.** Build the principal from **real configuration**, not by hand. Phase 1.6 found a hand-built principal meant a boundary test stayed green while the boundary was gone.

- [ ] **Step 4: Demonstrate it failing.** Temporarily grant `developer` to the detached-run roles, observe the test go RED, restore, confirm a zero-line diff, observe GREEN. A security boundary never seen to fail is not yet a boundary.

- [ ] **Step 5: Unit gate plus the boundary tests. Commit.**

### Task 5: Verification and close-out

- [ ] **Step 1: Full suite.** Unit projects, then Integration and Playwright.Api. Compare against the baseline captured at the start. No pre-existing failure may change.

- [ ] **Step 2: Confirm the phase goal** — enumerate the `git__*` tools, show each is bound to `developer`, and show the detached-run principal is denied all of them.

If an end-to-end proof against a real repository is wanted, report that it is ready and wait — phase 1.9 proved its read path against live GitHub, and the write equivalent needs a human decision about which repository and what gets left behind.

- [ ] **Step 4: Update ROADMAP and STATE**, recording what was consolidated and any carried-forward items. Commit and open the PR.
