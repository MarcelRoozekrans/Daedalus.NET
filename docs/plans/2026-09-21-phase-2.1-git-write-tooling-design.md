# Phase 2.1 — git write tooling (design)

**Date:** 2026-09-21
**Milestone:** 2 — Software Manufacturing
**Phase:** 2.1, the first phase of the milestone

## Goal

Give agents the ability to branch, commit, push and open a pull request — gated behind the same
authorization boundary phase 1.9 built for `repoaction__*`.

## What the roadmap assumed, and what recon found

The roadmap describes 2.1 as "git write tooling: branch, commit, push and pull-request tools". That
implied greenfield work. Most of it already exists, scattered across three places:

| Capability | Where it lives now | Exposed to agents? |
|---|---|---|
| commit, push, tag, reset | `IGitWorkflowService`, LibGit2Sharp | **no** — used only inside the Ralph loop |
| pull-request creation | `IPullRequestFactory` in the CodeAnalysis area | **no** |
| issue comment, label, close | `IGitHubWriter` via `repoaction__*` | yes, gated behind `developer` |

**Genuinely missing:** branch creation, and an agent-facing surface for any of it.

## The trap that nearly shaped this wrong

The obvious reading is that there are two duplicate GitHub HTTP clients — phase 1.9's `GitHubApi` and
`GitHubPullRequestFactory` — and that 2.1 should fold one into the other. I scoped it that way at first.

That is wrong. `PullRequestFactory` is a **multi-platform dispatcher**: it calls
`IRepositoryPlatformDetector`, then routes to `GitHubPullRequestFactory` or
`AzureDevOpsPullRequestFactory`. `GitHubApi` is GitHub-only. Folding PR creation into `GitHubApi` would
have silently dropped Azure DevOps support from `RalphLoopOrchestrator` and `WorkspaceOrchestrator`,
both live consumers.

The two clients are not duplication. They sit at different levels: `GitHubApi` is a GitHub client,
`IPullRequestFactory` is a platform-agnostic capability. Recording this because the surface reading is
convincing and wrong, and a future phase will be tempted by it again.

## Approach

**Consolidate underneath the dispatcher, then expose.** Platform routing is preserved; the GitHub
client is not duplicated.

### 1. One GitHub HTTP client

`GitHubApi` gains PR creation. `GitHubPullRequestFactory` becomes a thin adapter that delegates to it,
keeping its place behind `IPullRequestFactory`. `AzureDevOpsPullRequestFactory` is untouched, and
`PullRequestFactory`'s dispatch is unchanged.

Net effect: one GitHub HTTP client instead of two, with platform dispatch intact and no consumer
affected.

### 2. Branch creation

The genuine gap. `IGitWorkflowService` has no branch concept at all — zero mentions. Add branch
creation there, on LibGit2Sharp, alongside the existing commit and push.

### 3. The agent tool surface

Two axes, and they must not be conflated:

- **Local git** — branch, commit, push — operates on a working copy through LibGit2Sharp.
- **Remote** — open a pull request — is an HTTP call to a hosting platform.

An agent that can commit locally but not push has changed nothing anyone can see; an agent that can
open a PR without a branch to open it from has nothing to offer. The tools should make that ordering
obvious rather than leaving the agent to discover it by failing.

New tool class, following `DaedalusRepoActionTools`'s precedent exactly:

```csharp
[ThalosToolType]
public sealed class DaedalusGitTools(IGitWriteOperations git)
{
    [ThalosTool("create_branch")] ...
    [ThalosTool("commit")] ...
    [ThalosTool("push")] ...
    [ThalosTool("open_pull_request")] ...
}
```

Prefix: `git__*`.

**The class takes exactly one dependency.** `DaedalusRepoActionTools` is deliberately constructed with
only `IGitHubWriter` and cannot reach `IGitHubReader` or `GitHubApi`, because pairing read and write in
one class would quietly defeat the boundary. The same rule applies here: no read capability, no direct
`GitHubApi` access.

### 4. The authorization boundary — the point of the phase

`git__*` is bound to the **`developer`** policy in `ToolPolicies`, exactly as `repoaction__*` is.

Phase 1.9 established that this boundary is enforced by **authorization, not by tool naming**: a
detached scheduled run holds only `reader`, so the authorizer denies every `git__*` tool regardless of
what the agent's tool list contains. That property is what makes it safe to give an agent write tools
at all, and phase 2.1 must not weaken it.

**An unattended run must not be able to push or open a pull request.** That is the whole reason the
boundary exists.

## Risks

| Risk | Mitigation |
|---|---|
| Consolidation silently drops Azure DevOps | `AzureDevOpsPullRequestFactory` untouched; dispatch unchanged; a test asserts both platforms still route |
| `git__*` reachable from a detached run | A test asserting the detached-run principal fails the `developer` policy for `git__*`, mirroring `RepoToolBoundaryTests` from 1.9 |
| Tool class gains read access later | One constructor dependency, and a test asserting it |
| An agent pushes to a shared branch | Out of scope here, but the tools must not make it the easy default. Branch creation exists so that work lands on a branch |

## Definition of done

- [ ] `GitHubApi` is the only GitHub HTTP client; `GitHubPullRequestFactory` delegates to it
- [ ] `PullRequestFactory` still dispatches GitHub and Azure DevOps, proven by test
- [ ] Branch creation exists on the local git surface
- [ ] `git__*` tools: create branch, commit, push, open pull request
- [ ] `git__*` bound to the `developer` policy, with a test proving a detached run is denied
- [ ] The tool class cannot reach any read surface, with a test proving it
- [ ] Full suite green, no pre-existing failure changed
