# Phase 1.8 — Thalos.NET 0.6.0, docs and architecture diagrams (design)

**Date:** 2026-09-21
**Phase:** 1.8 — the last phase of Milestone 1
**Issue:** [#233](https://github.com/MarcelRoozekrans/Daedalus.NET/issues/233)

## Goal

Make the documentation describe the system that exists, and release Thalos.NET as **0.6.0**.

## Non-goal: the 1.0 tag

Decided 2026-09-21 and recorded on the roadmap. A 1.0 signals API stability, and Milestone 2 will
reshape this framework — phase 2.2's durable workflow engine and 2.3's squad roster will very likely
want changes to `ISubagentRunner` and the agent contracts. Tagging 1.0 immediately beforehand forces a
choice between a fast 2.0 and holding the framework design back to preserve compatibility. Neither is
worth a version number. **1.0 is tagged once Milestone 2 has settled the contracts.**

## The problem, measured

`docs/architecture-diagrams.md` is 1456 lines across 15 sections with 18 mermaid diagrams. It is not
wrong in the way documentation usually rots — it contains **zero** references to
`CSharpFunctionalExtensions` or `FluentValidation`, so it makes no false claims about the pattern
library. The problem is what it omits:

| Term | Occurrences |
|---|---|
| `Mediator` | **0** |
| `IApplicationCommands` | **0** |
| `ZeroAlloc.Results` | **0** |
| `ScheduledRun` | **0** |
| `IScheduleDiagnostics` | **0** |
| `GitHubApi` | **0** |

It documents the architecture as of roughly phase 1.3. Everything phases **1.4 through 1.9** built is
absent: channels and outbox delivery, scheduled runs, subagents, schedule diagnostics, the scout's
GitHub tooling, and the entire Mediator dispatch layer. Meanwhile it opens with the Ralph Loop worker
pipeline, which phase 2.5 retires.

So roughly half the architecture is undocumented, and a good share of what *is* documented is the half
being replaced. A newcomer reading it would form a materially wrong model of the system.

## Approach: restructure, do not append

The additive option — keep the 15 sections, add the missing subsystems — was considered and rejected.
It would leave the document opening with Ralph and ordering the reader's attention by what was built
first rather than by what matters. Section order is itself a claim about importance.

The rewrite is organised around **what the system is now**, with legacy clearly marked as legacy.

### Proposed structure

1. **System context** — Daedalus, Thalos.NET, Rag.NET, AI.Sentinel and the external services, and which
   of them owns what
2. **Solution layout** — the 11 projects and their dependency direction, including `Daedalus.Agents`,
   which does not appear in the current document at all
3. **Domain model** — an ERD covering the entities that actually exist today, including `ScheduledRun`,
   `ScheduledRunExecution`, `AgentMemory`, `AgentMessage`, `AgentSession`, `ChannelConversation` and
   `Skill`, none of which are in the present diagram
4. **Dispatch: commands and queries through the mediator** — replaces the old hand-rolled CQRS section.
   Must show the `internal IMediator` / public `IApplicationCommands` boundary, because that is the
   single most surprising thing about the current design and the thing a newcomer will get wrong
5. **Agent runtime** — `IAgentRuntime`, sessions, memory over pgvector, skills, subagents via
   `ISubagentRunner`
6. **Channels and delivery** — `IChannelAdapter`, the Telegram and CLI adapters, and delivery through
   `ZeroAlloc.Outbox`
7. **Scheduling** — `ScheduledRun`, `NextRunAt` as source of truth, the `BackgroundService` sweeper, and
   why there is deliberately no durable job store
8. **Schedule diagnostics** — `IScheduleDiagnostics`, the nine-verdict model, and the five ways a digest
   dies
9. **The scout and its repository tooling** — `IGitHubReader` / `IGitHubWriter` and the authorization
   boundary, where `repoaction__*` is bound to the `developer` policy and a scheduled run holds only
   `reader`
10. **Data access** — EF Core, `xmin` concurrency, migrations
11. **API surface** — controllers and endpoints as they are now
12. **Technology stack** — the ZeroAlloc libraries actually in use, and a short "not in this codebase"
    note mirroring `CLAUDE.md`
13. **Legacy: the Ralph Loop** — clearly marked, with a pointer to phase 2.5

### What carries over

The Git workflow, Git service architecture, and code-extraction sections are still accurate and are
kept with light edits. Multi-instance worker coordination needs checking against the current claiming
logic before it is kept.

## Thalos.NET documentation

The framework side is thin for something about to be consumed by a manufacturing pipeline: a 391-line
root `README.md` and a 24-line `docs/README.md`, against 11 published packages.

Scope: a per-package overview explaining what each package is for and when to reach for it, the agent
contracts in enough detail to implement against, and a getting-started path. Not a full API reference —
that is what the source and XML docs are for.

## Release

Thalos.NET **0.6.0**. The release notes should say plainly that 1.0 is deliberately deferred and why,
so consumers can read the version as the signal it is meant to be.

## Verification

Documentation cannot be verified by a test suite, which is exactly why this phase is at risk of
producing confident fiction. The rules:

- **Every diagram must be checked against the code it describes.** Name a type, a file or an interface
  that exists. Phase 1.7 found the copilot instructions referencing `RalphLoopService.cs` and
  `ClaimNextTaskAsync`, neither of which exists.
- **Every claim about a package must be checked against `Directory.Packages.props`.** The same audit
  found ~80 lines documenting Polly, which is not a dependency, and a Specification pattern that is not
  present.
- **Mermaid must render.** A diagram that fails to parse is worse than no diagram.
- **State what is NOT there.** Absence cannot be discovered by reading code, so it has to be written
  down. `CLAUDE.md` already does this and it is the cheapest defence against invented architecture.
