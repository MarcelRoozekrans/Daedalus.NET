# Phase 2.5 Roslyn staleness spike (Task A1)

Throwaway harness, run against a `dnx RoslynCodeLens.Mcp` server pointed at a tiny two-project
solution living in a **linked git worktree**, using the exact launch shape
`src/Daedalus.Api/.mcp.json` uses (`dnx RoslynCodeLens.Mcp --yes -- <sln>`,
`ROSLYN_CODELENS_OPEN_PROJECT_TIMEOUT_SECONDS=600`). The harness and the target solution/worktree
lived entirely under the session scratchpad and were never committed; only this finding is.

Tool names below are exactly what the server's `ListToolsAsync` returned (67 tools total); the
five named in the task brief — `list_solutions`, `search_symbols`, `get_diagnostics`,
`get_file_overview`, `rebuild_solution` — all exist with those names.

## Readiness signal

Three back-to-back runs, timing each of (a)-(d):

| Call | Run 1 | Run 2 | Run 3 |
|---|---|---|---|
| (a) `McpClient.CreateAsync` | 4.92s | 3.13s | 3.63s |
| (b) `ListToolsAsync` | 0.05s | 0.03s | 0.04s |
| (c) first `list_solutions` | *(not called)* | 2.70s | 2.68s |
| (d) first `search_symbols("Class1")` | *(not called)* | 0.035s | 0.05s |

(a) and (b) return in low seconds/milliseconds regardless of whether the solution has finished
loading — they only complete the MCP stdio handshake and the tool-list RPC, neither of which
touches the workspace. **(c), the first `list_solutions` call, is the call that actually blocks**:
it took ~2.7s on both runs, consistently longer than (a)+(b) combined would predict if it were
cheap, and its response carries a `status` field per solution (`"status":"ready"` in every run
here, one project). By the time (c) returns, the workspace is fully indexed: (d)
(`search_symbols`) then returns in ~35-50ms with a correct hit, and stays that fast for every
later query in the same session.

**Decision: `readyTool = list_solutions`.** Poll `list_solutions` (with no arguments) until the
target solution's entry reports `status: "ready"`; that is the first observed signal that
doubles as proof of load completion, because the tool itself appears to block until loading
settles rather than returning a `"loading"` status to poll against. (No `"loading"` status was
ever observed in this spike — only `"ready"` — so a caller must budget for `list_solutions`
itself being the slow call, not for polling a fast call repeatedly.)

## Staleness

Two edits were made directly to disk on the linked worktree, exactly as `workspace__write_file`
would (no filesystem watcher setup, no explicit notification to the server):

1. A **new file**, `Lib/Added.cs`, containing `public class AddedBySpike {}`.
2. An **edit to an existing, already-loaded file**, `Lib/Class1.cs`, adding
   `public void SpikeMethod() {}`.

`get_file_overview` was tried first for the edited-file probe but turned out to be the wrong tool
for it: its schema and its actual response (`{"filePath","project","typesDefined","diagnostics"}`)
only ever list *type* names, never members, so it could not show `SpikeMethod` even on a fully
fresh, rebuilt workspace. It is not a usable staleness probe at method granularity. The probe was
corrected mid-spike to use `search_symbols("SpikeMethod")` instead (kept in the harness; the
`get_file_overview` calls were left in place and are included below for completeness).

| Query | Before any reload | After `rebuild_solution` |
|---|---|---|
| `search_symbols("AddedBySpike")` (new file) | **miss** — `{"items":[],"totalCount":0}`, 0.025s | **hit** — `Lib.AddedBySpike` found, 0.011s |
| `get_diagnostics(project="Lib")` | 0 diagnostics, 0.30s (no signal either way — the added file has no errors) | 0 diagnostics, 0.004s |
| `search_symbols("SpikeMethod")` (edit to loaded file) | **hit**, already — `void Class1.SpikeMethod()` found, 0.29s | **hit** (unchanged), 0.002s |
| `get_file_overview("Class1.cs")` | `typesDefined:["Class1"]` only, no method list; 3.81s | `typesDefined:["Class1"]` only, no method list; 0.002s (not a usable staleness probe) |

`rebuild_solution` itself took **2.08s-2.38s** across two full runs ("Rebuild complete. 1
project(s) compiled in 2.1s-2.4s").

Two distinct staleness behaviours came out of this:

- **Edits to a file already part of the loaded workspace are visible immediately, with no
  reload call at all.** `search_symbols("SpikeMethod")` was already a hit on the very first
  post-edit query. The cost of noticing the change is paid lazily by that first query, not
  eagerly: the first `search_symbols`/`get_file_overview` call after the edit took 0.29s-3.81s
  (against a one-file, one-type project), while the *same* calls after `rebuild_solution` took
  0.002s. That gap is consistent with an on-disk file watcher that invalidates and reparses the
  changed document on demand rather than on write.
- **Brand-new files are not picked up at all until an explicit reload**, even though the
  `Lib.csproj` is SDK-style with implicit globbing (`**/*.cs`) and should logically include
  `Added.cs` once the directory is reread. The workspace's project file list is evidently fixed
  at load time and is not re-enumerated on a bare file-watcher tick. `rebuild_solution` fixed
  this in one call (~2-2.4s) and the fix held on every later query — no server restart was needed
  in either full run (`AddedBySpike` and `SpikeMethod` were both hits after `rebuild_solution`
  alone, so the "still stale → restart" branch in the harness never triggered).

## Decision

**`reload = tool:rebuild_solution`.**

- `none` is ruled out: it would leave every newly created file permanently invisible to the
  server for the run's whole lifetime — a real failure mode for an implementer agent that adds
  files, not an edge case.
- `restart` is ruled out as the default: it is strictly more expensive (a fresh (a)+(b)+(c)
  sequence measured at ~2.9s just to reconnect and re-list tools, on top of needing to reopen the
  solution) and, in this spike, never produced a result `rebuild_solution` couldn't already
  produce. Nothing observed required tearing down the process.
- `tool:rebuild_solution` is sufficient and cheap enough (2.08s-2.38s, one call, no process
  restart) to run before or after write-bearing turns without materially changing the run's
  latency budget, and it is what B9 should configure as the reload step whenever the file set
  a node just wrote to may include new files (the common case: an implementer agent creating new
  source files is not unusual).

## Worktree

**A linked worktree loads normally.** `git worktree add ../wt -b spike/1` was created from the
throwaway target repo; `wt/.git` is confirmed to be a plain file (not a directory,
`PSIsContainer: False`) containing `gitdir: .../target/.git/worktrees/wt`, i.e. the standard
linked-worktree layout. `dnx RoslynCodeLens.Mcp --yes -- <wt>/Spike.sln` opened that solution
without any special handling: `list_solutions` reported `status: "ready"`, `projectCount: 1`, no
`skippedProjects`, and `search_symbols("Class1")` found the one type in `Lib/Class1.cs` under the
worktree path. No worktree-specific failure or degradation was observed anywhere in the spike.
