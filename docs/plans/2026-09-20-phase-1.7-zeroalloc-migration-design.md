# Phase 1.7 — Daedalus ZeroAlloc migration (design)

**Date:** 2026-09-20
**Phase:** 1.7
**Roadmap row:** `docs/planning/ROADMAP.md`
**Adoption context:** `docs/plans/2026-09-20-zeroalloc-org-adoption-review.md`

## Goal

Remove `CSharpFunctionalExtensions` and both `FluentValidation` packages from Daedalus, replacing
them with ZeroAlloc equivalents, and replace the hand-rolled CQRS layer with `ZeroAlloc.Mediator`.

**Done means the packages are gone**, not merely unused — `CSharpFunctionalExtensions`,
`FluentValidation` and `FluentValidation.DependencyInjectionExtensions` deleted from
`Directory.Packages.props`, with an architecture test that fails if any returns.

## Non-goals

`ZeroAlloc.Telemetry`, `.Rest`, `.Cache`, `.StateMachine` and the rest of the adoption programme
belong to milestones 2 and 3. This phase already rewrites 151 files; adding new capability on top
would make the diff unreviewable, which is how the cross-cutting truncation defect in phase 1.6
passed two separate reviews.

## Measured scope

Every number below was counted in this tree, and every API was verified by reflecting over the
shipped assembly rather than by reading a description.

| | Count |
|---|---|
| Files using CSFE | 151 — 137 `src`, 14 `tests` |
| CSFE combinator call sites | **48** — 28 `Combine`, 13 `Bind`, 4 `Match`, 3 `GetValueOrDefault` |
| CSFE `Maybe<T>` uses | **0** |
| Entities on `Entity<TId>` | 9 |
| Value objects on `ValueObject` | 3 |
| FluentValidation files | 11 — 8 validators, 1 action filter, 2 wire-up |
| Commands / queries / handlers | 12 / 2 / 14 |
| Dispatch sites | 21 in `Daedalus.Application`, 2 in `Daedalus.Api` |
| Commands crossing the Api boundary | **8** |

The three `GetValueOrDefault` hits are `Dictionary.GetValueOrDefault`, not CSFE's. They do not move.

**The headline:** 1372 mentions of `Result` but only 48 combinator sites. CSFE is used as a plain
return type, not as a railway-oriented pipeline. This is a volume problem, not a semantic one.

## Migration A — FluentValidation to `ZeroAlloc.Validation`

**Shape change, not a rename.** FluentValidation puts rules in a separate `AbstractValidator<T>`
class; `ZeroAlloc.Validation` puts them in attributes on the model and source-generates the
validator. The 8 validator classes are **deleted**, and their rules move onto the DTOs.

The existing rules are all simple property-level checks with custom messages — `NotEmpty`,
`MaximumLength`, `InclusiveBetween`, `GreaterThanOrEqualTo`. Every one has an attribute equivalent,
confirmed against the shipped assembly's 28 attributes: `NotEmpty`, `MaxLength`, `InclusiveBetween`,
`GreaterThanOrEqualTo`, plus `Must` and `CustomValidation` if anything needs an escape hatch.

```csharp
// before — Daedalus.Application/Validators/CreateTaskDtoValidator.cs
RuleFor(x => x.Title)
    .NotEmpty().WithMessage("Title is required.")
    .MaximumLength(500).WithMessage("Title cannot exceed 500 characters.");

// after — on CreateTaskDto itself
[NotEmpty(ErrorMessage = "Title is required.")]
[MaxLength(500, ErrorMessage = "Title cannot exceed 500 characters.")]
public string Title { get; set; } = "";
```

### Decision: keep the HTTP status at 400

`ZeroAlloc.Validation.AspNetCore` ships an action filter that returns **HTTP 422**. The current
`FluentValidationFilter` returns **HTTP 400** with RFC 7807 `ValidationProblemDetails`, and the
status is not documented as configurable.

**We keep 400.** An internal library swap must not change the external API contract as a side
effect. The filter is retained and rewritten to resolve `ValidatorFor<T>` from DI and build the same
`ValidationProblemDetails` it builds today, so every response byte stays identical. That costs about
50 lines of filter we would otherwise delete, and buys a migration no API client can observe.

This is reversible: adopting the built-in 422 filter later is a deliberate, separately-reviewable
API change rather than a silent consequence of this phase.

### Packages

- Add `ZeroAlloc.Validation.Inject` — emits `AddZeroAllocValidators()` for bulk DI registration
- Add `ZeroAlloc.Validation.Testing` — for the one existing validator test
- **Align the version skew:** `ZeroAlloc.Validation` is 1.7.1 while `.Generator` and `.AspNetCore`
  are 1.5.6. Bring all to one version before use
- `ZeroAlloc.Validation.AspNetCore` stays referenced for `ValidatorFor<T>` even though its filter
  is not used

## Migration B — CSFE `Result` / `ValueObject` / `Entity`

Three moves, because removing the package needs all three. Doing only the `Result` swap would leave
`CSharpFunctionalExtensions` referenced for its base classes — and leave the transitive-pinning
exposure that cost phase 1.5 its end-to-end proof.

### B1. `Result<T>` to `ZeroAlloc.Results` 1.2.2

Mechanical across 151 files. The API covers every member in use, verified by reflection: `Error`,
`Value`, `IsSuccess`, `IsFailure`, `Success`, `Failure`, and the extensions `Bind`, `Combine`,
`Match`, `Map`, `Ensure`, `Tap`, `TapError`, `MapError`.

The shipped assembly reports `AssemblyVersion 1.2.2.0`. This matters: 1.2.1 shipped `0.1.0.0`, a
downgrade that broke assembly binding while every test stayed green, because VSTest's
`PlatformAssemblyResolver` probes by simple name and ignores version. The fix is confirmed present
in the package we are adopting, not merely claimed in a release note.

### B2. `ValueObject` to `ZeroAlloc.ValueObjects` 2.0.7

Three classes: `AnalysisOutcome`, `CodeLocation`, `RepositoryReference`. This is also a shape
change — an attribute plus generator rather than a base class:

```csharp
// before
public sealed class CodeLocation : ValueObject
{
    protected override IEnumerable<object> GetEqualityComponents() { yield return File; ... }
}

// after
[ValueObject]
public sealed partial class CodeLocation
{
    [EqualityMember] public string File { get; }
}
```

The classes must become `partial`. The payoff is real: no boxing, no iterator allocation, AOT-clean
— which milestone 3 wants anyway.

### B3. `Entity<TId>` — hand-rolled, because the org ships no replacement

`ZeroAlloc.ValueObjects` exports `ValueObjectAttribute`, `EqualityMemberAttribute`,
`TypedIdAttribute` and the ULID/UUIDv7/Snowflake cores, but nothing Entity-shaped. Nine entities
derive from CSFE `Entity<TId>`: `ScheduledRun`, `ScheduledRunExecution`, `AgentMemory`,
`AgentMessage`, `BrainstormMessage`, `ChannelConversation`, `Skill`, `TaskExecution`,
`AnalysisIteration`.

Contract to reproduce, taken by reflection over CSFE 3.6.0:

```csharp
public abstract class Entity<TId> : IComparable, IComparable<Entity<TId>>
    where TId : IComparable<TId>
{
    public TId Id { get; protected set; }   // protected setter — EF Core materialisation needs it
    // Equals, GetHashCode, op_Equality, op_Inequality, CompareTo
}
```

Note `Skill : Entity<string>` — the replacement must be generic over `TId`, not hardcoded to `Guid`.

**Characterisation tests come first.** Before the base class is touched, tests are written against
the **current CSFE behaviour** and must still pass afterwards:

- two transient instances (default `Id`) are **not** equal
- two instances with the same non-default `Id` **are** equal
- instances of different types with the same `Id` are **not** equal
- an EF Core proxy compares equal to its unproxied counterpart
- `GetHashCode` is stable across an `Id` assignment round-trip
- `CompareTo` orders by `Id`
- round-trip through `DbContext` preserves identity semantics

Without these, the swap is unfalsifiable — and phase 1.6 already produced two "guards" that could
not fail. Equality underpins EF Core change-tracking, so a silent regression here corrupts writes
rather than throwing.

## Migration C — hand-rolled CQRS to `ZeroAlloc.Mediator` 5.1.1

The architecturally risky one, and the reason the ordering below changed.

### The constraint

`IMediator` is **generated into the consuming assembly and emitted `internal`**, because its members
are derived from the handlers discovered in that assembly — one strongly-typed `Send` overload per
handler. Two assemblies get differently-shaped copies, so neither can be public. Exposing one in a
public signature is **CS0051**, inconsistent accessibility.

Handlers live in `Daedalus.Application`, so the generator runs there and `IMediator` is internal to
`Daedalus.Application`. `Daedalus.Api` cannot reach it at all — not even through the internal seam
the upstream docs prescribe, because that seam would also be internal to `Daedalus.Application`.

Daedalus has **14 public MVC controllers**, which must be public to be discovered.

### The design

Most dispatch is unaffected: 21 of 23 sites are already inside `Daedalus.Application` and use the
internal `IMediator` directly. Only **2 controllers** — `ProjectsController` and `TasksController` —
dispatch commands, covering **8 commands**.

So `Daedalus.Application` exposes a small **public** facade over its internal `IMediator`:

```csharp
// public — Daedalus.Application
public interface IApplicationCommands
{
    ValueTask<Result<ProjectDto>> CreateProjectAsync(CreateProjectCommand cmd, CancellationToken ct);
    // ... 8 members, one per command that crosses the boundary
}

// internal — takes the generated IMediator
internal sealed class ApplicationCommands(IMediator mediator) : IApplicationCommands
{
    public ValueTask<Result<ProjectDto>> CreateProjectAsync(CreateProjectCommand cmd, CancellationToken ct)
        => mediator.Send(cmd, ct);
}
```

Controllers depend on `IApplicationCommands`, never on `IMediator`. Registering an internal
implementation is ordinary DI — the container resolves by type, not by signature.

**Honest accounting:** this facade is a thinner version of the `ICommandHandlerFactory` being
deleted. The migration's payoff is therefore *not* "less abstraction". It is compile-time
zero-allocation dispatch, build-time diagnostics for missing or duplicate handlers, and — the real
prize — the bridge packages.

### Why this unlocks the rest of the programme

`ZeroAlloc.Mediator` ships pipeline bridges: `WithValidation()`, `WithAuthorization()`,
`WithTelemetry()`, `WithCache()`, `WithResilience()`. `WithAuthorization()` uses
`ZeroAlloc.Authorization`, already adopted in phase 1.9 for the detached-run policy boundary.

That means the later adoptions — Telemetry in 2.6, Cache in 2.7, Resilience in milestone 3 — land as
a pipeline registration rather than bespoke cross-cutting wiring. Migration C is the load-bearing
one for the whole programme, which is a second reason to do it carefully rather than quickly.

### Mechanical changes

- Commands become `IRequest<TResponse>`; queries likewise
- Handlers become `IRequestHandler<TRequest, TResponse>`, returning **`ValueTask<T>` not `Task<T>`**
- `ICommand`, `IQuery`, `ICommandHandler`, `IQueryHandler`, `ICommandHandlerFactory`,
  `IQueryHandlerFactory` and `CommandQuery.cs` are deleted — 8 abstraction files
- Add `ZeroAlloc.Mediator.Generator` as an analyzer reference:
  `OutputItemType="Analyzer" ReferenceOutputAssembly="false"`
- `services.AddMediator()` replaces the hand-rolled factory registrations

**No notification surface exists** — no `Publish(`, no `INotificationHandler` anywhere in `src`. The
upstream defect that killed `ZeroAlloc.Saga` in phase 1.5, where generated `Publish` ignores
DI-registered `INotificationHandler<T>`, therefore cannot affect this migration. The bug is real and
still open; it is simply not on this path.

## Ordering — riskiest last

The roadmap records "smallest first". **Executing that literally would be wrong**, and the reason is
worth stating: the principle's actual goal is *riskiest against the most settled tree*, and I had
equated size with risk. Measured, they are inverted. Migration B touches 151 files but is a
mechanical type swap. Migration C touches ~25 files but changes assembly visibility, DI shape,
return types and a public API boundary.

| Order | Migration | Files | Risk |
|---|---|---|---|
| 1 | **A** — Validation | 11 | Low. Isolated; touches nothing the others touch |
| 2 | **B** — Results, ValueObjects, Entity | 151 | Medium. High volume, low subtlety, except the `Entity` equality swap which the characterisation tests pin |
| 3 | **C** — Mediator | ~25 | High. Architectural |

Migration C runs last, against a tree where `Result<T>` has already reached its final type — so the
facade signatures are written once, against final types, rather than written and then rewritten.

Overlap is bounded: the 14 handlers are touched by both B and C. That is unavoidable in either
order, and B's change to them is a type rename.

## Testing strategy

- **Characterisation first for `Entity<TId>`** — see B3. Written against current behaviour, must
  pass unchanged after the swap
- **The full suite runs after every task**, not just the tests for the files touched. Phase 1.6
  produced a regression precisely because a dispatch omitted that instruction
- **No new test may be one that cannot fail.** Recurring across ~14 defects in phases 1.5, 1.6 and
  1.9: a fixture that looks like a guard but is structurally incapable of failing — a colon-free
  token fixture, a truncation test covering only the already-correct category, a fallback test
  comparing a default against the same default. Every test added here states what breaks it
- **An architecture test enforces the goal**: `CSharpFunctionalExtensions` and both
  `FluentValidation` packages must be absent from every `.csproj` and from
  `Directory.Packages.props`, in the same style as the existing `ZeroAlloc.Saga` and
  `ZeroAlloc.Scheduling` ban in `CleanArchitectureTests`
- **API response bytes are asserted unchanged** for at least one validation failure, pinning the 400
  decision above

## Risks

| Risk | Mitigation |
|---|---|
| `Entity<TId>` equality regression corrupts EF Core change-tracking silently | Characterisation tests written first, including a real `DbContext` round-trip |
| Validation status silently becomes 422 | Custom filter retained; response bytes asserted |
| `NU1109` from new transitive deps — `ZeroAlloc.Pipeline` 1.2.2, `ZeroAlloc.Serialisation` 2.4.2 | Pin both explicitly. `NU1109` is an error and not suppressible, so this fails loudly rather than silently — the safe failure mode |
| Mediator's internal `IMediator` blocks a controller | The 8-member facade, designed above. Only 2 of 14 controllers are affected |
| `ValueTask` vs `Task` changes await semantics at 23 dispatch sites | A `ValueTask` must not be awaited twice; reviewed per site rather than mechanically |
| 151-file diff is unreviewable in one pass | B is split into per-project tasks, each independently reviewable |
