# Phase 3.1: the native smoke run of each server target

The first runtime evidence of milestone 3. `Daedalus.Api`, `Daedalus.Cli` and `Daedalus.Migrations` were published
with Native AOT and each was run as far as it got, against the measurement stack. The survey,
`docs/plans/2026-10-17-native-aot-survey.md`, could only count warnings; this records what the binaries do. Phases
3.2 to 3.5 fix what it found, and 3.6 makes the three targets run.

## How it was run

- **Commit:** `ab18c80c` on `phase/3.1-aot-foundation`, on 2026-10-21. Product code was not changed.
- **VM:** the one of the JIT baseline, `docs/plans/2026-10-17-phase-3.1-aot-baseline.md`. .NET SDK 10.0.402, clang
  and zlib from the agent VM's native toolchain.
- **Publish:** the counter's command from `eng/aot/count-warnings.sh`, one target at a time, each with a fresh
  `--artifacts-path` outside the repository:

  ```bash
  dotnet publish src/Daedalus.<Target> -c Release -r linux-x64 -p:PublishAot=true -p:TreatWarningsAsErrors=false \
    -p:WarningsAsErrors= -p:TrimmerSingleWarn=false --artifacts-path <scratch> -tl:off
  ```

- **Stack:** the Postgres and Keycloak of `eng/measure/`, under the harness's own container names and ports. It was
  started by hand, because `stack_up` applies the migrations with `dotnet run`, and the native migration runner is
  one of the targets.
- **Migrations** ran on the host against the empty database, with `ConnectionStrings__daedalus` set.
- **CLI** ran on the host as `measure-cli.sh` runs it: in the directory of the binary, with an open stdin that never
  delivers a line, and Information logging.
- **API** ran as `measure-api.sh` runs it, with its environment variables and host networking. The image was
  `mcr.microsoft.com/dotnet/sdk:10.0`, with the publish directory mounted as `/app`, because no native API image
  exists yet. The binary needs glibc 2.38 and the image has 2.39.
- **Tokens:** the `/api/projects` call would have taken a `dev` token from the realm, as `load-projects.sh` does. No
  run got that far.

## Run results

None of the three targets reached its ready signal. Each failure is listed in the order it was met.

| Target | Got as far as | Failures, in order | Unblocked by |
| --- | --- | --- | --- |
| Migrations | the first EF Core call | M1, EF Core model building | nothing; no config gets past it |
| CLI | `Host.StartAsync` | C1, `.mcp.json` parsing; C2, a DI constructor trimmed | C1: `Thalos__McpConfigPath` |
| API | `AddControllers` in `Program.cs` | A1, `.mcp.json` parsing; A2, MVC application parts | A1: the same setting |

### M1. Migrations: EF Core refuses to build its model

- **Exception:** `System.InvalidOperationException: Model building is not supported when publishing with NativeAOT.
  Use a compiled model.` Exit code 1, 44 ms after start.
- **Top of the stack:**

  ```text
  Microsoft.EntityFrameworkCore.Internal.DbContextServices.CreateModel(Boolean) + 0x1d9
  Microsoft.EntityFrameworkCore.Internal.DbContextServices.get_Model() + 0x1a
  Microsoft.Extensions.DependencyInjection.ServiceLookup.CallSiteRuntimeResolver.VisitCache(...) + 0xca
  ...
  Microsoft.EntityFrameworkCore.DbContext...IResettableService.ResetState() + 0x5f
  Microsoft.EntityFrameworkCore.Internal.DbContextPool`1.Return(IDbContextPoolable) + 0x3f
  Microsoft.Extensions.DependencyInjection.ServiceLookup.ServiceProviderEngineScope.Dispose() + 0x59
  Program.<<Main>$>d__0.MoveNext() + 0x8ed
  ```

- **Predicted by:**
  - IL3050 at `src/Daedalus.Infrastructure/Persistence/ApplicationDbContext.cs:18`, `DbContext(DbContextOptions)`:
    "EF Core isn't fully compatible with NativeAOT";
  - IL3050 at `src/Daedalus.Migrations/Program.cs:27`, `MigrateAsync`: "Migrations operations are not supported with
    NativeAOT";
  - IL2026 in `ApplicationDbContext.OnModelCreating`, `ModelBuilder.ApplyConfigurationsFromAssembly`.
- **The logged stack is from the scope's `Dispose`, not from the first throw.** `Program.cs` holds the scope in a
  `using`, so the pooled context's `ResetState` builds the model again while the first exception unwinds, and its
  exception replaces the first one. The first one was not seen. Building the model throws the same way wherever it
  runs, so it is almost certainly the same failure, in `GetRequiredService<ApplicationDbContext>` or `MigrateAsync`.
- **The workflow engine's migrations,** the ZeroAlloc.ORM half of the runner, were not reached.
- **Owner:** 3.5, which replaces EF Core and its migrations with ZeroAlloc.ORM's `MigrationRunner`.

### M2. Migrations: a failed run usually logs nothing

- **What happens:** the runner exits with code 1 and prints only "Starting database migration". The `LogError` in the
  `catch` reached the console in 2 of 15 runs. `Environment.Exit(1)` ends the process before the console logger's
  background queue writes the line.
- **Why native shows it:** the native runner fails 44 ms after start. The JIT runner, failing on a closed port, logged
  the error in 4 of 4 runs, because the connection attempt took long enough for the queue to drain. Nothing makes the
  JIT path safe; it is only slower.
- **Predicted by:** no warning. It is not an AOT defect.
- **Owner:** **UNOWNED.** Native AOT does not cause it, and no phase rewrites the runner's exit path. It hides every
  failure of the native runner, so it matters to 3.5 and 3.6. The fix: return the exit code from `Main` after the
  host is disposed, instead of `Environment.Exit`, and hold the scope in `await using`.

  application. Either use the source generator APIs or explicitly configure the 'JsonSerializerOptions.TypeInfoResolver'

- **Top of the stack, CLI:**

  ```text

  Daedalus.Agents.DaedalusAgentsServiceCollectionExtensions.<>c__DisplayClass8_0.<AddDaedalusAgents>b__8(ThalosBuilder)
  Thalos.ThalosServiceCollectionExtensions.AddThalos(IServiceCollection, Action`1) + 0xc7
  Daedalus.Agents.DaedalusAgentsServiceCollectionExtensions.AddDaedalusAgents(...) + 0x844
  Daedalus.Cli.CliHostServices.ConfigureServices(IServiceCollection, IConfiguration, IHostEnvironment) + 0x121
  ```

- **Top of the stack, API:** the same `McpConfigFile.Parse`, reached earlier, from
  `DaedalusAgentsServiceCollectionExtensions.ValidateCSharpWriteBindings` at `AddDaedalusAgents`'s boot check.
- **Predicted by:** IL2026 and IL3050 in `Thalos.Mcp.McpConfigFile.Parse(String)`, on

- **Local unblock:** `Thalos__McpConfigPath=/nonexistent/.mcp.json` in the environment. Both callers treat a missing

- **Owner:** 3.2, the source-generated System.Text.Json contexts in Thalos.

### C2. CLI: the DI container cannot find `PostgresConversationMap`'s constructor

- **Exception:** `System.InvalidOperationException: A suitable constructor for type
  'Daedalus.Agents.Channels.PostgresConversationMap' could not be located. Ensure the type is concrete and services
  are registered for all parameters of a public constructor.` "Hosting failed to start", exit code 1. "Application
  started" was not logged.
- **Top of the stack:**

  ```text
  Microsoft.Extensions.DependencyInjection.ServiceLookup.CallSiteFactory.CreateConstructorCallSite(...) + 0x3e9
  Microsoft.Extensions.DependencyInjection.ServiceLookup.CallSiteFactory.CreateExact(...) + 0x181
  ...
  Microsoft.Extensions.DependencyInjection.ServiceProviderServiceExtensions.GetRequiredService[T](IServiceProvider)
  Microsoft.Extensions.Hosting.Internal.Host.<StartAsync>d__14.MoveNext() + 0x450
  ```

- **Why:** `DaedalusChannelsServiceCollectionExtensions.cs:100` registers it with `UseConversationMap<TMap>`, whose
  `TMap` carries no `[DynamicallyAccessedMembers(PublicConstructors)]`. The trimmer kept the type and dropped the
  constructor's metadata.
- **Predicted by:** IL2091 in `Thalos.Channels.ChannelThalosBuilderExtensions.UseConversationMap<TMap>(ThalosBuilder)`,
  on `ServiceDescriptor.Singleton<TService,TImplementation>()`. The survey lists it as
  `ChannelThalosBuilderExtensions.cs(55)`. The API's log has the same warning, so the API would meet this too.
- **Local unblock:** none. The registration is code.
- **Owner:** 3.2, `[DynamicallyAccessedMembers]` on the DI generics.

### A2. API: MVC cannot load its application parts

- **Exception:** `System.IO.FileNotFoundException: Cannot load assembly 'Asp.Versioning.Mvc'. No metadata found for
  this assembly.` Unhandled, container exit code 139. `/health` never answered.
- **Top of the stack:**

  ```text
  System.Reflection.Assembly.Load(String) + 0x70
  System.Linq.Enumerable.SizeOptIListSelectIterator`2.MoveNext() + 0x7c
  ...
  Microsoft.AspNetCore.Mvc.ApplicationParts.ApplicationPartManager.PopulateDefaultParts(String) + 0x63
  Microsoft.Extensions.DependencyInjection.MvcCoreServiceCollectionExtensions.GetApplicationPartManager(...) + 0x5a
  Microsoft.Extensions.DependencyInjection.MvcCoreServiceCollectionExtensions.AddMvcCore(IServiceCollection) + 0x2e
  Microsoft.Extensions.DependencyInjection.MvcServiceCollectionExtensions.AddControllers(IServiceCollection, Action`1)
  Program.<<Main>$>d__0.MoveNext() + 0x538
  ```

  The call is `builder.Services.AddControllers(...)` at `src/Daedalus.Api/Program.cs:146`.
- **Predicted by:** the MVC group as a whole, not by a warning at this call. `Assembly.Load(String)` carries no
  annotation, so nothing warns where it failed. The nearest is IL2026 in
  `MvcServiceCollectionExtensions.AddControllersCore`, on `AddApiExplorer`: "MVC does not currently support trimming
  or native AOT". `Daedalus.Api.csproj` sets `EnableTrimAnalyzer=false`, so no warning names `Program.cs` either.
- **Local unblock:** none. MVC discovers its parts by loading assemblies by name, which Native AOT cannot do.
- **Owner:** 3.4, the controllers to minimal APIs. `Asp.Versioning.Mvc` goes with them.

## What was done locally and not committed

- `Thalos__McpConfigPath=/nonexistent/.mcp.json`, as an environment variable for the CLI and the API runs. See C1.
- The schema was applied with the JIT runner, `dotnet run --project src/Daedalus.Migrations`, as `stack_up` does, once
  the native runner had failed, so the CLI and the API had a migrated database. Neither got far enough to use it.
- Nothing in the repository changed. `eng/measure/` needed no flag: the smoke runs drove the binaries directly.
