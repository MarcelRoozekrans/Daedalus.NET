# Phase 2.3 — The Manufacturing Squad

**Date:** 2026-09-23
**Surface:** Backend
**Milestone:** 2 — Software Manufacturing
**Depends on:** 2.2 (durable workflow engine, Thalos.NET 0.7.0)
**Roadmap entry:** "The manufacturing squad: a role roster, per-role memory scoping so a reviewer
does not inherit the implementer's context, and routing between them"

---

## 1. What this phase is for

Phase 2.2 built a durable pipeline and proved it survives a process kill. It did **not** staff that
pipeline. Every task node in `processes/manufacture.yaml` runs as a single agent, `Daedalus
Architect`, which implements the work and then reviews its own work with full access to its own
reasoning.

Phase 2.2's close-out states the consequence plainly: reaching `Succeeded` proves each node called
the outcome tool its schema demanded, not that the work was real. The successful run's `review`
approval almost certainly came from a documented fallback rather than a reading of `implement`'s
output.

This phase makes review **independent and evidenced**. Independent, so the reviewer cannot read the
implementer's reasoning or edit the code it judges. Evidenced, so an approval that did not look at
the work is visibly hollow in the database rather than indistinguishable from a real one.

It does not make a model diligent. See §12.

## 2. Decisions

| # | Decision | Rationale |
|---|---|---|
| D1 | Handoff travels in `WorkflowRun.Variables`; memory is for learning **across** runs | Variables are transactional and need no embedding index. 2.2 observed memory handoff failing silently. |
| D2 | A role **is** an agent — no `Role` entity, no migration | `AgentMemory.AgentId` and the 2.2 name resolver already exist. YAGNI. |
| D3 | Squad disabled falls back to `Daedalus Architect` for every node, and the run says so | A true rollback keeps the pipeline working; 2.2's proof remains the fallback path. |
| D4 | Memory scoping is two-tier: `AgentId = me` private, `AgentId = null` shared | Mirrors per-agent history plus team-wide decisions. Keeps a reviewer competent without leaking this work's reasoning. |
| D5 | Scoping is enforced **at the tool boundary**, not by instructions or a decorator | The tool exposes no agent parameter, so isolation cannot be asked around. Fails closed. |
| D6 | Roster is `implementer` + `reviewer`; the Architect covers `adjudicate` and `publish` | 2.2 ruled publishing cannot open a real PR, so a `publisher` role would have no permitted capability. |
| D7 | Recall degrades through tiers and records which tier answered | 2.2's silent-empty recall read as "nothing to know". |
| D8 | The reviewer never receives the implementer's narrative | A reviewer reading the account reviews the account. |
| D9 | The review rubric ships as a versioned skill, not as agent instructions | Improving review becomes editing a document, not a redeploy. `ISkillStore` exists since 1.3. |
| D10 | Outcomes carry evidence; approval states what was checked | Makes a hollow approval visible at the time it happens. |
| D11 | Three review lenses, sequential, short-circuiting on first rejection | Adversarial spend concentrates on approvals, which are the ones that ship. |
| D12 | The reviewer runs a **peer-strength** model from a different family | Uncorrelated blind spots. A same-model reviewer shares the implementer's failure modes. |
| D13 | Only a human-facing interactive agent may write a shared (`AgentId = null`) memory | One bad unattended turn otherwise poisons every role's recall permanently. |

## 3. The roster

Two new agents in `Thalos:Agents` alongside the existing three.

| Node | Squad on | Squad off |
|---|---|---|
| `implement` | `implementer` | `Daedalus Architect` |
| `review` | `reviewer` | `Daedalus Architect` |
| `adjudicate` | `Daedalus Architect` | `Daedalus Architect` |
| `publish` | `Daedalus Architect` | `Daedalus Architect` |

**`implementer`** — `Tools: roslyn__*, daedalus__*, memory__*, skills__*, context7__*`.
Model: default. Holds `roslyn__apply_*` and `roslyn__rename_*`. Holds no `git__*` and no
`repoaction__*`; both remain bound to `developer` in `ToolPolicies`, and the `workflow` principal
does not carry that role.

**`reviewer`** — `Tools: roslyn__find_*, roslyn__get_*, roslyn__analyze_*, roslyn__go_to_definition,
daedalus__*, memory__*, skills__*, context7__*`.
Model: peer-strength, different family from the implementer's.

The reviewer's tool list is an explicit read-only enumeration rather than `roslyn__*` minus
exceptions. A reviewer that can edit the code it judges can make its own verdict true, and no
instruction prevents that — only the absent tool does. Enumerating positively means a newly added
`roslyn__apply_something` is absent by default rather than admitted by a wildcard.

### Why not four roles

A `publisher` role would hold no capability it is permitted to exercise: 2.2 ruled Option D, and
publishing a real pull request is deferred to Option C, where host code calls `IPullRequestPublisher`
outside the model's trust path. `adjudicate` is the escape hatch when the visit cap trips — a
judgment call, closest to what the Architect already is. Both earn roles when they earn capabilities.

## 4. The handoff contract

```
implement  writes  { summary, files_touched, rationale }
review     reads   { work_intent, files_touched }
           writes  { verdict, findings[], checked[] }
```

`work_intent` comes from the run's opening variables — what was asked — not from the implementer.
`files_touched` is a **pointer**: the reviewer reads the actual code through `roslyn__*` and judges
delivered against asked.

`summary` and `rationale` are written by the implementer and are **not** passed to the reviewer.
They remain in the run record for humans and for `adjudicate`. Withholding `rationale` while passing
`summary` would be a half-measure: a summary is rationale in compressed form, and a reviewer reading
it evaluates the argument rather than the artifact.

This is the isolation that matters most, because unlike the memory tier it is inspectable after the
fact — the variables are a database row.

## 5. Memory scoping

### 5.1 The two tiers

| `AgentId` | Meaning | Who reads | Who writes |
|---|---|---|---|
| `null` | Project-wide fact | every agent | interactive agents only (D13) |
| set | That agent's own learning | that agent | that agent |

### 5.2 The gap this closes

`PostgresMemoryStore` currently filters:

```csharp
q = q.Where(m => m.AgentId == agentGuid); // pinned to this agent only (owner-wide rows need AgentId = null)
```

Filtering by agent returns **only** that agent's rows and excludes the shared ones. Today the choice
is all-or-nothing: every memory, or one agent's private set. There is no "my own learning plus
shared project facts" query. The comment concedes it.

This phase adds that query shape: `AgentId = @me OR AgentId IS NULL`.

### 5.3 Enforcement at the tool boundary

`memory__recall`, `memory__list` and `memory__remember` resolve the calling agent's identity from the
turn context. The tools expose **no** agent or scope parameter. An agent cannot request another
agent's memories because there is no argument with which to request them.

The rejected alternative — a scoped store decorator — gives equivalent isolation only if every call
path resolves the scoped instance. A missed path fails open and silently: the reviewer simply sees
more than it should and nothing goes red. The tool-boundary form fails closed by construction.

The further rejected alternative — instructing the reviewer not to look — is not a control. Phase 2.2
shipped skills reasoning about tools being "denied by policy" when those tools were simply absent
from the agent; the review recorded it as a wrong-mechanism claim. Prompt guidance is not a boundary.

### 5.4 Tiered recall

Recall degrades rather than returning empty, and records which tier answered:

| Tier | Source | Used when |
|---|---|---|
| 1 | Semantic search over the Rag.NET index | index warm, `IndexPending = false` rows exist |
| 2 | Recency-ordered rows direct from Postgres, filtered to the caller's two tiers | index cold or unavailable |
| 3 | None — agent proceeds on instructions and skill alone | no rows at all |

Phase 2.2 observed every `AgentMemories` row stuck at `IndexPending = true` for the lifetime of a
run, so semantic recall had nothing to search and returned silence. The agent then found nothing
wrong and proceeded. `ReindexPendingMemoriesHostedService` and Ollama (`nomic-embed-text`, wired in
`AppHost`) both exist — the pipeline is not missing, it was not warm inside the run's lifetime.

The tier is written to the turn record. "Tier 2, index cold" is auditable; silence is not.

## 6. Review quality

### 6.1 The rubric is a skill

The reviewer loads a versioned skill through `ISkillStore` rather than carrying its criteria in
`Instructions`. Changing how review works then means editing a document under `skills/`, which is
also the direction phase 2.4 takes for the process as a whole.

### 6.2 Outcomes carry evidence

The `review` node's outcome schema, extending 2.2's closed-set mechanism:

- **reject** requires `findings[]`, each with `file`, `line` and a failure scenario.
- **approve** requires `checked[]` — what was examined and found sound.

An approval with an empty `checked[]` is visibly hollow **in the database**, at the moment it
happens. Phase 2.2's `Succeeded` run is the motivating case: its approval was indistinguishable from
a real one until a human reasoned about it afterwards.

### 6.3 Three lenses, sequential, short-circuiting

The `review` node runs up to three passes, one lens each, stopping at the first rejection:

| Lens | Asks | Defect class it targets |
|---|---|---|
| Correctness | Does it do what was asked; name the input that breaks it | 2.2's `StartAsync` never enqueuing the first dispatch |
| Falsifiability | For each test and control added, what turns red if removed | four unguarded fixes in 2.2 Part B; two non-failing guards in 1.7 |
| Mechanism | For each claim in a comment, doc or name — does the thing it credits enforce it | nine wrong-mechanism instances in 2.2 |

Each lens is chosen because it would have caught defects this project actually shipped. A rejection
stops the pipeline already, so confirming it with two more passes buys nothing; an **approval must
survive all three**. Cost is therefore proportional to quality: wrong work costs one lens, right work
costs three.

This needs **no engine change**. Phase 2.2's invariant is one *transition* per transaction, not one
*turn* per node — a node may take several turns and complete once. This activates the `lenses` and
`quorum` fields that 2.2 parsed and left inert.

Worst case is `maxVisits: 5` × 3 lenses = 15 review turns; the realistic path is one or two
iterations. Every turn is bounded by 2.2's per-turn budget decorator.

## 7. The squad flag

`Thalos:Squad:Enabled`, defaulting to the same pattern as `Thalos:Workflow:Enabled`.

Disabled maps **every** node to `Daedalus Architect` at resolution time. The process file is
unchanged, so `manufacture.yaml` needs no edit to roll back and 2.2's end-to-end proof remains a
working configuration rather than only history.

**The fallback must be loud.** With the squad off, one agent implements and reviews its own work.
That fact is written to `workflow_run_event` on the transition. Otherwise a `Succeeded` run under a
disabled squad is indistinguishable from one with genuine independent review — the exact class of
false assurance this phase exists to remove.

## 8. Models and cost

Per-agent model selection already exists: `AgentOptions.Model` ("provider model id; null →
`Thalos:Anthropic:DefaultModel`") and `AgentOptions.MaxOutputTokens`. Assigning the reviewer a
different model is configuration, not code.

The reviewer runs a **peer-strength** model from a different family (D12). The motivation is
independence rather than thrift: a reviewer sharing the implementer's model shares its blind spots
and will tend to accept exactly the reasoning errors that model is prone to making. Cost control
comes from the visit cap and the budget decorator, both from 2.2.

### 8.1 The pricing defect this phase fixes

`CostAnalyticsService` resolves an unpriced model like this:

```csharp
if (!_pricing.Models.TryGetValue(modelId, out var pricing))
{
    var first = _pricing.Models.FirstOrDefault();
    modelId = first.Key ?? modelId;          // relabels the model
    pricing = first.Value ?? new ModelPricing { 3.0m, 15.0m };
}
```

An unpriced model silently borrows the **first dictionary entry** and renames itself to it.
`ModelPricing.Models` lists `claude-sonnet-4-20250514`, `claude-haiku-4-5-20251001` and
`claude-opus-4-20250514`, while `Thalos:Anthropic:DefaultModel` is `claude-sonnet-5` — which is not
in the list. Every run today is costed at Sonnet 4 rates and reported as Sonnet 4.

This phase prices the models actually in use and makes an unpriced model **fail loudly** rather than
impersonate another. A phase that introduces a second model cannot leave cost attribution silently
wrong, because comparing the two models' cost is the first thing anyone will try.

## 9. Error handling

| Condition | Behaviour |
|---|---|
| Squad enabled, a roster agent missing from the catalog | Fails at **load**. 2.2 collapsed `AgentExistsAsync` and `ResolveAgentIdAsync` into one method precisely so a process cannot validate clean and then fail per node on a live, paying run. |
| Semantic index cold or unavailable | Tier 2 recall; tier recorded on the turn. |
| No memories at all | Tier 3; recorded. Not an error. |
| Unpriced model | Loud failure, not silent substitution (§8.1). |
| Reviewer attempts a write tool | Not reachable — the tool is absent from its list, and `roslyn__apply_*`/`roslyn__rename_*` remain bound to `developer`. |
| Lens 1 or 2 rejects | Short-circuit; remaining lenses do not run. |
| Reviewer returns an approval with empty `checked[]` | Schema violation — the outcome tool rejects it, the turn does not complete the node. |

## 10. Testing

Per-assertion falsifiability, per `CLAUDE.md`. Each control below names the change that turns it red,
and each must be **verified red by making that change**, not by asserting it would.

| Assertion | Turns red when |
|---|---|
| The recall tool surface exposes no agent/scope parameter | someone adds one back — a schema assertion over the tool definition |
| A reviewer recalling against a DB seeded with implementer-private rows receives its own plus shared only | the `OR AgentId IS NULL` filter widens to unconditional, or narrows to exclude shared |
| The `review` node's variables contain `files_touched` and `work_intent` and **not** `summary` or `rationale` | the contract leaks either field |
| The reviewer's tool list contains no `roslyn__apply_*` or `roslyn__rename_*` | a wildcard replaces the positive enumeration |
| With the squad disabled, every node resolves to `Daedalus Architect` **and** the run event records the mode | the fallback stops being recorded |
| An approval with empty `checked[]` is rejected by the outcome tool | the schema stops requiring evidence |
| An unpriced model fails loudly | the silent first-entry substitution returns |
| Lens 2 and 3 do not run after lens 1 rejects | short-circuiting is lost and cost silently triples |

The seeded-database requirement on the second row is load-bearing: a scoping test over an empty
store passes whatever the filter says. That is the vacuous shape this codebase keeps producing —
phase 1.7 alone found eight instances.

## 11. Out of scope

- **Parallel agent dispatch.** Sequential lenses give panel review without it. True parallelism
  breaks 2.2's single-transition-per-transaction invariant and is not needed for this phase's goal.
- **Charter-as-markdown.** Agents stay in configuration. Defining roles as documents belongs to
  phase 2.4, whose stated goal is the process as skills.
- **A shared configuration repository.** Parked with reasoning in `docs/planning/parked-ideas.md`;
  revisit after 2.4. It turns process definitions into a supply chain and needs provenance designed,
  not discovered.
- **A `publisher` role.** Earns its place when Option C gives it a capability (§3).
- **Fixing semantic indexing latency.** Tiered recall makes a cold index survivable rather than
  fatal. Making it warm faster is a separate concern.

## 12. Honest limits

**This phase does not prove the reviewer reviews well.** It proves the reviewer cannot read the
implementer's reasoning, cannot edit the code it judges, must produce evidence to approve, and must
survive three lenses to do so. Those remove the mechanisms by which a hollow approval could pass
*quietly*. A determined model can still produce a plausible `checked[]` for work it skimmed.

What changes is that such an approval is now **visible in the database at the time it happens** —
`checked[]` naming things that do not exist, or three lens passes that raise nothing against a real
defect — rather than reconstructed from a run that merely said `Succeeded`.

**The squad-disabled path is genuinely weaker**, by design, and says so in the run record.

**The three lenses are chosen from this repository's defect history.** They are well-aimed at the
mistakes this project has made, and correspondingly less aimed at mistakes it has not made yet.
