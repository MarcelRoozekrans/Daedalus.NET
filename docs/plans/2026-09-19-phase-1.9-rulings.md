Every decision taken on the user's behalf is recorded here with its reasoning and its cost-if-wrong.

**Six defects in the implementation plan itself were found downstream by implementers or reviewers**
— a test snippet that would not compile, a single-argument constructor that weakened a production
type, a hand-built principal that left the security boundary unguarded, a truncation test that
exercised only the already-correct category, a fallback test that could not fail, and a target file
that contained no logic. The plan was written by the same author as this ledger; that ratio is the
argument for the review loop rather than against it.

**The defect the whole-branch review caught is the one worth remembering.** Task 3 fixed `Truncated`
so it measured the raw page rather than the filtered list, proven with per-category tests that
failed first. Task 5 then wrote a renderer that checked emptiness before truncation and discarded
the flag entirely. Both tasks passed their own reviews. The defect lived only in the seam between
them, which is exactly where a task-scoped diff review is blind by construction.

### Rulings

Ruling PF-1: Task 1 must add `<PackageReference Include="Microsoft.Extensions.TimeProvider.Testing"/>`
  to tests/Daedalus.Tests.Unit/Daedalus.Tests.Unit.csproj before anything else. The package is
  already pinned centrally at 10.10.0 and used by Tests.Unit.Application and Tests.Integration, but
  Tests.Unit does not reference it and has no hand-rolled fake clock. Task 3's tests would not
  compile. Options.Create and NullLogger arrive transitively and need no addition.
  Cost if wrong: one line in a csproj.

Ruling PF-2: Task 4's tests reuse the `Build(...)` helper and `StubHandler` defined in Task 3's test
  file. That is deliberate, not duplication — the plan's "No Placeholders" rule forbids "similar to
  Task N", but these are genuinely the same helper in the same test folder. Task 4's dispatch will
  say to reuse them rather than re-declare, and to put StubHandler in its own file as the plan
  specifies so both classes can see it. Cost if wrong: a duplicate helper a reviewer would flag.

Ruling PF-3: the plan's own self-review already names this and I am upholding it. Task 6's boundary
  tests must resolve Thalos's real tool-name matcher rather than hand-rolling a glob, and report
  BLOCKED if it is unreachable. A bespoke matcher that disagrees with the real one would make every
  boundary assertion in that file lie — and the policy layer is the entire security argument of this
  phase. Do not let an implementer "just write a simple wildcard match". Cost if wrong: Task 6
  blocks and the boundary must be proven another way before the phase can claim it.
