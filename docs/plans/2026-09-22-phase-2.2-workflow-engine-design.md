# Phase 2.2 — durable workflow engine (design)

**Date:** 2026-09-22
**Milestone:** 2 — Software Manufacturing
**Phase:** 2.2, the one genuinely new subsystem in this milestone

## Goal

A durable, resumable process engine with branching, loops and human approval gates, whose process
shape is data rather than code — so the manufacturing process can change without a redeploy, as
phase 2.4 requires.

## The roadmap's premise was wrong, and it was measured, not argued

The roadmap describes 2.2 as "built on `ZeroAlloc.StateMachine` and `ZeroAlloc.EventSourcing`, with
`ZeroAlloc.AsyncEvents` for internal dispatch — these are the substrate, not an add-on." A spike
tested that claim against the shipped assemblies and against real Postgres.

**`ZeroAlloc.StateMachine` cannot define a process shape at runtime.** Its entire runtime assembly —
9 KB — is seven attribute types and nothing else:

```text
CompositeStateAttribute`1   HistoryStateAttribute`1     StateMachineAttribute
StateMachineGroupAttribute  StateMachinePartAttribute`2 TerminalAttribute`1
TransitionAttribute`2
Non-attribute types: 0
```

`TryFire` exists only because a Roslyn generator wrote it onto a specific partial class at compile
time from enum members the compiler resolved statically. There is no path from a database row to a
working machine without re-running the compiler. This is what the library *is*, not a configuration
gap.

**`ZeroAlloc.EventSourcing` is not a workflow engine.** It has no step, branch or transition
vocabulary at all. It is an event store — a good one, with durability proven end to end across a real
process boundary.

**`ZeroAlloc.Saga` fails the same way, and was already rejected here once.** The generator enforces a
contiguous, unique step order — `ZASAGA007: Order values that are not contiguous starting at 1:
[1, 2, 3, 3]` — and empirically supports neither loops nor general branching. An earlier phase reached
the same verdict from a different direction and recorded it in the code:

> "the saga was found undriveable — its generated `Publish` dispatches to a closed list of handler
> types fixed at the saga's own compile time, and never enumerates handlers registered later via DI"
> — `DaedalusSchedulingServiceCollectionExtensions.cs:71`

**The whole ZeroAlloc org shares one thesis** — resolve everything at compile time, allocate nothing,
stay AOT-clean — across all 26 repositories. A runtime-interpreted engine is the negation of that
thesis, not a missing feature. Adding one to `ZeroAlloc.StateMachine` would make the package
contradict its own README and every sibling. Owning the org makes that easy to do, which is the trap.

**So we write our own.** The roadmap's other supporting claim — "`RunStep` is already a hand-written
state machine, so the pattern is not speculative" — also does not carry: `RunStep` is
`Pending` to `Scout` to `Writer` to `Deliver` to `Done`, strictly forward. It is precedent for the
linear shape, not for branching.

## What already exists, and is not being rebuilt

`ScheduledRunExecutionStore` is a working durable pipeline: transactional outbox enqueue, `xmin`
concurrency, idempotent redelivery, failures routed to `FailAsync` rather than thrown. Its own
summary calls it "the correctness core of the saga-free scheduling redesign … the row is the saga's
state, and the `UNIQUE (ScheduleId, OccurrenceAt)` index is the saga's old correlation key, now
enforced by the database rather than by any handler's diligence."

2.2 generalises that pattern from a fixed chain to a graph read from a file. It does not invent it.

## Decisions

| Decision | Choice |
|---|---|
| Where a process is defined | a file in git, synced to the database, hot-reloaded — not a DB-edited graph, not C# |
| Run history | an append-only event log, giving full "why did it do that" audit |
| Data access | **`ZeroAlloc.ORM`, not EF Core** |
| Scope | a new engine only; the RepoDigest scheduling chain is untouched |

**Why ORM rather than EF Core.** Milestone 3 already carries the data-layer migration from EF Core to
`ZeroAlloc.ORM` *because EF Core is the AOT blocker*. Building 2.2 on ORM makes it the pilot for that
migration — proving the path on greenfield tables where a mistake is cheap, instead of discovering it
while rewriting the whole data layer. It is also the precondition for the engine living in
Thalos.NET, which must not drag EF Core into a reusable framework.

The stack is verified, not assumed:

```text
ZeroAlloc.Outbox.Orm 2.6.0 -> ZeroAlloc.Outbox 2.6.0, AdoNet.Async.Adapters 1.4.0,
                              ZeroAlloc.ORM 1.6.6          [no EF Core anywhere]
  OrmOutboxStore.EnqueueAsync(String typeName, ReadOnlyMemory<byte> payload,
                              DbTransaction transaction, CancellationToken ct)
  OutboxOrmMigrations
```

Transactional enqueue against a raw `DbTransaction`. Note this requires **Outbox 2.6.0**; the
solution is pinned at 2.5.2 today.

## The graph model

Two node kinds, two edge kinds. That is the whole vocabulary.

```yaml
process: manufacture
version: 3

nodes:
  plan:
    agent: planner
    skill: writing-plans
    next: implement

  implement:
    agent: backend
    skill: test-driven-development
    next: review

  review:
    agent: reviewer
    skill: code-review
    models:  [opus-5, gpt-5.6-sol, grok-4.6]   # optional panel, fan-out inside the node
    lenses:  [correctness, security, does-it-run]
    quorum:  2
    outcomes: [approved, rejected]
    branch:
      approved: gate
      rejected: implement                       # loop-back is just an edge
    maxVisits: 5
    onExceeded: adjudicate

  gate:
    await: human_approval
    next: publish

  publish:
    agent: publisher
    skill: finishing-a-development-branch
    next: done

  done:
    terminal: succeeded
```

**Four primitives: sequence, branch, loop-back, gate.** A loop is not a construct — it is an edge
pointing backwards. That single decision removes a category of engine complexity.

**A branch selects on a declared outcome, never an expression.** The node declares a closed set of
outcomes and routes each one. There is no `when: run.attempts > 3 && vars.risk == 'high'`. That line
is the difference between a config format and a programming language: cross it and you inherit a
parser, a type system, evaluation errors surfacing mid-run, and an injection surface in a file agents
are allowed to edit. Anything genuinely conditional belongs inside a skill or a node implementation,
which is code with tests.

**`maxVisits` is a financial control.** An unbounded review-to-implement loop is not a hang; it is
agent turns billing in a cycle until someone notices. `onExceeded` routes to a named node rather than
simply failing — taken from `subagent-driven-development`, whose fix loop trips a breaker at round 5
and adjudicates rather than giving up.

**Validation happens at load, not at runtime.** Every branch key matches a declared outcome, every
edge target exists, every `agent:` and `skill:` resolves, every node is reachable, and every path
reaches a terminal. A malformed process fails the *file*; it cannot fail three nodes into a run that
has already paid for two agent turns. This is what makes hot-reload safe.

### What this engine will never do

No parallel branches or fork/join. No sub-processes. No compensation or rollback. No first-class
timers. No expression language. No visual designer.

Those six are what turn 1,200 lines into 20,000. Recorded here so the question is settled rather than
re-litigated each phase. If a later phase genuinely needs one, that is a decision made with evidence.

**Consequence to accept knowingly: a run is strictly sequential.** Parallelism exists only *inside* a
node — a node may fan out to several subagents and synthesise, as `dispatching-parallel-agents`
describes, but the durable graph does not fork. The Copilot runtime port hit resource contention with
15 concurrent agents and responded by serialising through a mutex; sequential-by-default is the right
starting position.

## Skills, roles and the graph: one authority per concern

A skill is already a process description. `subagent-driven-development` contains loops, branches and
stop conditions — the same four primitives, in prose. Two representations of one thing is how systems
rot, so the boundary has to be explicit:

> **A skill is guidance a model may ignore. A graph is control it cannot.**

This is observed, not theoretical: skills in this project have instructed agents never to background
a test run, and agents backgrounded test runs repeatedly. Prose is advisory in practice. A loop-back
edge with `maxVisits: 5` is not.

| Layer | Artefact | Authority | Storage |
|---|---|---|---|
| Control flow | process YAML | the **engine** — guaranteed | git to Postgres |
| Procedure | skill `.md` | the **model** — guidance | git to Postgres, body verbatim |
| Role and scoped memory | squad team `.md` | the **model** — persona | git to Postgres |
| Target-repo knowledge | `AGENTS.md` | the **model** — context | the target repository |

There are therefore **no per-node C# handlers**. A node names an agent, a skill, and its declared
outcomes. That is literally 2.4's "the manufacturing steps written as skills rather than code",
landing in 2.2 as a consequence of the model. Two independent redeploy-free axes: edit the file to
change the shape, edit the skill to change how a step is performed.

**Outcomes must be structurally enforced, not politely requested.** A node declaring
`outcomes: [approved, rejected]` must constrain the agent to return one of them through a tool call
over a closed set — not ask in a prompt and parse the reply. Ask nicely and you get
"approved, with some concerns", and the branch has nothing to match. This is where "control the model
cannot ignore" is either true or decorative.

**A node pins its skill by name; it does not search for it.** `ISkillIndex` does semantic retrieval,
which is right for an agent hunting supporting material and wrong for a manufacturing step — the same
node must not load different skills on different runs.

### Porting the existing skill corpus

Measured against `Daedalus.Domain.Entities.Skill`'s limits, all 14 base superpowers skills already fit
on name, description and body size. Two things do not, and they split cleanly by coupling:

- **Port verbatim — 6 skills with zero harness coupling**: `test-driven-development`,
  `verification-before-completion`, `requesting-code-review`, `receiving-code-review`,
  `brainstorming`, `dispatching-parallel-agents`. These are judgement, and are what nodes should pin.
- **Do not port — the 2 most harness-coupled**: `using-git-worktrees` and
  `finishing-a-development-branch` describe session mechanics that become *engine* behaviour here.
- **Split — the process skills**: control flow moves to the graph, judgement stays in the skill. A
  side benefit is that `subagent-driven-development` shrinks well below its current 32 KB.
- **Open decision — 8 of 14 are multi-file**, and `Skill` stores one verbatim body plus a
  `SourcePath`. Either the schema gains a supporting-asset child table, or Daedalus authors its own
  single-file skills borrowing the content. This design recommends the latter.

## Persistence and the transaction boundary

```sql
workflow_run
  id, correlation_key UNIQUE      -- idempotent run creation, enforced by the database
  process, process_version        -- pinned at run start, never changes
  current_node, current_seq
  status                          -- Running | Awaiting | Succeeded | Failed | Cancelled
  awaiting_signal                 -- non-null iff status = Awaiting
  variables jsonb
  visits    jsonb                 -- node to count, backs maxVisits
  last_error, created_at, updated_at

workflow_run_event                -- append-only, never updated
  run_id, seq, at, node
  kind        -- Entered | Completed | Branched | Awaiting | Resumed | Failed | CapExceeded
  outcome     -- the declared outcome that selected the edge
  next_node
  payload jsonb                   -- agent, skill, model, tokens, duration, output reference
```

**One transaction per node completion**, containing exactly four things: append the event, evaluate
the edges, update the run row, and enqueue the next message via
`OrmOutboxStore.EnqueueAsync(..., DbTransaction, ct)`. All four commit or none do. That is what makes
a crash safe at *every* node boundary — the whole reason to accept outbox latency when a node is a
multi-minute agent turn. A crash never re-pays for a completed turn.

**`process_version` is pinned at run start.** A file edited mid-run does not retarget in-flight runs;
they finish on the shape they began with. Without this, hot-reload becomes a way to corrupt running
work.

**Redelivery is a no-op settled by the database.** The outbox is at-least-once, so a redelivered
message for a node the run has already left must do nothing. The existing code's form —
`if (execution.Step != RunStep.Scout) { return; }` — generalises to
`if (message.Seq != run.current_seq) return;`, with the real race settled by `WHERE xmin = @expected`
returning zero rows. Raw SQL is an advantage here: `byte[] RowVersion` was silently inert on Npgsql
across seven entities in this codebase, and an explicit predicate cannot be inert.

## Gates, resumption and hot-reload

**A gate holds nothing.** On reaching an `await:` node the dispatcher sets `status = Awaiting` and
`awaiting_signal`, appends the event, and **enqueues nothing**. No thread, no timer, no worker slot.
The process can exit and the run survives as a row.

**A mismatched signal is a loud failure, never a silent drop.** `ResumeAsync` verifies
in-transaction that the run is `Awaiting` and that the delivered signal matches, then appends
`Resumed`, advances, and enqueues. A mismatch returns a failure naming what the run is actually
waiting for. This is explicitly the behaviour the spike measured in `ZeroAlloc.Saga`, where an
unexpected event type was dropped and the saga sat at `Step1` forever with no error anywhere.

**The agent must not be able to resume its own gate.** This is the security property of the phase. If
a `workflow__resume` tool existed in the manufacturing agents' toolset, a run could approve itself and
publish, making every gate decorative. Resume is an API and console action bound to the `developer`
policy, and is **not registered as an agent tool**. A detached run holding only `reader` is denied by
the same authorizer that denies `git__*`, and this gets the demonstrated-failing test that 2.1's
boundary got.

**Cancel, because there are no timers.** A gate nobody answers parks indefinitely, which is visible
rather than dangerous — but indefinite needs an exit. `CancelAsync(runId, reason)` moves the run to a
terminal state and appends the event. Without it a stuck run can never be cleared and its branch
leaks.

**Hot-reload rides the mechanism that already exists.** Process definitions sync git to Postgres
exactly as skills do: same authoring story, same reviewability, and every instance sees the same
definition, which a per-host file watcher would not guarantee. Two rules make it safe:

- **A definition failing validation is rejected; the previous version stays active.** A broken edit
  never becomes runnable.
- **Old versions are retained while any run pins them.** A version can only be deleted once no run
  references it.

**Known limitation:** an in-flight run cannot be migrated to a new process version. Cancel and restart
is the answer; definition migration is deliberately not built.

## Automated multi-model review

An automated review is **a node, not a gate** — it does work rather than parking — so it needs no new
primitive. The fan-out lives inside the node, exactly as with `dispatching-parallel-agents`.

Thalos already has the seam: `IChatClientProvider.CreateChatClient(AgentDefinition)` is documented for
"Anthropic, OpenAI, a fake…", and `AgentDefinition.Model` is per-agent. What is missing is only a
second provider package; `Thalos.NET.Anthropic` is the only one that ships.

**Diversity of lens matters more than diversity of vendor.** Three models given the same prompt
produce correlated agreement, not independence. The Copilot port's panel worked because it had an
oracle — behavioural equality against the existing TypeScript — and a pipeline building new software
has none. So each reviewer gets a distinct question, and model diversity is a cheap hedge on top, not
the mechanism.

**It does not remove the human gate**; it reduces what reaches it. `models` and `quorum` are optional
per node, because three models inside a loop bounded at five is up to fifteen review turns per task.

## Error handling

| Class | Example | Response | Retried |
|---|---|---|---|
| Node failure | the reviewer rejected; the build did not compile | a declared outcome or a `failed` edge | **never** |
| Infrastructure fault | Postgres unreachable, model API 503 | exception, outbox backoff | yes |
| Engine fault | an edge points at a node that does not exist | fail the run, log loudly | never |

The line between the first two is checkable: **did we consume a model turn?** A turn that completed
and produced a disliked result is a node failure. A turn that never produced a result is
infrastructure. Conflating them costs the price the existing dispatcher documents — "paying for the
same failing turn eight times over, with nobody told until it dead-letters."

**Stranded runs must be swept.** When a message does dead-letter, the run sits at `status = Running`
with nothing in flight and nothing that will ever advance it. It looks alive and is not. A reconciler
sweep, following `ScheduleReconciler`'s pattern, terminates such runs with a named reason. Without it
runs rot silently, which is the worst outcome for a system whose point is inspectability.

**External side effects are not transactional.** A node that pushes a branch and then fails will
redeliver and push again, so every node touching the outside must be idempotent by construction —
`create_branch` tolerating an existing branch, `open_pull_request` finding-or-creating.

## Testing

The recurring defect in this codebase is tests that pass for the wrong reason — eight instances in
phase 1.7 alone, including a suite that passed *because* the system under test was broken. A workflow
engine is unusually good at producing them.

- **The graph walker must not be testable with everything stubbed.** Asserting "the run reached
  `Succeeded`" with no-op handlers returning `approved` verifies nothing. Every engine test names the
  edge it exercises and demonstrates red by deleting that edge from the process file.
- **Durability means two processes, not two scopes.** Write in process A, let it exit, read in a
  brand-new process B, confirm with raw SQL — the spike's methodology, and the only kind that would
  have caught the `StateMachine` and `Saga` differences.
- **The gate test must prove no thread is held.** Park the run, terminate the host, start a new one,
  deliver the signal, assert it advanced. Asserting `status == Awaiting` tests an enum.
- **The self-approval boundary is demonstrated failing.** Grant `developer` to the detached-run roles,
  observe RED, restore, confirm a zero-line diff, observe GREEN — with the principal built from real
  configuration, because phase 1.6 found a hand-built one leaving a boundary test green while the
  boundary was gone.
- **`maxVisits` is proven by a process that actually loops**, not by setting the counter directly.
- **Validation tests assert the valid neighbour too**, one character apart, so "rejects malformed
  input" cannot pass by rejecting everything.
- **Concurrency needs real contention** — two dispatchers, one run, one losing on
  `WHERE xmin = @expected`.

## Placement

Following the `Git` and `Git.LibGit2Sharp` split established in 2.1:

| Lives in | What | Why |
|---|---|---|
| `Thalos.NET.Workflow` | graph model, loader and validator, edge evaluation, gate semantics, `IWorkflowStore` and `IWorkflowDispatcher` abstractions | generic; no ORM or Outbox dependency |
| `Thalos.NET.Workflow.Orm` | run row and event log, migrations, outbox-backed dispatch | `ZeroAlloc.ORM`, `ZeroAlloc.Outbox.Orm` |
| **Daedalus** | the process files, agent and skill supply, hosting, the resume endpoint and its policy binding | hosting and authorization are the consumer's concern |

**Thalos must never reference Daedalus.** The independence guard added in 2.1 already enforces this.

## Risks

| Risk | Mitigation |
|---|---|
| Scope creep into a general workflow platform | the six never-do items are recorded above and are part of review |
| A stranded run after dead-lettering | the reconciler sweep, specified above; without it runs rot invisibly |
| Outcomes parsed from prose rather than constrained | structural enforcement through a closed-set tool call, tested |
| An agent resuming its own gate | resume is not an agent tool; authorization tested and demonstrated failing |
| Hot-reload activating a broken definition | validation at sync; previous version stays active on failure |
| Two persistence stacks until Milestone 3 | accepted deliberately; the RepoDigest chain stays on EF Core |
| The `Outbox` 2.5.2 to 2.6.0 bump | required by `Outbox.Orm`; verify the existing scheduling chain against it |

  `RalphPromptTemplateBuilder` instructs agents to "update or create @AGENT.md … only build/run/test

  only in Ralph, which phase 2.5 deletes. It must move to the engine first.
- `FileSystemWorkspaceContextProvider` probes `AGENT.md` and four Copilot paths but never
  `AGENTS.md`, the cross-tool convention. Adding it is a one-entry change.
- 8 of 14 base skills are multi-file against a single-body `Skill` model — schema change or
  re-author.
- `Thalos.NET.Anthropic` is the only chat provider; a multi-model panel needs a second.
- The squad roster and per-role history live as filesystem markdown for Claude Code and would need
  the same git-to-Postgres sync skills already have. That is phase 2.3's work, not this one.
