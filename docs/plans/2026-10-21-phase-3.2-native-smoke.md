# Phase 3.2: the native runs of each server target

The second runtime evidence of milestone 3, after `docs/plans/2026-10-17-phase-3.1-native-smoke.md`. 3.2 took the
reflection out of Daedalus and, through Thalos 0.19.0, out of Thalos. This records how far the natively published
`Daedalus.Migrations`, `Daedalus.Cli` and `Daedalus.Api` now get, and what stops each one.

## How it was run

- **Commit:** `8881a8d6` on `phase/3.2-reflection-out`, run on 2026-10-23. It adds only the `native-publish` workflow
  and the Task 22b Sentinel options on top of `9b263bf1`, whose CI warning keys name the predicting warnings below.
- **Publish:** not on the agent VM, where ILC runs out of memory. The `native-publish` workflow published the three
  targets in run 39953487637, with the counter's command and an output directory:

  ```bash
  dotnet publish src/Daedalus.<Target> -c Release -r linux-x64 -p:PublishAot=true -p:TreatWarningsAsErrors=false \
    -p:WarningsAsErrors= -o <dir> -tl:off
  ```

  The workflow deletes the `.dbg` files before it uploads the directory.
- **Two defects of the artifact,** both fixed in `5e3f19ef`, `ci: publish native binaries that run on Ubuntu 24.04
  and keep .mcp.json`:
  - The runner was `ubuntu-latest`, which is now Ubuntu 26.04. The binaries need `GLIBC_2.43`, for libm's float
    functions such as `sqrtf` and `atan2f`. The agent VM has glibc 2.41 and `mcr.microsoft.com/dotnet/sdk:10.0` has
    2.39, so neither could start them. The job is now pinned to `ubuntu-24.04`.
  - `actions/upload-artifact` skips dotfiles by default, `include-hidden-files: false` in the run's log, so the
    artifact had no `.mcp.json`. A run without it treats the file as absent and never parses it, which would have
    hidden C1 and A1. The upload now includes hidden files.
- **Run image:** because of the glibc, the binaries ran in a local image of `ubuntu:26.04` with `libicu-dev` and
  `ca-certificates` added, glibc 2.43. The targets set `InvariantGlobalization=false`, so ICU is needed. The publish
  directory was mounted read-only as `/app`, with host networking. The image was removed afterwards.
- **`.mcp.json`:** copied from `src/Daedalus.Cli/.mcp.json` and `src/Daedalus.Api/.mcp.json` at the commit into the
  publish directories, where `dotnet publish` puts them.
- **Stack:** the Postgres and Keycloak of `eng/measure/`, under the harness's own container names, network and ports,
  started by hand as in 3.1, because `stack_up` applies the migrations with `dotnet run`.
- **Migrations** ran against the empty database, with `ConnectionStrings__daedalus` set to the harness's `PG_CONN`.
- **CLI** ran as `measure-cli.sh` runs it: in the directory of the binary, with a stdin that stays open and never
  delivers a line, and Information logging.
- **API** ran with `measure-api.sh`'s environment variables: `ASPNETCORE_ENVIRONMENT=Development`, the harness's
  `ASPNETCORE_URLS`, `ConnectionStrings__daedalus`, `Authentication__Authority`, an empty
  `OTEL_EXPORTER_OTLP_ENDPOINT`, its log levels and `Thalos__Workflow__DataRoot`.
- **No `Thalos__McpConfigPath` unblock.** 3.1 needed it to get past C1 and A1. These runs read the real `.mcp.json`.

## Run results

None of the three targets reached its ready signal. The two 3.2 owned, C1 and A1, `.mcp.json` parsing, are gone.

The CLI's "Application started" was 3.2's finish line. It now stops at C3, the Anthropic SDK, which 3.3 replaces, and no
stop is in code 3.2 owns. The owner moved "reaches Application started" to 3.3 on 2026-10-23; the phase 3.2 design's
finish line records the amendment.

- **Predicted by:** the IL3050 on the `DbContext` constructor and on `MigrateAsync`, as in 3.1.
- **M2, #404, is still there.** All five runs logged "Database migration failed", but the stack was cut at a different

- **Then:** the schema was applied with the JIT runner, `dotnet run --project src/Daedalus.Migrations -c Release`, as

### C3. CLI: the Anthropic SDK serialises through reflection JSON

- **Exception:** `System.InvalidOperationException: Reflection-based serialization has been disabled for this
  application. Either use the source generator APIs or explicitly configure the 'JsonSerializerOptions.TypeInfoResolver'
  property.` "Hosting failed to start", exit code 1. "Application started" was not logged.
- **Top of the stack:**

  ```text
  System.Text.Json.JsonSerializer.GetTypeInfo[T](JsonSerializerOptions) + 0x2b
  Anthropic.Models.Messages.CacheControlEphemeral..ctor() + 0x52
  Thalos.Anthropic.AnthropicChatClientProvider..ctor(IOptions`1, Func`2, HttpClient) + 0x85
  ...
  Microsoft.Extensions.DependencyInjection.ServiceProviderServiceExtensions.GetService[T](IServiceProvider) + 0x34
  Thalos.ThalosServiceCollectionExtensions.<>c.<AddThalos>b__0_2(IServiceProvider sp) + 0x2e
  ...
  Microsoft.Extensions.DependencyInjection.ServiceLookup.CallSiteRuntimeResolver.VisitIEnumerable(...) + 0x60
  ...
  Microsoft.Extensions.Hosting.Internal.Host.<StartAsync>d__14.MoveNext() + 0x450
  ```

- **Why at boot:** the host resolves its hosted services, one of which depends on Thalos' chat client provider, and
  `AnthropicChatClientProvider`'s constructor creates a `CacheControlEphemeral`. That constructor asks
  System.Text.Json for a type info through the SDK's reflection-based options; the warning keys put its two
  `JsonSerializer.SerializeToElement<String>` calls at lines 55 and 64. So the Anthropic SDK fails before any model
  call, as soon as the provider is built.
- **Predicted by:** IL2026 and IL3050 in the Anthropic SDK 13.1.0,
  `src/Anthropic/Models/Messages/CacheControlEphemeral.cs` lines 55 and 64, on
  `JsonSerializer.SerializeToElement<String>(String, JsonSerializerOptions)`, in the CLI's warning keys. The same
  four keys are in the API's.
- **Local unblock:** none. `AddDaedalusAgents` calls `thalos.UseAnthropic(configuration)` unconditionally.
- **Owner:** 3.3, which replaces the Anthropic SDK with `ZeroAlloc.Rest.Anthropic`. This is the native reproduction
  the owner's rule asks for before the Anthropic issue is filed; 3.3 still checks the latest SDK first. The API would
  meet it too, because it registers the same provider, but it stops earlier, at A2.

### C1, A1 and C2: gone

- **C1 and A1, `.mcp.json` parsing,** are gone. Thalos 0.19.0's `McpConfigFile.Parse` uses a source-generated
  context, and no key names `McpConfigFile` in either target. The runs did reach it: with the real `.mcp.json` the
  CLI got past `ConfigureServices` and the API past `AddDaedalusAgents`, and with a malformed file mounted in its
  place both stopped with `System.Text.Json.JsonException: The JSON value could not be converted to System.String.
  Path: $.mcpServers.x.type`, from `McpConfigFile.Parse`, called by `McpServersLoader.Load` in the CLI and by
  `ValidateCSharpWriteBindings` in the API. That is the source-generated reader rejecting bad input, not the
  reflection error.
- **C2, `PostgresConversationMap`'s trimmed constructor,** has no warning left: no key names
  `ChannelThalosBuilderExtensions` or `UseConversationMap`. At run time it is unproven. The CLI's `StartAsync` met C3
  while it resolved the hosted services, and nothing shows whether the map had been built by then.
