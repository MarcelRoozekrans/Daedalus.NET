## The things worth remembering

**1. Both privacy leaks came from wiring, not from a tag anyone wrote by hand.** B4's repository tag was set by a
generated proxy from the request parameter, before the allow-list check ran. B8's Telegram bot token came from the
runtime's own `url.full`, which keeps the path. No per-task test saw either, because each test checked the tags its
task added. A review that asked "what can reach this span" found both.

**2. A test's `ForceFlush` hid a production defect.** B2's collector test failed on `/v1/logs` as written. The
implementer added a manual flush and called it "not a wiring fault". The reviewer was told to root-cause it instead,
and found an upstream regression that loses every log of a short-lived host over `http/protobuf`.

**3. An in-memory exporter keeps references, so it cannot prove ordering.** B8's redaction test passed with its exporter
registered before the redacting processor, because the processor mutated the same `Activity` after export. Only an
exporter that copies the tags at export time turns that red.

## Incidents

- **OTLP `http/protobuf` loses a short-lived host's logs (B2), an upstream regression.**
  - B2's collector test saw `/v1/traces` and `/v1/metrics` but no `/v1/logs`. The log exporter creates its HTTP client
    lazily on the first export (open-telemetry/opentelemetry-dotnet PR 7298), through a closure over the root service
    provider. Nothing flushes on host stop, so the first log export runs inside `ServiceProvider.Dispose`, gets
    `ObjectDisposedException` and drops the batch. Traces and metrics create their clients eagerly and are not
    affected, and neither is grpc. Aspire defaults to grpc, so the AppHost is not affected.
  - The owner asked whether it is really upstream. The controller proved it with a standalone repro that uses only
    Microsoft.Extensions.Hosting and OpenTelemetry: on 1.17.0 and 1.19.1, `UseOtlpExporter`, `AddHttpClient` and
    per-signal `AddOtlpExporter` all lose logs 6 of 6. Waiting 7 s, or a flush in `StoppedAsync`, delivers them 6 of 6.
  - Re-verified before filing with a clean minimal repro: the bug needs `Microsoft.Extensions.Http` to be loadable,
    which the first repro's package reference had hidden. A stock `WebApplication` reproduces it 3 of 3. It is a
    regression: 1.15.3 delivers the logs, and 1.16.0, 1.17.0 and 1.19.1 lose them.
  - Filed upstream with the owner's approval as **open-telemetry/opentelemetry-dotnet#7915**, and tracked in
    **Daedalus#332**, with the corrections in a comment.
  - Mitigation: `TelemetryShutdownFlush` (`a70e74c`, `a86961b`), tested through a real host's Start, Stop and Dispose
    with no `ForceFlush`.
  - **The gap it leaves.** In .NET 10 a host whose start fails is disposed without `StoppedAsync`, so its startup-failure
    logs are still lost until the upstream fix. The first review had offered the flush as covering that case; the
    re-review disproved it with a hosted service that throws in `StartAsync`. Covering it is a decision for the owner,
    on #332.
- **Privacy leak 1, the repository tag from caller input (B4 review I1).** The generated proxy set
  `daedalus.repository` from `request.Repository` at span start, before the starter checked the allow-list. So a refused
  start recorded whatever the caller sent: the JSON body of `WorkflowRunsController.Start`, with no length cap, or the
  `repository` argument of the `DaedalusManufactureTools.Start` LLM tool call. Fixed before release in `049cce0` and
  `a86e0ad`: the tag is the configured name, set after the match, and only on the start span.
- **Privacy leak 2, the Telegram bot token in `url.full` (B8 review I2).** B2 added HttpClient tracing with no filter.
  Thalos's Telegram client sends to `/bot{token}/{method}`, and .NET 10's runtime redacts only the query, not the path.
  So any host with a `BotToken` and an OTLP endpoint would have exported the token on every poll and send. Fixed before
  release in `18c43f5` and `4fb39b9`: outgoing spans keep only the origin, for every call. `main` traced nothing, so
  neither leak ever shipped.
- **A full Integration run killed for low memory (B7).** The controller's rerun of the full Integration suite, to
  check two `RunScopedRoslynRoutingTests` failures, was killed by Claude Code for low memory and not restarted. From
  then on, test runs were memory-limited, and B8's full regression was held for the owner's go. It ran after a
  build-server shutdown, with 16.1 GB free, and only once no other test process was running.
- **Git Bash `sed -i` and CRLF (B5).** The whole-solution format check reported whitespace in scheduling files the
  branch never touched. The working copies were LF where format wants CRLF, so the controller first dropped it as a
  local line-ending artefact. The correction found real drift on `main`: 19 findings in 6 scheduling files, and no CI
  format step. The lesson recorded: Git Bash `sed -i` rewrites a CRLF file as LF, so edit with Python and keep CRLF, or
  re-run format.
- **CRLF in commit messages during the reword (final review M1, M2).** The `msg-filter` reword wrote CRLF into the
  messages on its first two tries, because Python's stdout was in text mode. Each time the branch was reset to
  `backup/phase-2.9-before-reword` and the reword redone. The final run differs only in the two intended places, the
  tree is identical, no message contains a CR, and commitlint is clean.
- **A duplicate issue.** B5 filed #333 for the scheduling format drift, which #312 already tracked with the same "add a
  format check to CI" fix. The file and line list moved to a comment on #312, and #333 was closed as not planned.
- **A Thalos CI flake after the release.** The `main` CI run 38097138876 after the release merge failed on one Windows
  test: a 1-tick `CancelAfter` race in a Sandbox.Host Roslyn tool-list timeout test, unrelated to telemetry. Filed as
  **Thalos.NET#297**. The release itself had published.
- **Smaller ones.** A5's implementer raced two mutation runs and restored `IWorkflowStore.cs` by hand; the reviewer
  diffed it line by line. A8's full Thalos run could not copy the McpServer helper DLL, locked by a .NET host process
  it had not started, so three projects were rerun by project. B1 briefly ran two test processes at once; all suites
  were rerun cleanly. B4's message reword could not use `git rebase -i`, so it was done by detaching, amending and
  cherry-picking, with the trees checked identical.

## Red-verification notes

Every task report carried a table of Reds, each applied, run and restored, and every review checked it. Reds that did
not fire as written, and what replaced them:

- **A2, the `DO UPDATE` red (K12).** It failed inside the second `StartAsync`, on a 23503 foreign-key violation, not at
  the run-id assertion. Replaced with an `UPDATE trace_parent` in `LookupExistingRunIdAsync`, which goes red on the
  final `TraceParent` assertion. Two doc-only reds were not run and were accepted on reasoning: a `SelectRunSql` throw,
  and an `UPDATE` that keeps the same id.
- **A3, a brief that could never pass.** The brief's `DispatchOf` used `Equals(s.GetTagItem(...), runId)` inside a
  FluentAssertions predicate, which the expression rewrite turns into an `ArgumentException`. All 8 span tests failed
  for the wrong reason before any production code existed. It became `runId.Equals(...)`, and the carry went to every
  later task. Two Red lines fail one assertion early: dropping the run-id tag fails at the `DispatchOf` lookup, and
  parent-instead-of-link fails at the link count. The unfalsifiable run-id assertion was deleted. The "`Activity.Current`
  is still the ambient one" assertion has only one red, turning `DispatchAsync` into a synchronous wrapper.
- **A4.** With the span name derived from the constant, the "drop `{type}`" red stayed green; the test now uses a literal.
  Dropping only `[Trace]` (K9) or only `[Histogram]` is refused by the generator (ZTEL004, ZTEL011), so each was dropped
  with its tags. The "span starts after the action" red was simulated by clearing `Activity.Current`.
- **A7.** The reviewer's own red was blocked by the locked McpServer DLL. The test was accepted on reading and on the
  implementer's verified reds.
- **B1, the stub-table red (K11).** Attributing every row to `sources[0]` threw Npgsql 42P07 from `ApplyAsync`, so
  `IsSuccess` was never reached. The call is now wrapped in `NotThrowAsync` with that red on it, and the
  "only `OutboxOrmMigrations.Postgres`" red stays on `IsSuccess`. Both were verified, at `:127` and `:131`.
- **B2.** The original collector test was green only because of its `ForceFlush`. Its replacement goes red when the flush
  registration is removed, 5 of 5. "Always true" in `IsTracedRequest` does not compile under the analyzers as a literal,
  so a non-constant equivalent was used.
- **B4.** The `RunIdTag ... BeNull()` assertion was unreachable by its red, since dropping `When = "IsSuccess"` throws in
  the act (M1). That red was reworded, and the assertion got its own: `[TraceTagFromResult(RunIdTag, "Error.Kind",
  When = "IsFailure")]`. The enabled starter's proxy had no red at all (I2), and neither did the `TagStartSpan` guard
  (R1); both got tests. Removing the whole `TagStartSpan` call is refused by S1144, so its `SetTag` was neutralised.
- **B5.** "Move the `SetTag` above the `found.IsFailure` check" does not compile, because `task` is not in scope there.
  Reworded to "tag `taskId` before the check".
- **B6.** The implementer approximated "tag the run id in place of the node". The reviewer ran it literally and it went
  red, so the line stands as written.
- **B7.** Five reds were simulated by filtering the captured list, because they are Thalos 0.15.0 internals. The review
  replaced two with real Daedalus changes: the link (`Activity.Current = null` before the store start) and the store
  proxy (the concrete `OrmWorkflowStore`, which fires at the `store.start` lookup). The resume span then got its own
  real red, `WorkflowRunGateway` over the unproxied store (`63fbc49`). The dispatch span, its own trace, the host-action
  child and the outcomes are now worded as guarded in Thalos by `DispatchTelemetryTests` and `HostActionTelemetryTests`,
  with no red claimed here. About ten assertions had no Red line at all (I2); each got one. The exported-span leak scan
  was dropped as redundant, since the capture sees every stopped span of a listened source.
- **B8, the ordering red (R1).** The redaction test could not catch a processor ordered after the exporter, because the
  in-memory exporter kept references. The test exporter now copies the tags at export time, and registering it before
  `AddServiceDefaults` turns 2 tests red. The processor's own red was real from the start: without it the exported
  `url.full` was `http://127.0.0.1:PORT/bot123456:SECRET-token/getMe?*`.
