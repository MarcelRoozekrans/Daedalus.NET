# Phase 3.5 Rulings: EF Core to ZeroAlloc.ORM

**Spec:** `docs/superpowers/specs/2026-11-05-phase-3.5-zeroalloc-orm-design.md`
**Gap audit:** `docs/plans/2026-10-17-zeroalloc-orm-gap-audit.md`
**Outbox handover:** `docs/plans/2026-11-05-zeroalloc-outbox-orm-handover.md`
**Plan:** `docs/superpowers/plans/2026-11-05-phase-3.5-zeroalloc-orm-plan.md`

The phase runs subagent-driven on `phase/3.5-zeroalloc-orm`. R1 to R6 are calls the design leaves to the builder or
the plan makes, R7 and R8 are the controller's, from the pre-flight scan of the plan, and R9 and R10 are Task 1's
own. Every later task appends from R11. Every decision taken on the owner's behalf is listed with what it costs if
it is wrong, so it can be checked and reversed. A changed or retired integration test is always a ruling here, as is
every save site's classification as guarded or independent, and every raw `[Query]` or `[Command]` written where
the cookbook's LINQ would not do.

## Owner decisions

Owner decisions are the owner's to weigh, so they carry no cost line.

2026-11-05, at the brainstorm, in the design's "Owner decisions":

- **Start now, settle the open gaps in the design.** Design and plan proceed; only the outbox move waits on a
  release.
- **Gap 4.5 is fixed upstream.** `ZeroAlloc.Outbox.Orm` gains a configurable table name per named pipeline and
  `RequeueAsync`, at least, on its store. The channel/RepoDigest pipeline keeps its own table, `"OutboxMessages"`, so
  its pending rows and leases stay where they are, and the workflow engine keeps `outboxmessages`.
- **#290 is fixed, not ported.** The five live aggregates with a dead `bytea` `RowVersion`, `AgentSession`,
  `BrainstormSession`, `RepositoryConfiguration`, `Project` and `CodeAnalysisRequest`, get a real `xmin` guard, as
  `Task` has. A migration after the baseline drops the six dead `bytea` columns, those five plus `ExecutionSession`.
  They are always `NULL`, so no data is lost.
- **Domain entities are rebuilt through explicit `Rehydrate` factories in `Daedalus.Domain`.** Infrastructure row
  records call them. Domain gains no ORM reference.
- **The guard protects against lost updates only, not against all concurrency.** A save is `xmin`-guarded when it
  writes values computed from the row it loaded. A save that writes independent columns updates only those columns,
  with no `xmin` check. Atomic in-database updates, such as counter increments and compare-and-swap transitions, stay
  as they are. Adding children inserts the child rows without touching the parent. So benign concurrency keeps
  today's results, and the parity bar holds.
- **Rolling back to an EF build is not supported.** Rollback means restoring a database backup taken before the
  upgrade. Migration 2 ships with the baseline in this phase. `__EFMigrationsHistory` is kept only for the adoption
  check. The dev-database proof shows the upgrade, not a downgrade.

## Rulings

Calls the design leaves to the builder, and the plan's, Task 1:

1. **R1:** store order is the audit's section 2 order, with transaction partners moved together, `CostAnalytics`
   after the tables it reads, and the outbox partners, `ScheduledRunStore`, `ScheduledRunExecutionStore` and
   `ScheduleReconciler`, last with the outbox move.
   *Cost if wrong:* a store ported before a partner it shares a transaction with would split that transaction across
   two connections; the outbox atomicity test per site catches it, and the fix is reordering, not rework.
2. **R2:** `Rehydrate` is `public`, documented "for persistence only". Domain has no `InternalsVisibleTo`, and two
   assemblies, Infrastructure and Agents, would need it.
   *Cost if wrong:* application code could call `Rehydrate` and build an entity that skips `Create`'s validation; a
   review or an architecture test catches a call outside Infrastructure.
3. **R3:** maps and SQL classes live in Infrastructure, under `Persistence/Sql/`. The generator reads maps from the
   compilation that holds the queries, and stores in Agents and Api use the same tables, so one assembly holds them
   all.
   *Cost if wrong:* Agents' stores reach their SQL through Infrastructure's public `…Sql` classes rather than owning
   them; moving a class later is a namespace change, not a rewrite.
4. **R4:** one `NpgsqlDataSource` serves the app and the workflow poller. `AddApplicationDatabase` registers it with
   `TryAddSingleton`, and Agents' workflow registration becomes `TryAddSingleton` too, so whichever runs first wins
   and both read the same `daedalus` connection string.
   *Cost if wrong:* the poller shares the app's pool, so a pool exhausted by one starves the other; Npgsql's default
   pool of 100 is far above what either uses today.
5. **R5:** the Daedalus migrations are embedded `.sql` resources in Infrastructure, under the migration source name
   `daedalus`, numbered `1`, `2`, ….
   *Cost if wrong:* the source name is written into `__zaorm_migrations` on every database it runs on, so a rename
   after the first deploy needs its own migration of the history rows.
6. **R6:** the dev-database proof uses the `postgres-data` volume whose newest `"WorkflowRunRecords"."CreatedAt"`
   is latest. Task 23 decides it.
   *Cost if wrong:* the proof runs on the stale copy and misses a row shape only the current one holds; the per-table
   row counts still prove the upgrade keeps data.

The controller's, from the pre-flight scan:

7. **R7:** Task 9 keeps the `AgentSession` EF mapping, its `RowVersion` unmapped, because `CostAnalyticsService`
   reads `AgentSessions`; Task 16 deletes it with the other mappings.
   *Cost if wrong:* one configuration file lives seven tasks longer than it must; deleting it in Task 9 instead would
   break `/costs` until Task 16.
8. **R8:** execution order is Tasks 1 to 17, then 23. Tasks 24 to 26 wait with 18 to 22 for the
   `ZeroAlloc.Outbox.Orm` release, because the native CLI stops at EF model building, so Task 24 cannot pass with EF
   in the graph, and Tasks 25 and 26 describe the final state.
   *Cost if wrong:* if the release lands early, the wait cost nothing; if Task 23's dev-database proof is affected
   by 18 to 22, it is repeated after 22.

Task 1, the capability spike (`OrmCapabilityTests`):

9. **R9:** a `text[]` column reads into its Domain property's own type and binds as `string[]` as a parameter. The
   spike maps the Domain entities themselves, so `"Skills"."Tags"` is `Skill.Tags`, an `IReadOnlyList<string>` with
   a hand-written getter over `_tags`, which the map brings in with `[ColumnMap(nameof(Skill.Tags))]`. It reads into
   a row record's `IReadOnlyList<string>` parameter, and an insert or a `SetProperty` binds a `string[]`. The first
   draft's query, `.Select(s => new SkillTagsRow(s.Id, s.Tags))` with `string[] Tags` on the record, held no
   conversion at all: it is ill-typed C#, CS1503. The build did not show CS1503. The generator rejected the chain with
   ZAO102, "... as the chain source is not supported", left the partial method unimplemented, and the resulting
   CS8795 is a declaration error, which stops the compiler from reporting errors in method bodies. With the
   conversion written, `s.Tags.ToArray()`, the chain reports ZAO107: a projection argument must be a mapped column,
   a parameter or a literal. Both reproduced in the Task 1 report. Row records declare `IReadOnlyList<string>` for
   such columns.
   *Cost if wrong:* none at run time; a store task that declares `string[]` on a row record meets ZAO102 without
   the C# error behind it, which this ruling explains.
10. **R10:** inserts are raw `[Command]`s listing every column of the table, as the plan's store recipe, step 5,
    says. The cookbook offers no LINQ insert: its "Not supported yet" sends inserts to `[Command]` or `BulkInsert`,
    and `[LinqCommand]` only updates or deletes. The spike's two inserts, into `"Skills"` and `"AgentMessages"`,
    follow the same rule.
    *Cost if wrong:* a column added to a table later needs adding to its insert by hand; a missed `NOT NULL` column
    fails the insert at once, and a missed nullable one is caught by the store's round-trip test.

Task 2, the baseline migration (`0001_baseline.sql`, `DaedalusMigrations`, the frozen EF chain):

11. **R11:** `AddNodeUsageUniqueIndex`'s `migrationBuilder.Sql` gains the `;` its `DELETE` lacked. EF runs each
    operation as its own command, so no database ever saw the difference, but `dotnet ef migrations script` glued the
    `DELETE` to the next `CREATE UNIQUE INDEX`, and the scripted chain failed as one batch. With the terminator in
    the migration, `ef-chain.sql` is the script's output unedited, apart from the byte-order mark `.editorconfig`'s
    `charset = utf-8` rules out.
    *Cost if wrong:* none on a database; a reviewer who wants the C# migrations byte-identical to their shipped form
    reverts one character and adds the `;` to `ef-chain.sql` by hand instead.
12. **R12:** the baseline folds every column a later EF migration added into its `CREATE TABLE`, at the end where
    `ALTER TABLE ... ADD` put it, and `"Tasks"`' `CK_Tasks_Status_Stored` into the table too. Tables and indexes
    follow EF's order, `CREATE EXTENSION IF NOT EXISTS vector` included, at `AddSemanticEmbeddings`' place. The data
    statements and `"StructuredLearnings"` with its HNSW index, created and later dropped by EF, are left out. The
    equality test compares more than the brief lists: column order, as the rank among live columns, since a dropped
    column leaves a hole in `ordinal_position`; type details; identity; and sequences. An insert without a column
    list or a `SELECT *` would read a different order on a fresh database otherwise.
    *Cost if wrong:* none at run time; the extra checks only make the test stricter.
13. **R13:** `EfChainDatabase` holds `CreateEmptyAsync`, `DropAsync` and `ExecuteAsync` beside the brief's
    `CreateAsync`, so the equality and adoption tests share one way to make and drop throwaway databases. The
    older-head database is an EF-chain database with the head migration undone by hand, its index dropped and its
    history row deleted, as `dotnet ef database update` to the predecessor would, rather than a second frozen script.
    *Cost if wrong:* if undoing by hand ever drifts from EF's `Down`, only the schema of a database the runner refuses
    anyway differs; the refusal reads `__EFMigrationsHistory` alone.

Task 4, `WorkflowRunRecordStore`, the first store port:

18. **R18, the store pattern:** every later store task copies these names and this shape.
    - **Place:** `Persistence/Orm/<Aggregate>/`, namespace `Daedalus.Infrastructure.Persistence.Orm.<Aggregate>`,
      here `WorkflowRunRecords`. One `<Aggregate>Sql` per aggregate; the maps of its child tables sit beside it in
      the same folder. The folder is `Orm`, not `Sql`, so the bare `Sql.Table<T>()` resolves (R22).
    - **Map:** `internal static class <Entity>Map`, with `[TableMap]` and only the `[ColumnMap]` overrides, here
      `PayloadJson` with `Json = true`.
    - **Row record:** `internal sealed record <Entity>Row(...)` with one parameter per column in table order and
      `ToDomain()`, which calls `<Entity>.Rehydrate`. A second read shape gets its own row record.
    - **SQL class:** `public sealed partial class <Aggregate>Sql(IAsyncDbConnection connection)`. Its public
      methods take and return Domain types, `InsertAsync(WorkflowRunRecord, ct)` and
      `ListAsync(runId, kind, ct)`, and map rows through `ToDomain()`. The generated methods are `private partial`
      and carry no `Async` suffix, `Insert` and `ListRows`; each companion is `private static <Method>Query`,
      starting from `Sql.Table<T>()`. A public method cannot return an internal row record (CS0050), and
      Infrastructure grants Agents no `InternalsVisibleTo`, so the public surface speaks Domain and the rows stay
      inside.
    - **House form for strings:** a string comparison in a chain, and in any caller, is
      `string.Equals(a, b, StringComparison.Ordinal)`, never `==`: Meziantou's MA0006 is an error in this
      repository. The optional filter reads `kind == null || string.Equals(r.Kind, kind, StringComparison.Ordinal)`
      and translates to the cookbook's `(@kind IS NULL OR "Kind" = @kind)`.
    - **Entity alias:** any file in the folder that also uses `Task` imports the entity by alias,
      `using WorkflowRunRecord = Daedalus.Domain.Entities.WorkflowRunRecord;`, not the whole namespace:
      `Daedalus.Domain.Entities.Task` makes `Task` ambiguous with `System.Threading.Tasks.Task`.
    - **Domain:** `public static <Entity> Rehydrate(<every column in table order>)`. The EF-only parameterless
      constructor becomes one private constructor taking every field, which `Create` and `Rehydrate` share and which
      EF binds by parameter name while a mapping lasts. Properties become get-only.
    - **Store:** opens one connection per call, `await using var connection = await db.OpenAsync(ct)`, and builds
      the SQL class on it.
    *Cost if wrong:* every store task from 5 on copies the shape, so changing it later means touching each ported
    store: a rename of the public methods or a move of the row records is mechanical per store, but it grows with
    every task that lands first.
19. **R19:** `WorkflowRunRecordStore`'s write sites. `AppendAsync` is an insert and the only write. The table is

    listing every column but the identity `"Id"`. The read is LINQ, `[LinqQuery]` with an optional `kind` filter.

    id-taking overload, an additive change.

23. **R23:** `PostgresConversationMap` save-site classification, Task 5. The store has two writes and no others,

    *Cost if wrong:* if a later change adds a version column, the upsert needs a guard clause; until then a rebind
    from a stale caller overwrites the session, which is today's behaviour.

29. **R29:** `PostgresRoleCharterStore` save-site classification, Task 6, read on 2026-11-05. The store has three
    writes, all independent: `UpsertAsync`'s version insert, its head insert or head update, and
    `DeactivateMissingAsync`'s sweep. No row has a version column, no `xmin` guard existed and none is added, so
    there is no lost-race test of the guarded kind. EF wrote the version and the head in one `SaveChanges`, one
    transaction; they are now two statements. A failure of the head write after the version insert leaves the
    version row behind, which is harmless: the history is append-only and the next sync finds the hash already
    captured. The check-then-insert race on the primary keys stays: the loser's insert throws Npgsql's
    `PostgresException`, caught as `DbException` around the writes only (the reads still propagate), and answers
    `SkillStoreFailed("Could not store the role charter.", ...)`; the detail string is the exception type name, now
    `PostgresException` where it was `DbUpdateException`. No caller or test reads it. The head update writes the
    three columns `SetCurrent` changes. Pinned by `Upsert_loses_the_head_insert_race_with_SkillStoreFailed`.
    The earlier scan's note that this store touches `.Skills` was `RoleCharter.Skills`, a text[] column of
    `"RoleCharterVersions"`; the store reads and writes no row of the `"Skills"` table, so nothing is mapped into
    `Persistence/Orm/Skills/`.
    *Cost if wrong:* a process that dies between the two statements leaves a version with no head until the next
    sync, which repairs it; a caller that reads the exception name in the detail sees a different string.
30. **R30:** Task 6 queries. The versions and heads are `[LinqQuery]` reads into row records; `Skills` reads into

    `Dictionary<string, RoleCharterHead>` in C# with `StringComparer.Ordinal`. The inserts are raw `[Command]`s
    (R10); the head update and the sweep are `[LinqCommand]`s. The sweep's `!roles.Contains(h.Role)` takes a
    `List<string>` parameter, not the `string[]` the brief named: on a `string[]`, `Contains` resolves to
    `Enumerable.Contains` and Meziantou's MA0002 is an error here, while `List<string>.Contains` has no comparer
    overload and the cookbook accepts `List<T>` as an array parameter. The generated SQL binds it as an array; an
    empty list deactivates every active head, pinned by `Deactivate_missing_flips_only_active_heads_outside_the_seen_roles`.
    The existence check is `.Any()` on the composite key, with `string.Equals(..., Ordinal)` (R18).
    *Cost if wrong:* none at run time; the parameter type is invisible to callers.
