## The three things worth remembering

**1. A hand copy of someone else's semantics drifted three times, and each fix was to ask the owner
of those semantics.** A4's hand-written reflection walk over tool parameters kept missing shapes the
serialiser would bind, so a forged admin principal reached the tool through `List<Principal>`, a DTO
property, a nullable struct and then generic DTO properties. It was replaced by a walk over
System.Text.Json's own `JsonTypeInfo`. A5's hand-resolution of symlinks let link chains and `..`
targets escape on Linux, and was replaced by `realpath` and `GetFinalPathNameByHandle`. A7's
hand-written git config parser let a valueless key bypass the allow-list and run a filter driver on
commit, and was replaced by asking git for the configuration it will actually use. The ledger's own
words at the third: "the third time a hand copy of kernel or tool semantics failed in this phase".
When a security check must agree with a serialiser, a kernel or a tool, ask that thing.

**2. The preflight checked the account's permission, not the token's.** B17's preflight saw
`push=true` on `daedalus-sandbox` and called the token fine. It was the account's permission. The
AppHost's fine-grained PAT had read access but not Contents write, so after the owner approved the
run at the gate, `git push` got 403. The action failed closed and kept the worktree and commit. But
nothing could move a Failed run forward: the API had only start, resume and cancel. Re-publishing
would have meant a new run and about 1.1M tokens again. Building the retry cost a Thalos release,
0.12.0, and a breaking change. A credential check must exercise the credential itself, the way the
later `push --dry-run` as the token did.

**3. Caching works, and the implement turn was smaller this time.** The whole run read 84.9% of its
input from cache. Implement used 291,161 input tokens against 2.4's 737,634, which is -60.5%. Per-node
usage was non-null on all three completions and cache reads were non-zero, so rulings R2 and R3 are
in effect. This is still one measurement against an intent of one class and its tests, so token
sizing stays open, as #280 says.

## A1's decision and A21's observed MAF behaviour

**A1, Roslyn staleness.** Measured against a one-project, two-file solution in a linked worktree,
with `RoslynCodeLens.Mcp` over stdio.

- **Readiness signal:** `readyTool = list_solutions`. The handshake and tool list return in seconds
  or less whatever the load state; the first `list_solutions` is the call that blocks, about 2.7 s,
  and it reports `status: "ready"` per solution. The fix round added a 60 s timeout with a 2 s poll,
  scaling as roughly `max(60, 15 * projectCount)` seconds; that scaling is an estimate, not measured.
- **Reload:** `tool:rebuild_solution`, about 2.1 to 2.4 s. Edits to files already loaded are visible
  with no reload. Brand-new files are never seen until an explicit reload, even under SDK-style
  globbing. `none` was ruled out because new files would stay invisible for the whole run; `restart`
  because it costs more and found nothing `rebuild_solution` did not. The rule recorded: reload
  before the next Roslyn call after any `workspace__*` write, which A9 already does.
- **Worktree:** a linked worktree loads normally.
- `get_file_overview` reports only types and diagnostics, never members, so it is not a method-level
  staleness probe; `search_symbols` is.
- Every timing rests on two runs at toy scale. The spike named B17 as the place to measure real
  scale; the ledger records no readiness or reload timing from the live run.

**A21, how Microsoft Agent Framework 1.22 treats `AIContext.Messages`.** Verified by decompiling
`Microsoft.Agents.AI.Abstractions` and `Microsoft.Agents.AI` 1.22.0.

- **It appends; it does not replace.** The default `AIContextProvider.InvokingCoreAsync` shows the
  provider only External-source messages, stamps its returned messages `AIContextProvider`, and
  returns `inputContext.Messages.Concat(providerMessages)`. A message returned from
  `ProvideAIContextAsync` therefore always lands after the latest user message.
- `ChatClientAgent.PrepareSessionAndMessagesAsync` loads history first, chains every provider, and
  takes the last provider's full `Messages` as the request list. So overriding `InvokingCoreAsync` is
  the documented hook for full control, and `MemoryContextProvider` now does that, inserting the
  recalled block, marked `Transient`, directly before the user message it was recalled for.
- **Storage:** the history store's default filter drops only `ChatHistory`-sourced messages, so a
  message stamped `AIContextProvider` is stored by default. The `Transient` filter in
  `SessionStoreChatHistoryProvider` is therefore necessary. It checks the value, not just the key.
- History is a lazy `Select` that clones untagged messages on each enumeration, so placement must
  work on one materialised list.
- Providers run once per run; `FunctionInvokingChatClient` carries the same list across tool round
  trips, so the block is kept, not re-inserted.
- The A21 review found the memory message broke the next turn's cache prefix, which led to the fourth
  breakpoint, see the A21 ruling.

## A note for the next run

Check each credential by doing the thing it is for, not by reading what the account may do. A
`push --dry-run` as the token would have caught the 403 before any credits were spent. And before a
live run, ask of every step after the human gate what happens if it fails: in this phase the answer
was "nothing can move the run forward", and finding that out at the gate cost a Thalos release.

### Part A, Thalos.NET 0.11.0

**A2**
- A duplicate `RunId` returns a Result failure naming the id, and the over-cap variables check
  returns a failure where it originates, so the blanket `catch ArgumentException` goes. Cost if wrong:
  the store's start contract changes, listed as breaking.

**A4**
- Reject at construction any `[ThalosTool]` parameter assignable to `ISecurityContext` that is not
  exactly `ISecurityContext`. Cost if wrong: a tool author meaning a concrete principal gets a startup
  error instead of a silent forgery.
- The guard becomes complete: nullable, array, generic and DTO-property shapes are walked
  recursively, by-ref principals refused, `object` the one documented limit. Cost if wrong: a tool
  taking a DTO that mentions a principal type must be reshaped.
- Replace the hand-written walk with a walk over System.Text.Json's own `JsonTypeInfo` from the
  tool's exact options, memoised. Cost if wrong: the guard depends on STJ metadata APIs, public and
  stable since .NET 7.
- The perf guard becomes a deterministic lookup counter, not a wall clock. Cost if wrong: an internal
  counter exposed through `InternalsVisibleTo`.
- `JsonConverter`-backed types are documented as free-form, not rejected. Cost if wrong: a converter
  author can still forge, which the docs name.

**A5**
- After following a link, re-walk its final target from the volume root. Cost if wrong: one extra
  walk per link.
- The `.git` refusal also runs on the resolved path, and NTFS aliases `git~N` are refused. Cost if
  wrong: a directory literally named `git~1` is refused.
- `:` is refused on every OS. Cost if wrong: a Linux file with a colon cannot be addressed.
- Link-dependent tests use `SkippableFact` and fail rather than skip under CI. Cost if wrong: one
  test package added.
- The unfalsifiable rooted check is removed as dead code. Cost if wrong: one fewer layer, covered by
  containment.
- `.` segments are refused on every OS. Cost if wrong: `./x` must be written `x`.
- Stop hand-resolving links: canonicalise through `realpath` on Unix and `GetFinalPathNameByHandle`
  on Windows, failing closed on any resolution failure. Cost if wrong: one P/Invoke per resolve, and
  dangling links are refused even when pointing inside.
- Only not-found exceptions mean absence; any other failure fails closed. Cost if wrong: an
  unreadable directory inside the workspace is refused.
- A lexical step refuses rooted and outside input first, with one generic message. Cost if wrong: an
  absolute path inside the workspace must be given relative.
- Every post-lexical failure returns the same generic refusal; detail goes to a debug log only. Cost
  if wrong: an operator error reads as a generic refusal.
