# UI Contract — Phase 1.6, Schedule Diagnostics

**Date:** 2026-09-18
**Phase:** 1.6 — Schedule management
**Design doc:** `docs/plans/2026-09-18-schedule-diagnostics-design.md`
**Design system:** sourced from `docs/design/MASTER.md`
**Route:** `/schedules`

This contract is the implementation spec and the audit target. `ui-review` grades the built page
against this file, not against intent.

## Design System

Sourced entirely from `docs/design/MASTER.md`. No new tokens, no new fonts, no new radius values.
Radzen components only; all colour by `--rz-*` token, never a literal hex.

### One required deviation from Radzen defaults

`RadzenBadge` renders white foreground on the severity colour. On `--rz-warning` (`#f59e0b`) that is
approximately **1.75:1**, which fails WCAG AA for text at any size.

**The `Overdue`, `Stranded` and `DeliveryUnknown` badges must use a dark foreground**, not the default
white. This is a contract requirement, not a preference — it is the only place this page knowingly
departs from library defaults, and `ui-review` should check it explicitly.

## Component Inventory

### `VerdictBadge`

The single place a verdict becomes visible. Every other component delegates to it, so the mapping
cannot drift across views.

- **Props:** `Verdict` (the eight-value enum), optional `Detail` string for the tooltip
- **Variants:** eight, one per verdict. Named here in full so this contract is auditable on its own
  rather than by cross-reference:

  | Verdict | Severity | What the row reads as |
  |---|---|---|
  | `Delivered` | Success | ran and arrived |
  | `Running` | Info | in flight right now |
  | `NotYetDue` | Light / muted | nothing wrong, not time yet |
  | `Overdue` | Warning — dark text | due and never claimed; is the sweeper alive |
  | `Stranded` | Warning — dark text | stuck mid-run past the threshold |
  | `DeliveryUnknown` | Warning — dark text | completed, outbox unreadable |
  | `Failed` | Danger | a step failed; error and step shown |
  | `Undelivered` | Danger | ran fine, delivery dead-lettered |

- **States:** none — pure display
- **Rules:** always renders the verdict name as text alongside the colour; never colour alone.
  `Undelivered` is danger, not warning — the run succeeded, so every other signal reads healthy and
  this is the one an operator must not scan past.

### `ScheduleOverview`

The landing view. Every schedule with its latest verdict.

- **Data:** `GetOverviewAsync`
- **≥768px:** `RadzenDataGrid`, `AllowPaging="true"`, `AllowSorting="true"`, `PageSize="15"` — matching
  `Executions.razor`
- **Columns:** Name, Verdict (`VerdictBadge`), Last run, Next run, Enabled
- **Row expansion** reveals `RunHistory` inline, so context is not lost
- **<768px:** not a grid — see Layouts

### `RunHistory`

Recent executions for one schedule, newest first.

- **Data:** `GetRunHistoryAsync(scheduleId, take)`
- **Columns:** Occurrence, Verdict (`VerdictBadge`), Step reached, Duration
- **Row selection** opens `RunDetail`

### `RunDetail`

Why this particular run ended as it did. The component that actually answers the page's question.

- **Always:** occurrence, verdict, step reached, timestamps
- **When `Failed`:** `LastError`, `FailedAtStep`, `Attempts`
- **When `Undelivered`:** `DeadLetterError`, `RetryCount`, and the resend action
- **When `Stranded`:** how long stuck, and the step it is stuck at
- **When `Delivered` or later:** `Findings` and `Digest`, collapsed by default — these are model output
  and can be long

### `ResendAction`

Offered only on an `Undelivered` run. Calls `RequeueAsync` on the outbox dashboard store.

- **States:** idle, in-flight, succeeded, failed
- **No confirmation dialog.** Requeueing puts the message back in the outbox for normal dispatch;
  the worst case is a duplicate digest, not data loss. A confirm step here would be ceremony.
- On success the row's verdict re-resolves on the next refresh rather than being optimistically
  rewritten — the page must not claim a delivery it has not observed.

## Layouts

### Desktop — 1280px and above

Existing chrome: 260px dark sidebar, header, main content. `/schedules` gains a
`RadzenPanelMenuItem` under the **Operations** group.

```text
┌──────────┬────────────────────────────────────────────┐
│ sidebar  │  Schedules                                  │
│ 260px    │  ┌──────────────────────────────────────┐  │
│          │  │ Name │ Verdict │ Last │ Next │ On    │  │
│ Ops      │  ├──────────────────────────────────────┤  │
│  …       │  │ daily-digest │ [Failed] │ … │ … │ ✓  │  │
│  Sched.  │  │   ▼ expanded: RunHistory + RunDetail │  │
│          │  └──────────────────────────────────────┘  │
└──────────┴────────────────────────────────────────────┘
```

### Tablet — 768px to 1279px

Sidebar collapses behind the existing `RadzenSidebarToggle`. The grid **drops** its lower-value
columns — `Next run` and `Enabled` — rather than shrinking all of them. Name and Verdict never drop.

### Mobile — below 768px

**Not a grid.** `RadzenDataGrid` scrolls horizontally rather than stacking, which on a diagnostic page
means scrolling sideways to reach the column that says what went wrong.

One `RadzenCard` per schedule, stacked:

```text
┌────────────────────────────┐
│ daily-digest    [ Failed ] │
│ Writer step · 07:04        │
│ provider returned 529      │
│                    Details │
└────────────────────────────┘
```

Name and verdict badge lead. The error line is visible without interaction. `Details` expands to
`RunDetail`. No horizontal scrolling anywhere on this breakpoint.

## Interaction States

| Surface | Loading | Empty | Error | Success |
|---|---|---|---|---|
| Overview | Radzen grid's built-in loading indicator; cards show skeleton placeholders on mobile | `RadzenAlert` — "No schedules configured", pointing at the `ScheduledRuns` config section | `RadzenAlert` severity error, with a retry action | Grid or cards render |
| Run history | Inline spinner within the expanded row | "No runs yet" — a valid state for a schedule that has never fired | Inline `RadzenAlert`; does not collapse the parent row | Rows render |
| Run detail | Inherits the parent's loading state | n/a — only opened for an existing run | Inline error; the surrounding verdict still shows | Detail renders |
| Resend | Button shows in-flight, disabled | n/a | `RadzenAlert` with the failure reason; the button re-enables | Confirmation message; verdict re-resolves on next refresh |

**The empty state must never be an empty table.** An unstyled empty grid reads as "no schedules" when
the truth may be "the request failed" — the exact ambiguity this page exists to remove.

`DeliveryUnknown` is a first-class rendered state, not an error: the run completed and the outbox could
not be read. The page says exactly that rather than guessing `Delivered`.

## Accessibility

- **Contrast:** dark foreground on all `--rz-warning` badges, per the deviation above. All other
  verdict badges use library defaults, which meet AA.
- **Never colour alone:** every badge carries its verdict as text. A monochrome screenshot must still
  be readable.
- **Semantics:** `RadzenDataGrid` provides table roles. The page has one `<h1>`. The mobile card list
  is a list, not a table.
- **Keyboard:** row expansion is reachable and toggleable by keyboard, not mouse-only. `ResendAction`
  is a real `<button>`. Tab order follows visual order.
- **Focus:** expanding a row moves focus into the expanded region; collapsing returns it to the row.
  Focus is never lost to `<body>`.
- **Live regions:** the resend result is announced, not only shown — it is the one action whose
  outcome a screen-reader user would otherwise miss.

## Open Questions

Two decisions I did not want to make silently.

1. **Should a specific run be deep-linkable?** A URL like `/schedules/{id}/runs/{executionId}` makes a
   failure shareable — "look at this one" — which matters for a diagnostic page. Row expansion alone
   is not addressable. *Recommendation:* ship expansion now, and put the schedule id in the query
   string so at least a schedule's view is linkable; full per-run routing as a follow-up.

2. **How much of `Findings` and `Digest` should render?** These are model output and can be long.
   *Recommendation:* collapsed by default, expand on demand, with no truncation once expanded —
   truncating the digest on a page whose job is showing you the digest would be self-defeating.

## Out of Scope

Creating or editing schedules; the stranded-run reaper itself — this page makes stranded runs visible,
which is its precondition; anything touching the scout's missing repository tooling; dark mode; and any
new font or spacing scale, all of which are product-wide decisions per `MASTER.md`.
