# Phase 2.6 — Sandbox network and Docker client spike

**Date:** 2026-10-01 · **Phase:** 2.6 · **Status:** finding, confirmed with amendments

Spike SP of the phase 2.6 plan (`docs/plans/2026-10-01-phase-2.6-sandboxed-run-pods-plan.md`). Throwaway
harness, nothing kept but this finding.

> **Verdict.** F8 is **confirmed**, not overturned: an `--internal` network has no route out, the squid
> egress proxy lets NuGet through and refuses everything else, and the nginx gateway reaches a sandbox
> on the internal network by Docker DNS from a host process. The per-route MCP mechanism is
> **confirmed**: `MapMcp("/mcp/{source}")` + `ConfigureSessionOptions` works. **But both config files
> in Task A6 fail as written.** The `squid.conf` and the `nginx.conf` are each fatal at startup and must be
> amended before A6 is implemented (see *Required plan changes*). One new risk needs an owner decision:
> sandboxes on the shared internal network can reach each other (see *Lateral reachability*).

Environment: Windows 11, Docker Desktop, Engine 29.5.2 (API 1.54, linux/amd64), .NET SDK 10. Images:
`curlimages/curl:8.10.1`, `ubuntu/squid:6.6-24.04_beta` (squid 6.13), `nginx:1.27-alpine` (nginx 1.27.5),
`mcr.microsoft.com/dotnet/sdk:10.0`. Every Docker object was named `spike-sp-*` or labelled `spike=sp`
and removed afterwards. The spike used the network name `spike-sp-internal`, not `thalos-sbx-spike`.
Harness: shell scripts, a console app for Docker.DotNet.Enhanced 4.3.3 and raw REST, and an ASP.NET app
for MCP 2.2.0. All of it lived under the session scratchpad and was deleted after this file was
written.

## Q2 — egress proxy (squid)

The container was set up the way A6 says: `docker create` on the default bridge, the config put in by
put-archive (`docker cp`), `docker network connect --alias egress spike-sp-internal`, then start.

**The `squid.conf` in A6 is fatal twice:**

1. `ERROR: 'api.nuget.org' is a subdomain of '.nuget.org'` and then `FATAL: Bungled /etc/squid/squid.conf
   line 2: acl nuget dstdomain api.nuget.org .nuget.org globalcdn.nuget.org`. Squid 6 refuses a
   `dstdomain` list in which one entry is covered by another. `.nuget.org` already matches
   `nuget.org`, `api.nuget.org` and `globalcdn.nuget.org`.
2. `FATAL: Cannot open '/dev/stdout' for writing. The parent directory must be writeable by the user
   'proxy'`. The image's squid drops to `proxy`, which cannot open the container's stdout. The
   image's entrypoint already `tail -F`s `/var/log/squid/access.log` to stdout.

The working config:

```
http_port 3128
acl nuget dstdomain .nuget.org {{EXTRA}}
acl SSL_ports port 443
acl CONNECT method CONNECT
http_access deny CONNECT !SSL_ports
http_access allow CONNECT nuget
http_access allow nuget
http_access deny all
cache deny all
access_log daemon:/var/log/squid/access.log squid
```

The same overlap rule applies to `{{EXTRA}}`. An extra domain that is covered by `.nuget.org`, or by
another extra entry, is fatal. Two examples are `foo.nuget.org`, and `a.example.com` next to
`.example.com`. Validation must reject or de-duplicate those, not just apply the regex.

Results with the fixed config:

```
curl -x http://egress:3128 https://api.nuget.org/v3/index.json   → 200
curl -x http://egress:3128 https://example.com                   → curl: (56) CONNECT tunnel failed, response 403
curl -x http://egress:3128 http://example.com                    → 403
curl -x ... -p http://api.nuget.org:80/                          → CONNECT 403  (deny CONNECT !SSL_ports)
curl -x ... https://nuget.org.evil.example                       → CONNECT 403
SDK container, internal network only, HTTPS_PROXY=http://egress:3128:
  dotnet new classlib && dotnet add package Newtonsoft.Json && dotnet restore
  → "PackageReference for package 'Newtonsoft.Json' version '13.0.4' added", rc=0, 9.1 s
squid access log: TCP_TUNNEL/200 CONNECT api.nuget.org:443 (×4);
  TCP_DENIED/403 GET http://crl3.digicert.com/... , http://ocsp.digicert.com/... , http://www.microsoft.com/pkiops/crl/...
```

NuGet's signature verification tries the CRL and OCSP endpoints of DigiCert and Microsoft over plain
HTTP. The proxy denies them at once, and restore still succeeds without a delay. Over all the spike
runs, 211 such requests were denied. `NUGET_CERT_REVOCATION_MODE=offline` would stop the attempts. It
is optional and only reduces log noise.

## Q3 — gateway (nginx)

The gateway was set up the same way: create on the default bridge with `-p 127.0.0.1:18431:8080`, put
`/etc/nginx/conf.d/default.conf`, connect to the internal network with alias `gateway`, then start. The
probe "sandbox" was `nginx:1.27-alpine` named `thalos-sandbox-<32hex>`, attached with
`--network spike-sp-internal` only, serving `return 200 "probe uri=$request_uri"` on 8080.

**The `nginx.conf` in A6 is fatal:** `[emerg] pcre2_compile() failed: missing closing parenthesis in
"^/sandboxes/(?<sid>[0-9a-f]"`. An unquoted `{32}` ends the regex token. The regex has to be quoted:

```nginx
location ~ "^/sandboxes/(?<sid>[0-9a-f]{32})/(?<rest>.*)$" {
```

With only that change, routing works. There is a second issue: `$rest` is a capture from the
*normalised, decoded* URI. A request for `/sandboxes/<id>/a%2Fb%20c` comes back as **400**, because
nginx rebuilds an upstream URI that contains a raw space, and `%2F` would be turned into `/`. The
following variant takes the remainder from the raw `$request_uri`. It was verified: the upstream sees
`/a%2Fb%20c?q=%20x`, and the 404 cases are unchanged.

```nginx
map $request_uri $sbx_rest {
    "~^/sandboxes/[0-9a-f]{32}(?<r>/[^?]*)" $r;
    default "/";
}
server {
    listen 8080;
    resolver 127.0.0.11 valid=10s ipv6=off;
    client_max_body_size 512m;
    # Only a 32-hex sandbox id is routable; anything else is a 404 and never proxied.
    location ~ "^/sandboxes/(?<sid>[0-9a-f]{32})/" {
        proxy_pass http://thalos-sandbox-$sid:8080$sbx_rest$is_args$args;
        proxy_http_version 1.1;
        proxy_set_header Connection "";
        proxy_buffering off;
        proxy_request_buffering off;
        proxy_read_timeout 1800s;
        proxy_send_timeout 1800s;
    }
    location / { return 404; }
}
```

The `map` sits at the top level of `conf.d/default.conf`, which nginx includes inside `http {}`, so
that is legal.

Measured from the host process over `127.0.0.1`:

| Measurement | Value |
|---|---|
| Steady-state GET through the gateway (200 requests) | p50 3.3 ms, p95 12.7 ms, max 27.1 ms |
| Gateway-local 404, no proxying (200 requests) | p50 3.6 ms, p95 9.6 ms |
| create + put-archive + start of a sandbox | 1.07–1.43 s (3 runs) |
| start → first 200 through the gateway | 118–175 ms (3 runs), first try every time |
| Unknown id | 502 after about 2.6 s, which is how long Docker DNS takes to answer NXDOMAIN |
| GET before the container exists (502), then create + start, then GET again | 200 on the first retry, after 79 ms. The `valid=10s` resolver did not keep the negative answer |

## Q4 — two networks

Both forms work, on the CLI and through the API:

- **Create, then connect** (the form A6 uses):
  `POST /containers/create` with `HostConfig.NetworkMode = "bridge"`, then
  `POST /networks/{internal}/connect` with body
  `{"Container":"<id>","EndpointConfig":{"Aliases":["egress"]}}`, then `POST /containers/{id}/start`.
  Connecting works on a **created, not yet started** container, and the alias is in place at start.
  Docker.DotNet: `Networks.ConnectNetworkAsync(net, new NetworkConnectParameters { Container = id,
  EndpointConfig = new EndpointSettings { Aliases = ["egress"] } })`.
- **Two endpoints at create** (API ≥ 1.44): `POST /containers/create` with
  `NetworkingConfig.EndpointsConfig = { "bridge": {}, "<internal>": { "Aliases": ["egress"] } }`.
  The container came up attached to `bridge[]` and to `spike-sp-lib-net-a[egress]`. On the CLI this is
  `docker run --network bridge --network <internal>`, and
  `--network "name=<internal>,alias=egress2"` also works.
- **A network-scoped alias on the default `bridge` is rejected:** `400 invalid endpoint settings:
  network-scoped aliases are only supported for user-defined networks`. Aliases belong on the internal
  network only, as A6 already does.

**Recommendation:** keep create-then-connect. It works on every API version, and the put-archive of
the config naturally falls between create and start.

## Q5 — Docker client

`Docker.DotNet.Enhanced` **4.3.3** is the version both Testcontainers 4.14.0 and 4.15.0 depend on.
The test ran from Windows over `npipe://./pipe/docker_engine`. The same binary also ran inside a Linux
container over `unix:///var/run/docker.sock`, with the socket bind-mounted for the test only. Every
operation passed:

| Operation | Docker.DotNet.Enhanced 4.3.3 | Raw REST over pipe/socket (`SocketsHttpHandler.ConnectCallback` → `NamedPipeClientStream` / `UnixDomainSocketEndPoint`, `/v1.44/`) |
|---|---|---|

| Create a volume | ✓ | ✓ 201 |
| Create a container with `User`, `Env`, `HostConfig { NetworkMode, CapDrop=["ALL"], SecurityOpt=["no-new-privileges:true"], ReadonlyRootfs=true, NanoCPUs, Memory, MemorySwap, PidsLimit, Tmpfs, Mounts(volume), AutoRemove=false }` | ✓ and the inspect reads every flag back exactly | ✓ 201 (JSON key is `NanoCpus`) |
| Put an archive into a **stopped** container | ✓ `Containers.ExtractArchiveToContainerAsync(id, new CopyToContainerParameters { Path = "/work" }, tar)` | ✓ `PUT /containers/{id}/archive?path=/work` 200 |
| Connect a network with an alias | ✓ | ✓ 200 |
| List by label | ✓ `ListContainersAsync(new ContainersListParameters { All = true, Filters = { ["label"] = { ["k=v"] = true } } })` | ✓ `GET /containers/json?all=true&filters={"label":[...]}` |
| Exec | ✓ `Exec.CreateContainerExecAsync` + `StartContainerExecAsync(id, new ContainerExecStartParameters())` → `MultiplexedStream.ReadOutputToEndAsync` | not needed |
| Force-delete a container, a volume and a network | ✓ A second delete throws `DockerContainerNotFoundException`, the 404 | ✓ 204, and the second delete gives 404 |

Docker.DotNet facts that A6 needs:

- **4.x has no `DockerClientConfiguration`.** The entry point is
  `new DockerClientBuilder().WithEndpoint(uri).WithTimeout(t).Build()`.
- **The library throws when the engine is unreachable.** A missing named pipe waits for the whole
  timeout and then throws `TaskCanceledException`, after 5046 ms with `WithTimeout(5 s)`. A refused
  TCP endpoint throws `AggregateException(SocketException)`. `CreateAsync` must catch these and return
  `AgentError.ProviderError`, which is what `An_unreachable_engine_fails_create_without_throwing`
  tests. It also needs a short client timeout, or a missing Docker Desktop holds `CreateAsync` for
  the default timeout.
- **A put-archive into the rootfs of a `ReadonlyRootfs` container is refused**, whether the container
  is stopped or running: `400 container rootfs is marked read-only`. The same applies to a `tmpfs`
  path such as `/tmp`. A put-archive into the **volume** mount `/work` succeeds. A6's run containers
  can therefore get their bundle only through `/work`. The egress and gateway containers are not
  read-only, so their config put still works.
- **The `/work` volume is owned by root unless the image says otherwise.** A fresh named volume copies
  the ownership of the image's `/work`. If the image has no `/work`, the root of the volume is
  `root:root 755`, and `User 10001` gets `touch: /work/w: Permission denied`. A `./` entry in the
  archive does **not** change the owner of the target directory. Two fixes were verified: (a) the
  sandbox image runs `mkdir /work && chown 10001:10001 /work`, and copy-up makes `/work` owned by
  10001; (b) the archive carries a subdirectory, such as `repo/…`, with uid and gid 10001. Use (a),
  and also write archive entries as 10001.

**Choice:** Docker.DotNet.Enhanced 4.3.3. None of the operations is missing. The library is maintained:
there were 8 releases between 2026-03-17 and 2026-06-28, and the latest is about 3 months old. It
handles npipe and unix sockets itself. Raw REST works too, but it would mean hand-writing the models
and the transport for no gain.

## Q6 — MCP tools per route (ModelContextProtocol.AspNetCore 2.2.0)

`MapMcp` in 2.2.0 is `MapMcp(IEndpointRouteBuilder, string pattern)`, and `HttpServerTransportOptions`
is a single DI-wide options object. The second option in the brief, *three `MapMcp` calls with
separate options*, therefore does not exist in this API. The first option works:

```csharp
builder.Services.AddMcpServer()
    .WithHttpTransport(o =>
    {
        // Stateless is the 2.2.0 default; keep it (see the caveat below).
        o.ConfigureSessionOptions = (http, options, ct) =>
        {
            var source = http.Request.RouteValues["source"] as string;
            options.ToolCollection = [];                 // REQUIRED: drops DI-registered tools
            if (source is not null && toolSets.TryGetValue(source, out var set))
                foreach (var tool in set) options.ToolCollection.Add(tool);
            return Task.CompletedTask;
        };
    });
app.MapMcp("/mcp/{source:regex(^(workspace|sandbox|roslyn)$)}");
```

Measured with `McpClient.CreateAsync(new HttpClientTransport(new HttpClientTransportOptions { Endpoint =
…/mcp/<source>, TransportMode = HttpTransportMode.StreamableHttp }))`:

```
/mcp/workspace: tools=[workspace_write,workspace_read]  call own → ok; call sandbox_build → McpProtocolException: Unknown tool: 'sandbox_build'
/mcp/sandbox:   tools=[sandbox_test,sandbox_build]      call own → ok; call workspace_write → Unknown tool
/mcp/roslyn:    tools=[roslyn_find_callers]             call own → ok; call workspace_write → Unknown tool
/mcp/other → 404 (route constraint)
first connect+list ≈ 210–310 ms (JIT), later routes 1–3 ms
```

- **You must reset `ToolCollection`.** Tools registered through `WithTools(...)` / DI are already in
  `options.ToolCollection` when the callback runs. Without the reset, a DI-registered `global_leak`
  tool showed up on **all three** routes. The collection is a per-session copy: in the no-reset run,
  the route sets did not build up across requests, so changing it does not race other sessions.
- **Caveat for Stateful mode:** an `Mcp-Session-Id` is not bound to the route that created it. A
  session initialised on `/mcp/sandbox` and replayed on `/mcp/workspace` returned **200 with the
  sandbox tool list**. The route's own endpoint auth still runs, but the tool set comes from the
  session. Use **Stateless**, which is the 2.2.0 default and the only mode for the `2026-07-28`
  protocol. In Stateless mode the callback runs on every request, so the route always decides. If
  Stateful mode is ever needed, the session must be bound to its route.

## Lateral reachability between sandboxes (new risk, needs an owner decision)

Every run container shares one internal network. From inside sandbox A:

```
curl --noproxy '*' http://thalos-sandbox-<B>:8080/direct                → 200 "probe uri=/direct"
curl --noproxy '*' http://gateway:8080/sandboxes/<B>/via-gateway         → 200
curl -x http://egress:3128 http://thalos-sandbox-<B>:8080/               → 403 (squid blocks it)
```

So one run's code (MSBuild targets, tests) can call another run's sandbox host directly, or through the
gateway, given the other run's id. F8 does not cover this. The ids are 32 hex characters and hard to
guess, but they are not secret by design, and Docker DNS will resolve any name that exists. Options:

1. **A per-run secret.** The API generates a bearer token at create time and passes it to the
   container in `SandboxSpec.Environment`. The sandbox host rejects any request without it. This is
   cheap and works the same on Kubernetes.
2. **A network per run.** The gateway and the egress proxy are connected to each run's own internal
   network. Sandboxes then cannot see each other directly, but they can still reach each other
   through `gateway:8080`. So this still needs option 1, or an nginx rule that rejects clients from
   sandbox networks.

The spike recommends option 1. It is a new security invariant, so it is the owner's call, and it should
be added to Task A6/A8 or tracked as a follow-up.

## Decisions

- **Docker client:** `Docker.DotNet.Enhanced` **4.3.3**, the version Testcontainers 4.14.0 and 4.15.0
  depend on. It does every required operation over npipe and unix sockets and is maintained, with its
  last release on 2026-06-28. Build it with `new DockerClientBuilder().WithEndpoint(uri)
  .WithTimeout(…).Build()`.
- **F8: confirmed.** That is an internal network, plus squid egress on bridge and internal (alias
  `egress`), plus an nginx gateway on bridge and internal (alias `gateway`) published on
  `127.0.0.1:<port>`, set up by create, put-archive, connect, start. The two configs are amended as
  shown above.
- **MCP per route:** a single `MapMcp("/mcp/{source:regex(^(workspace|sandbox|roslyn)$)}")`, with
  `ConfigureSessionOptions` replacing `options.ToolCollection` by the route's set. Stateless mode, which
  is the default.
- **Latency:** the gateway adds about 3 ms at p50. Container create to the first proxied 200 takes
  about 1.2–1.6 s. A cold sandbox is ready in about 20 s for this repo: about 1.5 s container, under
  0.1 s clone, 5–9 s restore and 13–15 s RoslynCodeLens. The sandbox image is 400 MB compressed.

## Required plan changes (Tasks A6, A8, B2)

- **A6 `squid.conf`:** use `acl nuget dstdomain .nuget.org {{EXTRA}}` and
  `access_log daemon:/var/log/squid/access.log squid`. The `ExtraEgressDomains` validation must also
  reject an entry already covered by `.nuget.org` or by another entry, because squid treats such an
  overlap as fatal.
- **A6 `nginx.conf`:** quote the `location` regex. Prefer the `map $request_uri` variant above, so that
  encoded paths reach the sandbox unchanged. Add a gateway test for an encoded path such as `a%2Fb`.
- **A6 `DockerSandboxRuntime`:**
  - Use the 4.x `DockerClientBuilder` API.
  - Catch every exception from the library and return `ProviderError`, with a short timeout.
  - Put the run bundle only into `/work`; a put into the read-only rootfs gives 400.
  - Write archive entries with uid and gid 10001.
  - Set `HOME`/`DOTNET_CLI_HOME` under `/work`, or keep them in the spec's env, because the rootfs is
    read-only. S1's env check has to allow these keys.
  - The `SecurityOpt` string is `no-new-privileges:true`, as A6 already says. The spike verified only
    that form. The brief's bare `no-new-privileges` was not tested.
- **A12 Dockerfile (feeds A6/B2 images):** add `mkdir /work && chown 10001:10001 /work` before
  `USER 10001`. Without it, `/work` is root-owned and the sandbox user cannot write. git is already in
  `sdk:10.0`.
- **A8 / B2 MCP routing:** use `ConfigureSessionOptions` with an explicit `ToolCollection` reset, keep
  Stateless mode, and test that a DI-registered tool does not appear on any route. If any route ever
  runs Stateful, a session must be bound to the route that created it.
- **Owner decision:** sandbox-to-sandbox reachability (above). The recommendation is a per-run bearer
  secret, checked by the sandbox host.
- **Optional:** `NUGET_CERT_REVOCATION_MODE=offline` in the sandbox env avoids repeated denied
  CRL/OCSP requests. Restore succeeds without it.

## Conclusion

The F8 network design holds on Windows Docker Desktop. With no default route on the internal network,
